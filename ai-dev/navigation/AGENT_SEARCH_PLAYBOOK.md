# AI-навигация: где искать и как не тратить контекст

**Цель:** быстро находить нужную реализацию, не превращая каждую задачу в полный аудит репозитория. Порядок из старого `_ai/README.md`, `_ai/MODULE_CROSS_REFERENCE_MAP.md` и `_ai/SERVICES_API.md` адаптирован к Platform 2.0.

## Перед каждым циклом

1. Прочитать **только** `AGENTS.md`, карточку текущей задачи, инструкцию назначенной роли и последние относящиеся к ней подтверждённые изменения.
2. Открыть `FILE_MAP.md` и **один релевантный раздел** `ai-dev/navigation/CODEBASE_MAP.md`. Детальную v1.2 читать по вопросу, не целиком.
3. Получить `git rev-parse HEAD`, ветку и `git status` **в нужном репозитории**; зафиксировать `NOT VERIFIED`, если Git отсутствует.
4. Проверить существование названных файлов (пример: `git ls-files 'js/services/*'`, `rg --files src/services/locations`). При расхождении — ограниченный поиск внутри соответствующего каталога.
5. Прежде чем разрабатывать аналог, искать публичный API в текущих сервисах и UI: `rg -n 'createContext|loadModule|LocationService' js/core src/services` — только пример, запрос должен быть узким.
6. Посмотреть контракт **и вызывающих пользователей** новой/изменяемой функции. Историческая карта межмодульных связей — указатель, а не доказательство текущего состояния.
7. Для модульной функции определить: владелец данных, единый источник, интерфейс и границу безопасности. Фиксировать решение `REUSE / EXTEND / EXTRACT / NEW`.
8. После изменений и PASS обновлять карту **только при изменении маршрута поиска** (новый файл, перенос, новый сервис, контракт), а не переписывать весь реестр каждый раз.

## Навигация по типу запроса

- **Новый модуль:** `js/core/module-loader.js` → `js/modules/modules.manifest.js` → `js/core/app.entry.js` → пример `src/modules/construction-v2/index.ts` → фактическая конфигурация сборки.
- **Роль/право:** `ai-dev/standards/AUTH_AND_ACCESS.md` → `js/services/permission.service.js` (история) → схема нового server-side access (пока проектируется) → тесты RLS/API.
- **Тема/кнопка:** `ai-dev/standards/DESIGN_SYSTEM.md` → `css/brand/rbi.css` / `css/rbi-ui.css` → текущая реализация React-обёртки, если существует.
- **Локация/ВОР:** `src/services/locations/` → `js/services/masterData.service.js` → текущий контракт → спецификация Plan/Fact. **Не пытаться получить позицию ВОР как узел локаций.**
- **Данные/синк:** `js/services/storage/` → `js/services/sync/` → `sql/` → реальные миграции нового окружения. **Не вызывать production.**
- **Бизнес-расчёт:** фактический доменный код и тесты текущего модуля; исторические PF-1…PF-6 — только подсказка поиска.

## Статусы сведений в отчёте

- `CONFIRMED IN CODE` — проверен конкретный файл и commit.
- `HISTORICAL` — найдено лишь в `_ai.zip`/старом отчёте/архивном снимке.
- `PROPOSED` — целевая архитектура, но код не подтверждён.
- `NOT VERIFIED` — проверить не удалось; объяснить недостающий источник.

**Запрещено:** массово читать все папки, выполнять подряд все исторические `_ai/scripts/`, использовать `_ai/TEST_CREDENTIALS.md`, объявлять `READY_FOR_REVIEW` из старого журнала эквивалентом пройденной независимой приёмки или домысливать отсутствующий код.
