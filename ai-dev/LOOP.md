# Platform 2.0 — рабочий цикл с передачей через файлы (две роли, ADR-062)

Определяет, **как** Архитектор и Исполнитель передают работу без пересказа в чате. Что делают роли — `WORKFLOW.md`. При расхождении главнее `AGENTS.md` и ADR-062.

## 1. Схема

```text
ARCHITECT ⇄ владелец (обсуждение блока) ──PLAN_READY──▶ «Исполнитель.» ──▶ EXECUTOR
   ▲                                                                       │ код → самопроверка → документы
   │                                                                       ▼
   └──── «Архитектор. принято ID» / «Вернуть ID: …» ◀── READY_FOR_ACCEPTANCE (или BLOCKED)
```

Одна сессия = одна роль. Владелец может сменить роль в том же чате фразой запуска. ID задачи роль берёт из `CURRENT_CONTEXT.md`, если владелец его не назвал.

## 2. Файлы передачи (`ai-dev/handoff/`, перезаписываются; история — `ai-dev/reports/<ID>/`)

| Файл | Пишет | Читает | Содержимое (≤ 40 строк) |
|---|---|---|---|
| `LATEST_ARCHITECT_PLAN.md` | ARCHITECT | EXECUTOR | ID, цель блока, карточка, что менять / не трогать, проверки, откат |
| `LATEST_EXECUTOR_REPORT.md` | EXECUTOR | владелец, ARCHITECT | repo/branch/commit, что сделано, **самопроверка (команда → результат)**, какие документы обновлены, NOT RUN и почему, вопросы |

Полный отчёт: `reports/<ID>/executor-<n>.md` (шаблон `templates/IMPLEMENTATION_REPORT.md` + раздел самопроверки по `templates/TEST_REPORT.md`).

## 3. Маркеры `STATUS:` (последняя строка `LATEST_*`)

| Роль | Значения |
|---|---|
| ARCHITECT | `PLAN_READY` · `NO_TASK_PENDING` (нужно решение владельца) |
| EXECUTOR | `READY_FOR_ACCEPTANCE` · `BLOCKED` |

**Правило входа:** EXECUTOR стартует, только если `LATEST_ARCHITECT_PLAN` = `PLAN_READY` по активной задаче (или по фразе «Доработка ID» после возврата). ARCHITECT стартует без активной задачи, после `BLOCKED`, после «принято ID» / «Вернуть ID».

## 4. Ворота владельца

- **Утверждение плана:** «**Исполнитель.**» при `PLAN_READY`. Исполнитель ставит карточке `IN_PROGRESS` и вписывает дату и цитату в карточку.
- **Приёмка:** «**Архитектор. принято P2-xxxx**» → Архитектор ставит `DONE`, заполняет `ACCEPTANCE_RECORD`, для CRITICAL-блоков перед этим делает read-only ревью diff (ADR-062), предлагает следующий блок.
- **Возврат:** «**Вернуть P2-xxxx: …**» → карточка `IN_PROGRESS`, Исполнитель дорабатывает по замечаниям («Исполнитель. Доработка P2-xxxx»).

## 5. Выбор следующего блока (ARCHITECT)

1. Источник — `ai-dev/ROADMAP.md` и `ai-dev/MVP_BACKLOG.md` по порядку; перепрыгивать без решения владельца нельзя.
2. Размер и нарезка — по `standards/BLOCK_SIZING.md`: один видимый результат, 3–7 этапов вертикальными срезами, контрольная точка (проверка + стоп-условие + коммит) после каждого этапа, не больше одной CRITICAL-зоны.
3. Перед планом — reuse review, Single Source of Truth review, impact-review для общих сервисов (`standards/*`).
4. Побочные находки — в `docs/TECH_DEBT.md` или правкой Markdown, отдельной задачей не оформлять.
5. **Сначала обсудить** блок с владельцем (2–3 варианта + рекомендация простым языком), потом писать карточку.

## 6. Короткие запуски

| Действие | Фраза |
|---|---|
| Планирование | `Архитектор. Следующий блок.` |
| Выполнение | `Исполнитель.` (или `Исполнитель. P2-xxxx`; после возврата: `Исполнитель. Доработка P2-xxxx`) |
| Приёмка | `Архитектор. принято P2-xxxx` |
| Возврат | `Вернуть P2-xxxx: <что не так>` |

Скилы `platform2-architect`, `platform2-executor` подхватывают роль по этим фразам. Скил `platform2-verify` — устарел (ADR-062), отключить.

## 7. Рабочие папки

- **Регламент и карточки (мастер-копия, единственная):** репозиторий `~/dev/platform-2-core` — корень (`CLAUDE.md`, `AGENTS.md`, `FILE_MAP.md`, `ai-dev/`). Перенесено в P2-0002 этап 6 (20.10.2026, вариант А владельца); iCloud-папка `Platform_2_0_AI_Roles_Workflow_v1_3__ARCHIVE_moved_to_repo` — архив, не редактировать.
- **Код:** `~/dev/platform-2-core` (позже `~/dev/planfact-smr`). `rbi-q-main/` — только чтение.
- Регламент хранится только в репозитории (решение владельца 20.10.2026, P2-0002) — одна копия.

## 8. Что не меняется

AGENTS §3: production RBI/Quality не изменять; новые Supabase-объекты — по ADR-061; merge, миграции на боевую БД, деплой — только по прямому разрешению владельца; push task-ветки — если в фразе есть «push разрешён»; NOT RUN ≠ PASS; роль не принимает собственную работу.

## 9. Скилы

Копии скилов — `ai-dev/skills-backup/`. Актуальные под ADR-062: `platform2-architect`, `platform2-executor`. `platform2-verify` — отключить в настройках скилов.
