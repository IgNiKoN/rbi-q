# Platform 2.0 — цикл разработки (две роли, ADR-062)

## 1. Принцип

Работаем **крупными законченными блоками**: результат блока владелец может увидеть и оценить (рабочий экран, отчёт по реальным файлам, проверенная миграция). Блок не дробится на мелочь ради формы и не раздувается до «всего MVP». Цель — настоящий MVP Plan/Fact, а не бесконечная подготовка.

## 2. Роли

| Кто | Делает | Не делает |
|---|---|---|
| **ARCHITECT** | изучает ТЗ/архитектуру/код; предлагает блок; **обсуждает с владельцем**; пишет карточку `tasks/<ID>.md` и план; при приёмке CRITICAL-блоков делает read-only ревью | не пишет продуктовый код/SQL; не принимает работу |
| **EXECUTOR** | реализует план; пишет тесты; **сам тестирует** по `roles/TESTER.md`; **сам документирует** по `roles/DOCUMENTER.md`; сдаёт отчёт | не выходит за план без согласования; не ставит DONE |
| **Владелец (Игорь)** | утверждает план, принимает или возвращает результат, меняет состав MVP | — |

## 3. Порядок

1. **ARCHITECT:** «Архитектор. Следующий блок.» → обсуждение с владельцем (варианты + рекомендация) → карточка `DRAFT` + `handoff/LATEST_ARCHITECT_PLAN.md` (`STATUS: PLAN_READY`).
2. **Владелец:** «Исполнитель.» — это утверждение плана.
3. **EXECUTOR:** код + тесты → самопроверка (команды и фактические результаты) → документация в той же ветке → отчёт `reports/<ID>/executor-<n>.md` + `handoff/LATEST_EXECUTOR_REPORT.md` (`STATUS: READY_FOR_ACCEPTANCE` или `BLOCKED`).
4. **Владелец:** «Архитектор. принято ID» → `DONE` / «Вернуть ID: …» → Исполнитель дорабатывает.

## 4. Статусы карточки

```text
DRAFT ─[«Исполнитель.»]→ IN_PROGRESS ─[самопроверка + документы]→ READY_FOR_ACCEPTANCE ─[«принято»]→ DONE
                              ↑                                          │
                              └──────────── «Вернуть ID: …» ─────────────┘
IN_PROGRESS ─[нет среды/доступа/решения]→ BLOCKED → ARCHITECT/владелец
```

## 5. Самопроверка Исполнителя (обязательна)

- Сборка, `tsc`, unit/integration, пользовательский сценарий карточки — **команда → фактический результат**.
- Для данных/прав — негативные тесты (чужая компания/проект/роль).
- NOT RUN ≠ PASS: что не запускалось — указать причину; при обязательной проверке → `BLOCKED`.
- Перед сдачей — просмотреть свой полный diff: нет ли файлов вне плана и «правок заодно».

## 6. Расхождения

- Нужно выйти за план или поменять архитектуру → стоп, вопрос Архитектору/владельцу.
- Нет среды, доступа, тестовых данных → `BLOCKED` с точным условием разблокировки.
- Риск для production → немедленно остановиться, ничего не проверять на боевых данных.

## 7. Git

Одна задача → одна task-ветка → один diff. Push — если владелец написал «push разрешён»; merge, миграции на боевую БД, деплой — только по прямому разрешению владельца.

Файловый протокол передачи — `LOOP.md`. Экономное чтение — `CORE_RULES.md`.
