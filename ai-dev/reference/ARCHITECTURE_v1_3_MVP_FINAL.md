# Platform 2.0 — итоговая архитектура и план быстрого MVP

**Версия:** 1.3 · **Дата:** 20.10.2026  
**Статус:** согласованная архитектурная база; детали реализации проверяются по актуальному Git и серверу.  
**Рабочее название:** Platform 2.0. Коммерческое имя выбирается позднее.  
**Первый продукт:** Plan/Fact СМР (React + TypeScript).  
**Назначение:** единый рабочий документ для дальнейшей разработки и выдачи небольших задач в Cursor.

> **Главное решение от 20.10.2026.** Действующая RBI Platform используется отделом, работает и пока не требует развития. Есть конкретный заказ на Plan/Fact СМР; приоритет — как можно быстрее показать заказчику **настоящий работающий MVP**, затем развивать его итерациями. Сейчас реализуем **только минимальный фундамент**, отсутствие которого в будущем заблокирует независимые модули, безопасность или развитие продукта. Полную Construction OS заранее не строим.

## 1. Правило приоритета и объём текущих работ

- **Сейчас (MVP):** изолированная копия оболочки RBI Platform; отдельный репозиторий и сборка React-модуля; проверенный контракт подключения; основы company/project/security; минимальные мастер-данные и настоящая цепочка «ВОР → план → факт → отклонение → дашборд».
- **После первого показа:** доработка Plan/Fact по обратной связи и исходному ТЗ; полноценные импорты, мобильный ввод, офлайн, фото, приёмка, шахматка, экономика — в согласованной последовательности.
- **Перспектива:** Quality, Construction, ИД, Budget, Safety, Warranty, AI, тиражируемый on-prem, расширенные конструкторы, интеграции, лицензирование и единая аналитика — сохранены как видение, но **не обязательны для MVP**.

Решения сегодняшнего обсуждения выше по приоритету, чем прежние ТЗ, архитектурные гипотезы и дорожные карты. При этом **бизнес-требования исходного «ТЗ для программы» не отменены**: они распределяются по релизам. Подробный реестр прежних решений остаётся в `Platform_2_0_ARCHITECTURE_DECISIONS_v1_2.md` (архив / справочник, не список задач «сделать всё сейчас»).

## 2. Архитектурные ограничения, которые нельзя откладывать

1. **Не трогать production RBI Platform / Quality.** Новый проект создаётся из проверенного commit исходной платформы, в отдельном репозитории и отдельном окружении. Новая система не должна использовать производственные данные или секреты старой без отдельного решения.
2. **Не переписывать оболочку.** Максимально повторно использовать App Shell, навигацию, дизайн-систему, Module Loader, общие сервисы, IndexedDB, PWA и архитектурные наработки TS/Vite. React — технология нового модуля, не всей оболочки.
3. **Независимые репозитории.** `platform-2-core` — оболочка/сервисы; `planfact-smr` — бизнес-модуль и его миграции; существующий репозиторий RBI — отдельно. Имена условные.
4. **Независимый модульный контракт.** Plan/Fact не импортирует внутренний код Quality/Construction, не пишет в их частные таблицы и не требует изменения ядра при каждом собственном релизе.
5. **Компания — граница данных.** С первого дня нужны устойчивые `company_id`, `project_id`, серверные проверки членства и доступа, RLS/Storage, чтобы позднее не переносить всю БД на мультитенантную модель.
6. **Единые Master Data внутри компании.** Проекты, физические объекты, локации, контрагенты и виды работ имеют стабильные идентификаторы, используемые модулями по контракту. Не создавать для Plan/Fact независимое параллельное дерево помещений.
7. **Переносимость.** Архитектура должна запускаться на self-hosted Supabase; нельзя создавать обязательную зависимость on-prem продукта от собственных SaaS-серверов разработчика.
8. **Качество поставки.** Каждая миграция, изменение API и версия сопровождаются тестами, безопасностью и документацией. Не накапливать неучтённый технический долг.

Это не означает, что до MVP нужны все будущие интерфейсы управления пользователями, ролями и типами объектов. Требуется **корректная основа модели и безопасности**, а полноценные конструкторы можно разработать позже.

## 3. Модель подключения независимых приложений

### Обязательный минимальный контракт v1

Оболочка Platform 2.0 предоставляет документированный ограниченный `ctx`: текущие пользователь/компания/проект, разрешения, настройки локали и разрешённые платформенные сервисы. Приложение публикует манифест с `id`, версией, диапазоном совместимости Platform API, entry point и маршрутами, а также жизненным циклом `init / mount / unmount` (точную форму адаптировать к существующему загрузчику).

Plan/Fact разрабатывается на **React + TypeScript**, собирается отдельно и монтируется в контейнер существующей оболочки. Каждое новое приложение в перспективе использует такой же контракт.

**Критерий:** совместимую версию Plan/Fact можно заменить/откатить без изменения кода Quality. Первым делом это проверяется на малом тестовом React-модуле; полноценную систему plugin marketplace не делать.

Межмодульные связи будущей Construction OS обеспечиваются каноническими идентификаторами, публичными API и версиями событий. Сложную событийную шину/outbox не разрабатывать до реального потребителя.


## 4. Компании, пользователи, проекты и подрядчики

**Принято:** Platform 2.0 — мультитенантный B2B SaaS. Один Supabase-контур обслуживает разные независимые компании. У каждой компании — собственные объекты, сотрудники, ВОР, бригады, документы, мастер-данные, права и лицензии. **Один строительный проект принадлежит одной компании**, даже если подрядчики работают на нём по договору.

Один пользователь SaaS может состоять в нескольких компаниях и переключать рабочий контекст. При этом права и локальные данные не смешиваются.

**Гостевой доступ утверждён.** Заказчик вправе пригласить конкретных сотрудников подрядчика в свой проект с ограничением по объекту, договору, фронту работ, сроку и операциям. Заказчик может делегировать назначенному представителю подрядчика право приглашать его сотрудников **только в пределах уже выданных полномочий**. Гости работают с данными заказчика, не получают доступа к собственному tenant подрядчика из гостевого контекста и не объединяют базы компаний.

Второй механизм взаимодействия независимых компаний — **явный обмен структурированными пакетами** (ZIP с манифестом, версиями, проверкой импорта); данные получателя остаются самостоятельной копией. Пакетный обмен сохраняется как направление, но не реализуется ради первого MVP.

**Подрядчик** в справочнике заказчика — контрагент, а не автоматически связанная компания SaaS. **Бригада** — производственный ресурс со своими назначениями и историей состава; каждому рабочему не требуется учётная запись.

### Роли и разрешения

Принята перспективная модель конструктора произвольных корпоративных ролей: администратор создаёт роли из каталога действий каждого модуля. Название должности не определяет возможности. Например, прораб может получить право загрузки PDF-плана, но не его утверждения. Роль имеет область действия (компания, проект, договор, локация, срок). Руководитель проекта назначает только разрешённые корпоративные роли в своих проектах; допускаются индивидуальные временные права. Изменения корпоративных ролей идут через **черновик → просмотр влияния → публикацию**. Саморасширение прав запрещено.

**Для первого MVP:** реализовать только нужные роли ПТО, прораба, руководителя и администратора, но хранить доступ и проверять действия на сервере так, чтобы затем добавить произвольные роли **без смены архитектуры**. Полный графический конструктор, управление подразделениями и все виды делегирования — следующие этапы.

## 5. Master Data и структура проекта

**Принято:** платформа даёт стандартные шаблоны, компания копирует их и формирует собственные справочники, проект содержит свои реальные объекты и производственные данные. Изменение общей версии шаблона не переписывает автоматически утверждённые корпоративные сведения.

**Проект — управленческий контейнер**, содержащий один или несколько физических объектов. Структура гибкая: жилой дом, корпуса, секции, этажи, квартиры; паркинг, уровни, зоны; сети, трассы и колодцы; фасады, захватки; благоустройство. Лишние уровни не навязываются.

Компания в будущем сможет создавать собственные типы локаций на основе технических категорий с атрибутами и правилами вложенности. **Вид работ — отдельный справочник, не узел дерева.** Позиция ВОР может относиться к нескольким локациям с распределением объёмов.

**Для MVP достаточно:**
- канонических `company_id`, `project_id`, `location_id`, `work_type_id`, `work_item_id` и будущей возможности связать позицию с несколькими локациями;
- минимального создания проекта и нескольких локаций (вручную или импортом);
- минимального справочника видов работ и единиц измерения;
- сохранения истории/идентичности при переименовании локации;
- адаптации существующих `LocationService` / `location_nodes` после сверки фактического кода и БД, без второго справочника.

**После MVP:** полноценный конструктор типов, правил вложенности и атрибутов; генерация этажей, шаблоны компании, массовый импорт/предпросмотр, версии структур, BIM/IFC, PDF-планы и сложные визуальные редакторы.

### Утверждённое правило онлайн/офлайн

**Изменения дерева проекта и корпоративных мастер-данных выполняются только онлайн.** Производственные действия модулей (ввод факта, проверки и др.) должны поддерживать офлайн, когда это предусмотрено соответствующим рабочим релизом.

Для **первого показа MVP** допускается online-only реализация реального сценария Plan/Fact. Это не отменяет офлайн-положения исходного ТЗ; **полевой пилот** не считаем полностью готовым, пока требуемая работа без сети не реализована и не протестирована. Многокомпанейский офлайн обязан изолировать локальные кэши/очереди и повторно проверять права на сервере при синхронизации.


## 6. Что именно показываем заказчику Plan/Fact

**Приоритет:** полноценная сквозная работа небольшого объёма данных, а не демонстрация всех кнопок из большого ТЗ.

### MVP — первый показ

1. Открыть Plan/Fact в новой оболочке и выбрать компанию/проект.
2. Создать минимальную структуру объекта/локаций.
3. Создать несколько позиций ВОР или **предпочтительно импортировать небольшой реальный/обезличенный Excel-файл** с проверкой данных.
4. Установить плановые объёмы и даты; сохранить исходный план.
5. Войти как прораб, внести фактически выполненные объёмы по дате и работе; сохранить изменения в БД с автором.
6. Получить расчёт «план — факт — остаток — % выполнения — отклонение по сроку».
7. Открыть управленческую сводку РП по проекту. По возможности — первый простой светофор; визуальную поэтажную шахматку развивать после проверки данных.
8. Проверить повторное открытие данных, корректировку факта, отсутствие скрытого пересчёта и ограничения доступа.

**Обязательный результат:** заказчик видит свои работы и реальные изменения показателей, а не мокап и не таблицу с заранее заданными числами.

### Минимальные модели с расчётом на будущее

Разделить сущности **позиция ВОР, распределение по локациям, плановые значения/версия, факт/операция, подтверждение**. В будущем отдельно учитывать сообщённый, подтверждённый, принятый, документально включённый и оплаченный объёмы — не смешивать все стадии одним статусом.

Утверждённые версии и значимые изменения не должны бесследно перезаписываться. Нужно иметь путь к исправлениям, истории и будущим документам приёмки без замены ключей в основной модели.

### После первого показа

Полноценные импорты ВОР/ГПР/ГДРС; мобильные сценарии и офлайн; фотографии; контроль превышений и подтверждение фактов; работа бригад и трудозатраты; шахматка; чек-листы; реестры 10/25 и КС-2; финансовый блок; сложная аналитика, уведомления и интеграции — по очереди, согласованной с заказчиком и исходным ТЗ.

Исходное ТЗ «ТЗ для программы» остаётся функциональным источником с кодами `PTO-01…10`, `PR-01…11`, `LP-01…09`, `MN-01…08`, `NFR-01…10`. Не объявлять всё ТЗ выполненным по завершении MVP.

## 7. Долгосрочная Construction OS — сохраняем, но пока не разрабатываем

Если одна компания приобрела несколько модулей, они могут образовать **единый производственный контур** через общие корпоративные идентификаторы, API, события и права:

- **Construction → Warranty:** история дефектов, замечаний, приёмки, фото, подрядчиков и устранений;
- **Quality → Plan/Fact:** проблемы/переделки и их возможное влияние на сроки;
- **Plan/Fact → Construction:** готовность работ к предъявлению;
- **Plan/Fact → Budget:** разрешённые объёмы для финансовых показателей;
- **Quality + Construction + Plan/Fact → Contractors:** единая история результатов подрядчика внутри компании.

Не создавать общей базы двух независимых компаний и не давать прямого доступа к tenant подрядчика. Гостевое участие и обмен пакетами остаются разными разрешёнными каналами.

**Продуктовый резерв из Construction OS:** Quality, Construction, Knowledge, исполнительная документация (ИД) и согласования, Safety, Technical Decisions, Schedule (шире ГПР Plan/Fact), Budget (шире экономики Plan/Fact), Contractors, Tenders, Procurement, Contracts & Legal, Projects & Portfolio, HR/Competencies, Warranty, Operation, Client Service, Cross-module Analytics.

Каждый будущий продукт разрабатывается по новому спросу в собственном модуле; не создавать дублирующие Schedule/Budget/документные функции там, где они уже существуют в Plan/Fact. **Полная система будущих сервисов не является условием MVP.**

## 8. Два способа коммерческой поставки

**SaaS:** продукт и данные размещены на инфраструктуре владельца; заказчик оплачивает подписку на используемые приложения/подмодули, получает обслуживание и не получает исходный код.

**On-prem:** клиенту передаётся независимая приобретённая версия платформы и модулей, собственный self-hosted Supabase, исходный код разрешённой комплектации, техническая документация, право самостоятельно дорабатывать и эксплуатировать систему. Правообладатель сохраняет права на исходный продукт и возможность продавать его другим компаниям. Поддержка/новые версии — отдельные условия. Обязательной онлайн-активации через SaaS поставщика не требуется.

**Одна основная кодовая база**, разные конфигурации развёртывания. Клиентские изменения не попадают в основную разработку автоматически; расширения рекомендовано создавать через публичные API/дополнительные модули.

**Сейчас:** сохранять переносимость self-hosted Supabase, миграций и конфигурации. **Позже:** on-prem установщик, клиентские Git-поставки, экспорт данных компании, коммерческое лицензирование и биллинг. До продажи проверить юридические права на наследуемые исходники и сторонние библиотеки.

## 9. AI-помощники и внешние интеграции

В будущем — общий **AI Gateway**: каждый модуль может вызвать помощника с разрешённым контекстом, инструментами, аудитом и ограничениями доступа. Возможны облачные и локальные модели, в том числе для on-prem. AI не вправе обходить права или самостоятельно выполнять юридически значимые действия.

Интеграции с 1С, календарными системами, Excel, ЭДО, ИД и внешними API предусматриваются через публичные контракты, без прямого редактирования приватных таблиц других модулей.

**В MVP не разрабатывать AI Gateway, агентов, общий WorkflowService и интеграционную платформу.** Не закладывать в базовую работу Plan/Fact обязательную зависимость от AI или внешнего SaaS.


## 10. Безопасность, документация, релизы и технический долг

**Обязательно для каждого нового релиза:**

1. Проверять tenant-изоляцию, права на проект/действие, отсутствие доступа к приватным Storage-файлам другой компании, отсутствие привилегированных ключей в браузере.
2. Держать SQL-миграции, версии API и инструкции установки **в Git**. Проверять создание чистой БД, обновление существующей и процедуру восстановления при ошибке.
3. Выполнять сборку, TypeScript-проверку, модульные тесты расчётов и негативные тесты прав; перед коммерческим SaaS/on-prem запуском — отдельную проверку ИБ и зависимостей.
4. Вести **docs-as-code**: `README.md` (запуск), `docs/ARCHITECTURE.md` (фактическая модель), `docs/MODULE_CONTRACT.md`, `docs/DATABASE_MIGRATIONS.md`, `docs/SECURITY.md`, `CHANGELOG.md`, `docs/TECH_DEBT.md` (краткий реестр компромиссов). Обновлять вместе с изменением кода.
5. Любой обход архитектурных правил оформлять как документированный временный компромисс с причиной, владельцем и условием устранения. Не требовать устранить весь унаследованный технический долг старого RBI до показа MVP, но не создавать новый бесконтрольный.

**Важная исходная особенность:** в августовской технической инвентаризации RBI Platform зафиксированы permissive RLS и публичные Storage buckets. Это исторический снимок, **не доказательство состояния сегодняшнего сервера**. Не копировать эти настройки в коммерческий мультитенантный SaaS без аудита и исправлений.

**Отдельное правило выпуска:** демонстрацию на вымышленных данных можно показать до полной production-подготовки, но она должна быть явно обозначена как demo. Использовать реальные корпоративные данные и допускать внешних пользователей — только после необходимых серверных проверок и защиты файлов.

## 11. Этапы работы в Cursor — не раздувать первый релиз

### Шаг 0. Сверка кода и независимая копия

- Сверить переданный архив с актуальным Git действующей RBI Platform.
- Зафиксировать версию источника, проверить сборку, загрузчик, сервисы, карту зависимостей и фактический Supabase.
- Создать `platform-2-core` и самостоятельное окружение без влияния на production Quality.
- Определить **минимальные** точки интеграции React/TS и изменения серверной модели.

**Приёмка:** воспроизводимый запуск копии оболочки без изменений действующего продукта.

### Шаг 1. Доказать модульную архитектуру

- Создать репозиторий `planfact-smr`.
- Подключить небольшой React/TypeScript-модуль к существующей оболочке.
- Показать правильный контекст пользователя/компании/проекта, маршруты, монтирование и отключение.
- Проверить независимую сборку/замену версии без правок Quality.
- Проверить минимальные серверные company/project permissions.

**Приёмка:** работает реальный, отдельно собираемый модуль. Не строить всю платформу плагинов.

### Шаг 2. Первый работающий MVP Plan/Fact

- Проект и минимальные локации.
- Позиции ВОР и плановые объёмы/даты, предпочтительно импорт небольшого реального Excel.
- Ввод факта, сохранение, расчёты и права ролей.
- Дашборд «план/факт/остаток/отставание».
- Проверка корректности итогов, перезагрузки, отсутствия доступа чужого tenant.

**Приёмка:** последовательность можно показать реальному заказчику и получить содержательную обратную связь.

### Шаг 3. Полевой пилот и итеративное расширение

По согласованию с заказчиком: полноценная обработка его ВОР, мобильный ввод, офлайн, фото, массовые операции, шахматка, согласование результатов и остальные требования исходного ТЗ. Финансы и реестры — отдельными защищёнными циклами.

**В каждом шаге:** минимальный diff, воспроизводимый запуск, тесты, миграция при изменении БД, документация и список оставшихся ограничений.

## 12. Критерии готовности к первому показу

MVP можно показывать, если:

- [ ] существующий рабочий RBI Platform/Quality не менялся;
- [ ] новая оболочка запускается независимо;
- [ ] React/TypeScript Plan/Fact работает из своего репозитория и сборки;
- [ ] реальная ВОР/работы, плановые значения и факты сохраняются;
- [ ] управленческая сводка пересчитывается после ввода факта;
- [ ] есть базовая проверка роли, компании и проекта на сервере;
- [ ] изменение модуля не требует переписывания Quality;
- [ ] БД воспроизводится миграциями, проект запускается по README;
- [ ] зафиксированы ограничения первого показа, проведены применимые тесты;
- [ ] несуществующие функции (офлайн, ЭП, финансы и т. п.) не представлены как готовые.

## 13. Единственные ближайшие открытые вопросы

1. **Supabase нового контура.** Согласовано: один Supabase для множества компаний Platform 2.0, не отдельный проект на каждого клиента. Пока **не утверждено**, делить ли его с действующим production RBI или поднять отдельный экземпляр на том же сервере. **Рекомендация: отдельный экземпляр** для новой Platform 2.0, чтобы не рисковать работающим Quality. Решение принять при первом инфраструктурном аудите; можно сразу работать в независимой тестовой среде.
2. **Образец для показа.** Небольшая настоящая или обезличенная ВОР и понятный целевой сценарий заказчика.
3. **Очередность после показа.** Выбрать по обратной связи, что нужнее: импорт ГПР, шахматка, мобильный факт, офлайн, подтверждения или расчёты.

Все остальные вопросы прежних спецификаций **не блокируют разработку MVP** и решаются при появлении реальной задачи.

## 14. Правила на следующий цикл обсуждений

**Финализируем этап архитектурного проектирования.** Не возвращаться к подробной проработке будущих модулей, конструктора мастер-данных, полного лицензирования, AI Gateway или on-prem дистрибутива до появления реального блокера первого Plan/Fact.

Изменять этот документ только:
- при новом утверждённом бизнес-требовании от заказчика;
- при выявленном техническом препятствии, подтверждённом кодом/тестом;
- для фиксации реально реализованного интерфейса, версии или ограничения.

### Первая задача для Cursor

**Подготовить аудит и минимальный технический эксперимент, не всю реализацию Plan/Fact:** выявить фактические точки подключения к App Shell, Module Loader, `ctx`, текущие команды сборки, границы серверных сервисов; затем запустить в отдельном контуре самый маленький React-модуль из отдельного репозитория. Представить работающий результат, список изменённых файлов, команды проверки, обнаруженные блокеры, обновлённую документацию. Production RBI/Quality не изменять.
