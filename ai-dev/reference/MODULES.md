# Platform 2.0 — каталог модулей

**Версия:** 1.0 · 26.10.2026 · решения раздела 7 утверждены владельцем 26.10.2026
**Что это:** один список всех модулей платформы на весь срок жизни проекта, от проектирования до эксплуатации. По каждому модулю указано: зачем он нужен, кто в нём работает, какие данные он хранит сам, что берёт из ядра, что отдаёт другим модулям и на каком он этапе.
**Чем не является:** это не план задач. Порядок работ задаёт `ROADMAP.md`, объём MVP — `ARCHITECTURE_v1_3_MVP_FINAL.md`.

**Источники:** `ROADMAP.md` (20.10), старая карта RBI Platform (13.08, разделы 3–9), `ARCHITECTURE_v1_3_MVP_FINAL.md` §4–7, `TZ_PLAN_FACT.md` v1.1, `SPEC_2026-10-20_ВОР…`, `research/2026-10-23-konkurenty/ОТЧЁТ.md`, `ПЛАН_ДОРАБОТОК_QUALITY.md` (24.10), решения владельца в Cowork (ADR-066, черновик).
**Статусы** взяты из отчёта о конкурентах (23.10) и обсуждения 26.10. Их нужно сверить с репозиторием `rbi-q`: в этом сеансе он не был подключён.

## Коротко

- **Устройство:** одно ядро плюс модули. В ядре хранятся общие записи: компания, проект, места, люди, подрядчики, договоры, виды работ. Модуль хранит только свои рабочие данные (проверки, факт, замечания) и **ссылается** на записи ядра.
- **Модулей 20.** Три уже работают (План/Факт, Качество, Стройконтроль). База знаний и Аналитика СК тоже работают, но только как старые модули Quality и в Platform 2.0 ещё не перенесены. Остальные 15 подключаются по спросу, каждый к тем же записям ядра.
- **Предложение:** добавить в карту один модуль, которого в ней не было, — «Проектирование». Его требует ваша формулировка «на всём жизненном цикле».
- **Решения по границам приняты** (раздел 7, 26.10.2026). Следующий шаг — архитектура данных ядра в репозитории по этим решениям.

## 1. Как устроено

```
Компания (границы данных, лицензии модулей)
 └─ ЯДРО: общие справочники + платформенные сервисы
     ├─ План/Факт   ├─ Качество   ├─ Стройконтроль   ├─ Сроки   ├─ Бюджет   …
     └─ каждый модуль = лицензия компании + права по роли
```

**Пять правил** (старая карта §3.2, ADR-066):

1. **Одна запись на всё.** Корпус, подрядчик или человек заводится один раз на компанию. Новый модуль не создаёт свой справочник.
2. **Модули не лезут друг в друга.** Они обмениваются данными через ядро: общие ссылки, публичные функции и события.
3. **Модуль — это лицензия.** Компания видит только то, что купила. Сотрудник видит только то, что разрешает его роль на этом проекте.
4. **Компании полностью разделены.** Подрядчик заходит в проект заказчика только гостем и только в пределах выданных прав.
5. **Ядро растёт по нужде.** Новая общая сущность появляется вместе с первым модулем, который её использует, а не «на будущее».

## 2. Ядро: общие данные

Все модули ссылаются на эти записи. Если запись не общая, сквозной аналитики «качество + срок + деньги» не будет.

| Сущность | Что это простыми словами | Кто ведёт | Кто использует | Статус |
|---|---|---|---|---|
| **Компания** | арендатор платформы, граница данных | админ платформы | все | ✅ |
| **Проект** | управленческий контейнер, например ЖК или очередь. Владелец, заказчик, сроки, бюджет | РП / админ компании | все | ✅ (в интерфейсе пока называется «Объект») |
| **Объект (здание)** | физический объект внутри проекта: корпус, паркинг, сети, благоустройство | ПТО | все | ⚠️ отдельного уровня нет |
| **Место** | дерево любой глубины: секция → этаж → квартира/помещение, а также МОП, кровля, захватка, трасса | ПТО | все | ⚠️ сводится в одно дерево (P2-0045) |
| **Сотрудник** | человек в компании, вход один на все компании | админ компании | все | ✅ |
| **Участие в проекте** | кто работает на проекте, в какой роли и с какой областью (проект, объект, договор, срок) | РП | права, все модули | ❌ права пока на всю компанию |
| **Роль** | набор разрешённых действий. Название должности на права не влияет | админ компании | права | 🟡 стартовые роли |
| **Контрагент** | подрядчик, поставщик или заказчик, по ИНН | ПТО / договорной отдел | все | ✅ |
| **Договор** | проект × контрагент: предмет, виды работ, фронт (места), цены, сроки | ПТО / договорной | План/Факт, Качество, СК, Бюджет, Тендеры | ❌ |
| **Бригада** | производственный ресурс подрядчика или «свои силы». Состав хранится с историей | прораб / подрядчик | План/Факт, Качество, ФОТ | ⚠️ только в План/Факте, не связана с подрядчиком |
| **Вид работ** | один справочник компании: код, название, ЕИ, нормы | ПТО | ВОР, ГПР, смета, чек-листы, замечания | 🟡 есть в ВОР, с Качеством не связан |
| **Единица измерения** | м², м.п., шт. | платформа | все | ✅ |
| **Позиция работ** | ячейка учёта: место × вид работ × объём. К ней цепляются срок, деньги, факт и качество | ПТО | План/Факт, Сроки, Бюджет, Качество, СК | ✅ в План/Факте |
| **Документ / фото** | файл с версией и привязкой к записи | все | все | 🟡 по модулям |
| **Задача** | поручение с ответственным и сроком; может пройти через несколько модулей | все | все | 🟡 только в Качестве |
| **Журнал изменений** | кто, что и когда изменил, значения до и после | система | все | 🟡 |

**Чего в ядре нет и не будет:** чек-листы, замечания, факт, сметы. Это рабочие данные модулей, и они **ссылаются** на записи ядра.

## 3. Платформенные сервисы

Это не модули для продажи, а общие механизмы, которыми пользуются все модули.

| Сервис | Что делает | Статус |
|---|---|---|
| Вход и контекст | один вход, выбор компании и проекта | ✅ |
| Права | проверка «роль + проект + действие» на сервере | 🟡 |
| Лицензии модулей | включение модуля для компании («Админ платформы») | ✅ |
| Администрирование | справочники, пользователи, роли, настройки компании | ✅ |
| Файлы и фото | хранение, сжатие, отметка даты и места, доступ только своей компании | 🟡 |
| Офлайн и синхронизация | работа на площадке без связи | 🟡 есть в Качестве, для остальных этап В |
| Импорт Excel | разбор файлов заказчика (ВОР, ГПР) | ✅ ВОР |
| Печать и экспорт | PDF, Word, Excel, единые шаблоны компании | 🟡 по модулям |
| Уведомления | в приложении, push, почта, Telegram | ❌ |
| Согласования (маршруты) | документ или решение по цепочке людей | ❌, делать только с первым реальным процессом |
| ИИ-шлюз | один вход к ИИ для всех модулей, с учётом прав | ❌ |
| Поиск | поиск по знаниям, документам и реестрам | ❌ |

## 5. Карточки модулей

Обозначения: ✅ работает · 🟡 частично · ❌ нет · ▶ в работе.

### 5.1. План/Факт СМР (`planfact`) — ✅ первый модуль Platform 2.0

- **Зачем:** провести работу от ВОР заказчика до денег: ВОР любой формы → наш единый вид → смета и КП → факт прораба → КС-2 в форме заказчика → сводка РП.
- **Кто:** ПТО, прораб и мастер, РП, экономист, руководство.
- **Сценарии:** загрузка ВОР любой формы со «светофором» сопоставления; редакции ВОР; справочник цен; тендерная смета и КП; ввод факта по месту и виду работ; КС-2 в Excel; сводка «план — факт — остаток — отставание».
- **Хранит сам:** исходник ВОР и его строки, связку «строка заказчика ↔ наша позиция», профиль формы девелопера, словарь сопоставлений, цены и накладные, смету и КП, вводы факта, редакции КС-2.
- **Берёт из ядра:** проект, места, виды работ и ЕИ, позиции работ, контрагента-заказчика, договор, бригады, людей.
- **Отдаёт:** факт и готовность → Сроки, Стройконтроль (готово к приёмке), Бюджет; объёмы КС-2 → Бюджет; выработку бригад → Подрядчики.
- **Этап В (по ТЗ):** ГПР и ГДРС, мобильный факт с фото, офлайн, чек-лист заказчика, бригады и ФОТ, реестры выплат на 10 и 25 число, 1С, ИИ-подсказки по ВОР. Из анализа конкурентов: три факта (прораб / принято / КС-2), правка факта 24 часа, прогноз по темпу, КС-3 и КС-6а.
- **Источник:** ТЗ v1.1, SPEC ВОР, ROADMAP этапы Б и В.

### 5.2. Качество (`quality`) — ✅ работает, ▶ переносится в Platform 2.0

- **Зачем:** риск-ориентированный контроль качества: проверка по чек-листу → дефекты B1/B2/B3 → аналитика → профилактика (PDCA).
- **Кто:** инженеры качества, РП, руководители, методологи.
- **Сценарии:** проверки по чек-листам, дефекты с фото, история, аналитика объектов и подрядчиков (УрК, ИКО), задачи и недельный план, совещания и протоколы с ИИ, мероприятия воздействия, эталоны, FMEA, ТИВИ, отчёты, геймификация.
- **Хранит сам:** шаблоны чек-листов и их версии, проверки, дефекты, эталоны, FMEA, совещания, мероприятия, оценки.
- **Берёт из ядра:** проект, места, подрядчиков, договоры, **виды работ** (чек-лист привязан к виду работ), людей, задачи.
- **Отдаёт:** оценку качества → Подрядчики и Тендеры; дефекты и переделки → Сроки и Бюджет; повторы → Технические решения.
- **Сейчас:** доработки по отзывам пользователей (`ПЛАН_ДОРАБОТОК_QUALITY.md`: фото, синхронизация, совещания); старое Качество потом заменяется новым. Для РБИ работает без потери данных.
- **Долг перед ядром:** связать чек-листы с видами работ и убрать старые «мосты» между справочниками.

### 5.3. Стройконтроль (`construction`) — ✅ ядро есть (construction-v2)

- **Зачем:** замечания на планах этажей, устранение, приёмка работ, готовность и передача помещений. Цель — заменить МРС / «Стройконтроль».
- **Кто:** инженеры СК, РП, подрядчики (в кабинете), участники приёмки.
- **Сценарии:** пин на PDF-плане; замечание → назначение подрядчика и срока → фото устранения → проверка → закрытие или возврат; заявки на приёмку и бронирование окна инженера; шахматка; передача помещений. Кабинет подрядчика готов (P2-0044).
- **Хранит сам:** PDF-планы и их привязку к местам, замечания и их историю, заявки на приёмку, акты, состояние передачи.
- **Берёт из ядра:** места, подрядчиков, договоры, виды работ, людей, задачи.
- **Отдаёт:** замечания → Сроки («задача заблокирована N дефектами»), Подрядчики, Гарантия (история квартиры); принятые объёмы → План/Факт (факт «принято»).
- **Развитие (из анализа конкурентов):** справочник дефектов с нормативом, предписание одной кнопкой, рецидивы, типы замечаний по отделам (СК, ОТ, авторский надзор), шахматка «выполнено / принято».

### 5.4. База знаний (`knowledge`) — ✅ работает в старом приложении

- **Зачем:** один актуальный стандарт для всех модулей: ТИВИ, нормативы (ГОСТ, СП), практики, эталоны, FAQ.
- **Кто:** все сотрудники; подрядчики — в пределах выданного доступа.
- **Хранит сам:** материалы и их версии.
- **Берёт из ядра:** виды работ (материал привязан к виду работ), компанию.
- **Отдаёт:** ссылки на норму в чек-листы Качества, справочник дефектов СК и Технические решения.
- **Этап:** переиспользовать, вести отдельно по каждой компании.

### 5.5. Аналитика внешнего СК (`sk`) — ✅ переходный, внутри Качества

- **Зачем:** загружать выгрузки чужой системы стройконтроля (Excel) и анализировать просрочки.
- **Судьба:** отомрёт, когда Стройконтроль заменит внешнюю систему. Отдельным модулем для продажи не становится.

### 5.6. Проектирование (`design`) — ❌ новое предложение, в картах не было

- **Зачем:** вести проектирование как стадию проекта: график выпуска РД, замечания к проекту, связь задержки документации со стройкой.
- **Кто:** ГИП, проектный офис заказчика, ПТО, проектировщик (гостем).
- **Сценарии:** график выпуска разделов, получение и проверка комплектов, замечания к листам, ИЗМы, запросы (RFI) «стройка ↔ проектировщик», статус «в производство работ».
- **Хранит сам:** разделы проекта, комплекты и их версии, замечания к ним, RFI.
- **Берёт из ядра:** проект, объекты, контрагента-проектировщика, договор, документы, виды работ.
- **Отдаёт:** даты выдачи РД → Сроки; узлы и решения → Технические решения; листы → планы для Стройконтроля.
- **Граница:** можно сделать частью «ПТО и документы» (см. вопрос 7.5).

### 5.7. ПТО и документы / СОД (`documents`) — ❌ граница не утверждена

- **Зачем:** общая среда документов: РД, ППР, исполнительная документация (АОСР и др.), версии, согласования, передача подрядчику.
- **Кто:** ПТО, проектировщики, СК, подрядчики.
- **Сценарии:** папки с правами, версии и сравнение, согласование по маршруту с чек-листом, штамп и QR «в производство работ», акт передачи документации, реестр ИД, комплектность по объекту и виду работ.
- **Хранит сам:** документы, версии, маршруты, реестры.
- **Берёт из ядра:** проект, места, виды работ, договоры, людей; сервисы файлов, согласований и печати.
- **Отдаёт:** комплектность ИД → приёмка в Стройконтроле; документ-основание → Сроки и Технические решения.
- **Правило старой карты:** не делать отдельный модуль на каждый вид документа.

### 5.8. Сроки и график (`schedule`) — ❌ этап 3

- **Зачем:** график всего проекта: ГПР, базовый план, зависимости, критический путь, прогноз окончания, ГДРС.
- **Кто:** ПТО, РП, планировщик, прорабы (только свои задачи).
- **Сценарии:** импорт графика (Excel, MS Project), базовые планы и отклонения, прогноз по темпу, готовность мест, окна приёмки, влияние дефектов на срок, сводная программа по проектам.
- **Хранит сам:** элементы графика, связи, базовые планы, календари.
- **Берёт из ядра:** позиции работ, места, виды работ, договоры, бригады.
- **Отдаёт:** даты → План/Факт, Закупки, Бюджет; риск срока → Аналитика.
- **Граница:** ГПР и ГДРС есть и в ТЗ План/Факта (этап В). Графиков не должно быть два (см. вопрос 7.2).

### 5.9. Безопасность (`safety`) — ❌ этап 3

- **Зачем:** охрана труда: проверки, нарушения, предписания, риски.
- **Кто:** специалисты ОТ, РП, прорабы, подрядчики.
- **Хранит сам:** чек-листы ОТ, нарушения, предписания, допуски к работам.
- **Берёт из ядра:** места, подрядчиков, бригады, людей, задачи.
- **Отдаёт:** рейтинг ОТ → Подрядчики и Тендеры; риски → Аналитика.
- **Подсказка:** по устройству это близнец Качества и СК (чек-лист → нарушение → устранение). Переиспользовать механику, а не писать заново.

### 5.10. Технические решения (`technical-decisions`) — ❌ этап 3

- **Зачем:** версии узлов и решений; отличать ошибку решения от ошибки исполнения.
- **Кто:** главный инженер, методологи, проектировщики.
- **Хранит сам:** узлы, версии, область применения.
- **Берёт из ядра:** виды работ, проекты, места.
- **Отдаёт:** версию узла → проверки Качества, замечания СК, обращения Гарантии.

### 5.11. Бюджет (`budget`) — ❌ этап 4, частично закрыт План/Фактом

- **Зачем:** бюджет проекта: план, факт, прогноз, стоимость отклонений и переделок.
- **Кто:** экономист, финансовый директор, РП, руководство.
- **Хранит сам:** статьи бюджета, лимиты, прогнозы, корректировки.
- **Берёт из ядра:** проект, договоры, позиции работ, виды работ.
- **Получает от модулей:** сметы и КС-2 (План/Факт), даты (Сроки), переделки (Качество, СК), закупки.
- **Обязательное условие:** строгие права на суммы (ТЗ: прораб по умолчанию сумм не видит).

### 5.12. Подрядчики (`contractors`) — 🟡 справочник есть, карточки нет

- **Зачем:** сквозная карточка подрядчика за весь жизненный цикл: качество, замечания, сроки, деньги, ОТ, гарантия, рейтинг, история воздействий.
- **Кто:** руководство, тендерный отдел, РП.
- **Хранит сам:** рейтинги, оценки, историю воздействий. Сам подрядчик — запись ядра.
- **Получает:** показатели от Качества, СК, Безопасности, Сроков, План/Факта (выработка бригад), Гарантии.
- **Отдаёт:** рейтинг → Тендеры.

### 5.13. Тендеры (`tenders`) — 🟡 тендерная смета и КП уже в План/Факте

- **Зачем:** выбрать подрядчика по цене **и** по его истории.
- **Сценарии:** лот, требования и виды работ, участники, предложения, сравнение, учёт рейтинга, решение.
- **Хранит сам:** лоты, предложения, протоколы.
- **Берёт из ядра:** виды работ, контрагентов, проект; рейтинг из Подрядчиков.
- **Отдаёт:** победителя → Договор (ядро).
- **Граница:** у нас две стороны тендера. Мы как подрядчик считаем смету и КП (План/Факт). Мы как заказчик выбираем подрядчика (этот модуль).

### 5.14. Закупки и МТО (`procurement`) — ❌ этап 4, по спросу

- **Зачем:** потребность в материалах, заявки, поставщики, поставки, склад.
- **Берёт из ядра:** позиции работ (материалы × норма), контрагентов, договоры.
- **Отдаёт:** риск поставки → Сроки; затраты → Бюджет.

### 5.15. Договоры (`contracts`) — ❌ граница не утверждена

- **Зачем:** жизнь договора: дополнительные соглашения, обязательства, гарантийные удержания, сроки, юридическая история.
- **Кто:** договорной и юридический отдел, ПТО, РП.
- **Важно:** сам **договор как запись** нужен уже сейчас: к нему привязаны бригады, права гостей подрядчика и КС-2. Поэтому запись живёт в ядре, а этот модуль добавляет работу с ней (см. вопрос 7.3).

### 5.16. Гарантия (`warranty`) — ❌ этап 5

- **Зачем:** гарантийные обращения и связь с историей строительства.
- **Сценарии:** обращение по квартире или элементу, причина, ответственный подрядчик (из истории места), срок, устранение, повторяемость.
- **Берёт:** места, подрядчиков, договоры (удержания), историю замечаний СК и проверок Качества, узлы.
- **Отдаёт:** повторяющиеся дефекты → Технические решения, Подрядчики, База знаний.

### 5.17. Эксплуатация и клиентский сервис (`operation`) — ❌ этап 5

- **Зачем:** передача помещений в эксплуатацию, состояние помещений, обращения жильцов.
- **Граница:** обращения клиентов, Гарантию и Эксплуатацию не делить на три отдельных потока обращений (старая карта §6.11).

### 5.18. Портфель проектов (`portfolio`) — ❌ по спросу

- **Зачем:** вехи и состояние проектов, сводная производственная программа, риски по портфелю.
- **Пока:** покрывается выбором проекта в оболочке и Аналитикой. Отдельный модуль заранее не делать.

### 5.19. Персонал и компетенции (`hr`) — ❌ по спросу

- **Зачем:** допуски, удостоверения, обучение, участие людей и рабочих бригад в проектах.
- **Пока:** закрывается «Участием в проекте» и составом бригад в ядре. Отдельный модуль — только если не подойдёт интеграция с HR-системой клиента.

### 5.20. Управленческая аналитика (`analytics`) — ❌ этап 5

- **Зачем:** один сигнал для руководства: качество, срок, бюджет, подрядчики и риски по всем проектам. Любую цифру можно раскрыть до исходной записи.
- **Условие:** не раньше, чем будут 2–3 модуля с реальными данными на общих записях ядра.
- **ИИ:** выводы ИИ только через ИИ-шлюз и только по данным, которые разрешено видеть пользователю.

### Не делаем (зафиксировано)

- **Цифровой мониторинг** (дроны, сканы, 360°) — только интеграция по спросу.
- **КЭП, ЭДО, ИСУП** — только если пойдём в госзаказ.
- **Своя ИИ-платформа** — нет, только шлюз к внешним моделям.

## 6. Сквозные цепочки (проверка правильности ядра)

Если цепочка не проходит по общим записям, значит, ядро сделано неправильно.

1. **Тендер → деньги:** ВОР заказчика → смета и КП → договор → позиции работ → факт прораба → принято (СК) → КС-2 → оплата бригадам (ФОТ) → бюджет.
2. **Качество → срок → деньги:** дефект → задача на переделку → сдвиг графика → дополнительные трудозатраты → бюджет.
3. **Подрядчик → тендер:** качество + замечания + сроки + ОТ + гарантия → рейтинг → выбор на следующем тендере.
4. **Решение → гарантия:** версия узла → проверки и замечания по узлу → гарантийное обращение → исправленный стандарт.
5. **Проект → стройка:** выдача РД → график → готовность фронта → приёмка → ИД → передача → гарантия.

Общие «оси», по которым всё связывается: **проект · место · вид работ · договор / подрядчик / бригада · человек · дата**.
