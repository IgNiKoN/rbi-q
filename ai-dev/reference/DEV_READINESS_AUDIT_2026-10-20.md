# Platform 2.0 — аудит готовности к AI-разработке

Дата: 20.10.2026. Материалы: Platform_2_0_ARCHITECTURE_DECISIONS_v1_3_MVP_FINAL, Platform_2_0_ARCHITECTURE_DECISIONS_v1_2, rbi-q-main (14) (архив). Исходный Git и рабочий Supabase не были предоставлены для сверки.

## Решение

Начинать разработку можно с небольшого архитектурного эксперимента и отдельной копии оболочки. Не начинать полную реализацию Construction OS. Документ v1.3 — управляющий приоритет; v1.2 — справочник ADR и отложенных возможностей. Работающий старый RBI Platform/Quality не изменять.

## Подтверждено чтением архива

- Архив: 405 элементов. Файлов `.git` нет, поэтому commit, история и соответствие production по архиву не устанавливаются.
- `js/core/module-loader.js`: фиксированный `MODULE_BASE_URLS`, импорт по локальному manifest, вызов `init` и кэш по id; независимый `mount/unmount`, runtime-версии и hot-replacement не доказаны.
- `js/core/app.entry.js`: фиксированные `MODULE_KEYS`, `BUNDLES`, `ALWAYS_INIT`; добавление нового business-id требует согласованной правки. `js/modules/modules.manifest.js` агрегирует статические манифесты.
- `js/services/company.service.js`: `COMPANY_ID = 'rbi'`, фиксированный каталог quality/construction/knowledge; `js/services/user-context.service.js` возвращает имя сотрудника как id и `projectCode`, а не доказанный Supabase user_id/project_id.
- `src/services/locations/types.ts`: строгое дерево object/building/section/floor/apartment; `src/services/locations/locations.service.ts` записывает `companyId: 'rbi'`; отсутствует обязательное сопоставление с новым project_id.
- `js/services/config.service.js` и отдельно `report.html`: содержат адрес действующего Supabase. Публичный anon-key не является серверным секретом, но использование действующего API из тестовой копии недопустимо. Нужен безопасный config для отдельного окружения.
- `sql/002_create_platform_v2_tables.sql`: разрешает anon SELECT и authenticated ALL с `USING (true)`; `sql/007_storage_construction_defects_policies.sql`: делает bucket публичным и разрешает операции anon. `sql/014_privilege_rls_hardening.sql` сужает политику одной таблицы, не исправляет всю архитектуру. Это исторический код; текущий production по нему не доказан.
- `js/services/sync/sync-auth.js`: авторизация на базе projectCode, имени и PIN (включая автоматическую регистрацию), не целевая персональная Auth-модель нового мультитенантного SaaS.
- `js/services/storage/storage-db.core.js`: локальная IndexedDB имеет общее имя `RBI_QUALITY_DB`. Для MVP Plan/Fact источником истины должен быть отдельный сервер; многокомпанейские офлайн-кэши — отдельный этап.
- `sw.js`: устаревшие имена и жестко зафиксированные пути модулей; в `activate` удаляются все caches текущего origin, кроме собственного. Новый продукт должен работать на другом origin, а версии bundle/SW — согласовываться.
- `.gitignore`: игнорирует `docs/`, `README.md`, `.cursor/`, `_ai/`; одновременно package.json ссылается на `_ai/scripts`. Без исправления будут теряться документы и проверки.
- В корне архива нет `.env.example`, CI workflow, `AGENTS.md` и `CLAUDE.md`; в текущем package.json нет React. Последнее нормально: React должен появиться в отдельном репозитории Plan/Fact, а не переписывать оболочку.

## Проведенные проверки

- `npm run test:unit` — 34/34 tests passed.
- `tsc -p tsconfig.json --noEmit` — 6 ошибок: `src/modules/construction-v2/plan-viewer.ts` (4), `src/services/locations/object-bridge.ts` (2; в том числе обращение к необъявленной `locs`). Не считать этот baseline зеленым.
- `npm run check:boundaries` — не проходит: отсутствует `_ai/scripts/check-module-boundaries.sh`.
- `npm ci --offline --ignore-scripts` — невозможен в среде аудита: пакет Vite отсутствует в локальном npm-кэше. Сборка не проверена, это не свидетельствует о ее неработоспособности.
- Полная браузерная smoke-проверка и live-проверка RLS/Storage не выполнялись. Нельзя заявлять готовность коммерческого SaaS по архиву.

## Необходимое для безопасного старта (P0)

**Исходник и право использования.** Подтвердить точный Git commit/ветку, цепочку прав на повторное использование кода и допустимость передачи исходников в выбранный облачный AI-сервис. Создать отдельные репозитории `platform-2-core` и `planfact-smr` (имена условные). Сохранить рабочий RBI как read-only источник; никаких merge/deploy/migration в действующий контур.

**Окружение.** Новый origin/домен, отдельный Supabase development/test, собственные Auth/Storage/БД, тестовые пользователи и данные. В dev/test запрещать любые сетевые соединения с production RBI endpoint; исправить и проверить конфиг также в report.html и других обращениях. Существующий `sw.js` не запускать в том же origin, что production.

**Воспроизводимый baseline.** README с запуском, Node/npm, `npm ci`, сборкой, TypeScript, юнит-тестами. Исправить 6 TS-ошибок ограниченным diff, восстановить или заменить проверку границ. Ввести минимальный CI: build, typecheck, unit, dependency/secret scan, позднее RLS.

**Контракт модуля.** В отдельной копии платформы определить компактный версионированный типизированный Module API: manifest + compatibility + разрешенный ctx, `init/mount/unmount` и уборка обработчиков. Проверить отдельно собранный React screen из planfact-smr, смену версии/rollback bundle без правок Quality и без обязательной пересборки ядра. Сбои или отключение модуля не должны ломать оболочку.

**Серверные данные и доступ.** Канонические `company_id`, `project_id`, `location_id`, stable `work_item_id`; аутентифицированная личность и членство, 2 компании/2 проекта для негативных тестов. Политики deny-by-default (включая Storage). Никогда не переносить широкие политики исторического SQL в новую базу. Для первого показа не требуется полный конструктор ролей и гостевой доступ, но серверные права должны позволять их добавить впоследствии.

**Минимальный производственный сценарий.** Реальная обезличенная ВОР в Excel на небольшой объем, один проект/локации, план по объему и датам, зафиксированный baseline, операции факта (дата/количество/автор), корректировки с историей, API и сводка. Без моков на финальном показе. Решить, какой временной профиль плана используется для расчета отклонения на дату; не суммировать напрямую разноразмерные позиции (шт., м², м³). Предусмотреть тест превышения, повторного ввода, исправления, реоткрытия и запрещенного доступа.

## Не включать в предпосылки MVP

Полный MasterData/role builder, приглашения делегированных гостей, универсальные интеграции, AI Gateway, полную событийную шину, on-prem установщик, мобильный офлайн, шахматку, КС-2, финансовый модуль, полный механизм пакетного межкомпанейского обмена. Сохранить в v1.2/roadmap, не реализовывать без новой задачи. Полевой пилот с offline является отдельным этапом.

## Контрольные точки

**0 — baseline и стенд:** исходный Git совпадает с выбранным snapshot, стенд запускается без production RBI, smoke shell пройден, проверки фиксируют существующий долг.

**1 — независимый модуль:** отдельный репозиторий React, типизированный manifest/ctx, реальный mount/unmount, изолированный release bundle, отключение/откат, нет зависимости от Quality.

**2 — заказчик:** реальный Excel/ВОР, план, введенный факт, корректный пересчет, серверная фиксация автора и история, API/RLS тест двух компаний, повторное открытие.

Каждый change — небольшой PR с перечнем файлов, командами/результатами тестов, миграциями, документацией и известными ограничениями. Запрещено считать тест непройденным только потому, что среда не содержит зависимостей: фиксировать точную причину.

## Что требуется дополнительно для предметной сверки

Актуальный Git URL и commit (или независимый экспорт репозитория с метаданными), фактическая SQL schema/RLS/Storage отдельного Supabase, безопасный доступ к тестовому контуру; исходное «ТЗ для программы», обезличенная ВОР/график и согласованный сценарий заказчика — для фазы Plan/Fact. Отсутствие этих входных данных не препятствует read-only этапу 0 и локальному исследованию загрузчика.
