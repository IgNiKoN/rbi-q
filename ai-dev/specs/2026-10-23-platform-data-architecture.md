# Архитектура данных платформы: компании, модули, обмен, работа без сети

**Статус:** УТВЕРЖДЕНО владельцем 23.10.2026 (вместе с P2-0015).  
**Основание:** ADR-064, ADR-065, ADR-066. Дополняет ADR-066 пп. 8–12.

## Ответы владельца 23.10.2026

| Вопрос | Решение |
|---|---|
| Данные между компаниями (КС-2 подрядчика → генподрядчику, замечание СК → подрядчику) | **Позже, но заложить сейчас** |
| Данные между модулями одной компании | **Через ядро** — модули друг в друга не лезут |
| Прораб без интернета (подвал, верхние этажи) | **Нужна работа без сети** — заложить сейчас, делать отдельным блоком |
| Копия у покупателя ↔ наше облако | **Позже, через обмен документами** — тот же механизм, что между компаниями |

## Картина

```
        ┌──────────────────────── сервер (облако или копия покупателя) ────────────────────────┐
        │  core (ядро)                                                                          │
        │   компании · люди/роли · модули-лицензии                                              │
        │   Объекты → корпус → секция → этаж → помещение · Контрагенты · ЕИ · виды работ        │
        │   связи между записями модулей (links) · журнал событий (events)                      │
        │   обмен документами: исходящие / входящие (outbox / inbox)                            │
        │        ▲ ссылки                ▲ ссылки                ▲ ссылки                        │
        │  planfact (ВОР, смета,   quality (проверки,      construction (замечания,             │
        │  факт, КС-2)             задачи)                 приёмка)                             │
        └───────────────▲──────────────────────────────────────────────▲───────────────────────┘
                        │ очередь изменений (без сети)                 │ пакет документа
                  телефон прораба                              другая компания / другой сервер
```

## Правила (обязательны для всех новых таблиц; проверяются тестом)

1. **Чьё это.** У каждой рабочей записи — `company_id`; ссылки внутри компании — составным ключом `(id, company_id)` (уже так в 001–014): сервер физически не даст сослаться на чужую запись. RLS — deny-by-default, по членству в компании.
2. **Номер записи — UUID**, может создаваться на устройстве. Нужен для работы без сети и переноса компании облако ↔ свой сервер без перенумерации.
3. **Учёт изменений.** У синхронизируемых таблиц: `updated_at`, `deleted_at` (мягкое удаление — устройство должно узнать, что запись удалена). Жёсткое удаление — только при очистке компании/тестовых данных.
4. **Границы модулей.** Модуль ссылается только на ядро и на свои таблицы. Чужие таблицы модулей не читает и не пишет; RPC другого модуля не вызывает. Клиент модуля получает мастер-данные только через `src/platform/core/`.
5. **Связи между модулями — в ядре:** `core.links` (откуда: модуль/тип/id → куда: модуль/тип/id, вид связи, компания). Пример: «замечание СК ↔ работа ВОР», «факт ↔ фото исполнительной». Отключили модуль — связи остаются, другие модули работают.
6. **События — в ядре:** `core.events` (компания, модуль, тип «факт подтверждён», ссылка на запись, время). Модули реагируют на события, а не друг на друга. Журнал же служит для уведомлений и аналитики.
7. **Компании не делят строки.** Обмен между компаниями — **копией документа**: у отправителя — исходящий пакет (`core.outbox`), у получателя — входящий (`core.inbox`) со статусом «получен / принят / отклонён» и ссылкой «откуда». RLS остаётся простым (каждая компания видит только своё). Контрагент может быть привязан к компании на платформе (`counterparties.platform_company_id`, необязательно).
8. **Другой сервер = тот же пакет.** Пакет документа — один формат (JSON + файлы, номер сервера-отправителя, подпись). Между серверами он едет тем же путём, что между компаниями, только через сетевой адрес. У каждой установки — свой `installation_id`.
9. **Без сети.** Телефон держит копию нужного пользователю (его объекты, ВОР, справочники) и очередь своих действий. Каждое действие — с номером операции: повторная отправка не создаёт дубль. Факт — только добавлением новых записей (не правкой старой), поэтому конфликтов почти нет; правки справочников — «последний сохранивший» + запись в журнал.
10. **Ничего не зашивать в код:** ни компанию, ни проект, ни сервер — только настройки (ADR-066 п.5).

## Что делаем когда

| Когда | Что |
|---|---|
| **P2-0015 (ядро)** | Схема `core`, Контрагенты с `platform_company_id`; правила 1–4 и 10; правило 3 — колонки `updated_at`/`deleted_at` у таблиц ядра; тест-линтер «у новой таблицы есть `company_id`, UUID, `updated_at`» |
| P2-0016 (Качество у покупателя) | `core.links` + `core.events` — первыми их потребуют замечания ↔ объекты/работы |
| Отдельный блок «Прораб без сети» (этап В) | Правило 9 для факта План/Факта (переиспользуем опыт очереди Качества) |
| Отдельный блок «Обмен документами» (по первому запросу клиента) | Правила 7–8: КС-2 подрядчик → генподрядчик; затем между серверами |

Порядок «заложить сейчас, построить по запросу» — ADR-066 п.6: ядро растёт по требованию модулей, но правила 1–4, 10 соблюдаются с первого дня, чтобы потом не переделывать.
