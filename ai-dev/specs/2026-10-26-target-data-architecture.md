## 1. Главная идея

Любая рабочая запись любого модуля (позиция работ, факт, проверка, замечание, приёмка, строка графика, статья бюджета, гарантийное обращение) отвечает на вопросы **ссылками на записи ядра, не текстом** — это «оси» MODULES §6:

| Ось | Запись ядра |
|---|---|
| **Где** | (подразделение →) проект → объект → место |
| **Что** | вид работ (→ позиция работ) |
| **Кто делает** | договор → контрагент → бригада |
| **Кто отвечает** | человек (участие в проекте) |
| **Когда** | дата / период |

Тогда «качество + срок + деньги» по объекту, этажу, виду работ, договору или бригаде — простое сложение, без сопоставления названий, и пять сквозных цепочек MODULES §6 проходят по одним записям.

## 2. Целевая модель

```
КОМПАНИЯ (тенант, граница данных, лицензии модулей)
│
├─ НАСТРОЙКИ: платформа → компания → проект; у параметра «замок» (проект наследует, менять нельзя) ← v1.3
│   шаблоны платформы (виды работ, чек-листы) компания копирует себе и правит (1а п.6)
│
├─ ЛЮДИ И ПРАВА: сотрудник · роль · УЧАСТИЕ В ПРОЕКТЕ
│   (человек + роль + проект [+ объект/секция, договор, срок] + «ответственный за факт»)      ← v1.3
│
├─ ПОДРАЗДЕЛЕНИЕ (дирекция) — необязательно: группа проектов для прав, аналитики, рассылок   ← v1.3
│   └─ ПРОЕКТ (ЖК, очередь): карточка, заказчик, сроки, РП, стадия жизненного цикла      ← 7.1
│       ├─ ОБЪЕКТ (здание/сооружение): корпус · паркинг · сети · благоустройство          ← 7.1
│       │   └─ МЕСТА (одно дерево): секция → этаж → помещение (стр. № / № БТИ) · МОП · кровля · захватка
│       └─ НАБОР ВИДОВ РАБОТ ПРОЕКТА — выборка из справочника компании,                    ← v1.3
│          свои параметры (кроме «под замком»), обновление от компании — явно, по версии
│
├─ УЧАСТНИКИ: контрагент (ИНН; своя компания — тоже контрагент)
│   └─ ДОГОВОР = проект × контрагент: предмет, виды работ, фронт (объекты/места), сроки     ← 7.3
│       └─ БРИГАДА — всегда у контрагента («свои силы» = своя компания), состав с историей  ← 7.4
│
├─ КЛАССИФИКАТОРЫ: вид работ (классификатор уровней → вид, ЕИ, нормы, трудозатраты; ПАРАМЕТРЫ: дней на ← v1.3
│   этаж/единицу, шаг, последовательность, вес для %; «кто принимает» — направление контроля)
│   · единицы (+ синонимы)
│   └─ ШАБЛОН ЧЕК-ЛИСТА — привязан к виду работ, с версиями; назначение: проверка качества,  ← 7.6, 5.3
│      приёмка этапа, чек-лист заказчика
│
├─ ПОЗИЦИЯ РАБОТ = место × вид работ × объём (+ договор) — ячейка учёта для всех модулей
│
└─ СЕРВИСЫ ЯДРА: документы/фото · задачи · журнал изменений · связи (links) · события (events)

МОДУЛИ (своё, ссылаются только на ядро):
  Семейство План/Факт (7.7):
    Сметы и КС-2: ВОР-исходник и связки, словарь, цены, смета, КП, КС-2 — создаёт позиции работ ядра
    Производство: факт, подтверждения, журнал, шахматка «выполнено», чек-лист заказчика, фото, офлайн
    Сроки: ГПР/ГДРС — отдельный модуль сразу, на позициях работ ядра                          ← 7.7 (вместо 7.2б)
    ФОТ и выплаты: расценки бригад, реестры 10/25, 1С — только вместе с Производством
  Качество: проверки по шаблону, дефекты, эталоны, FMEA, совещания
  Стройконтроль: замечания на планах, ПРИЁМКА ЭТАПОВ по шаблону вида работ, ШАХМАТКА, передача ← 5.3
  ПТО и документы (вкл. проектирование на старте): РД, ИД, версии, маршруты                ← 7.5
  Далее по карте: Бюджет, Подрядчики, Тендеры, Безопасность, Гарантия … — те же записи ядра
```

## 2а. Модули по компаниям (MODULES §1а)

- **У каждой компании свой набор модулей; ядро есть у всех.** Все записи ядра (проект, объекты и места, люди и участие, контрагенты, договоры, бригады, виды работ, шаблоны чек-листов) ведутся в разделе «Компания» и работают **без единого включённого модуля**. Экран записи ядра не живёт внутри модуля.
- **Модуль работает один.** Модуль ссылается только на ядро и свои таблицы (правило 4 от 23.10); никакой внешний ключ, запрос, функция или экран модуля не требует другого модуля.
- **Связь — только если у компании включены оба.** Связи между модулями идут через ядро: позиция работ, `core.links`, `core.events`. Потребитель показывает чужие данные (например, «принято» СК в План/Факте, «выполнено» прораба в шахматке СК) только при `company_modules` = включён у обоих; иначе связь скрыта, данные не теряются. Проверка — на сервере, не только в интерфейсе.
- **Три проверки изоляции в каждой карточке** (`templates/TASK_CARD.md`, раздел 3в): чужая компания · без модуля-партнёра · с модулем-партнёром.

## 5. Правила «без костылей» (дополняют правила 1–10 от 23.10)

11. **Записи ядра — только в ядре.** Модуль не держит копий проектов, объектов, мест, фирм, договоров, бригад, видов работ, шаблонов чек-листов. Модульная настройка — своя таблица со ссылкой на id ядра.
12. **Ссылка — всегда id.** Название в записи модуля — только снимок для печати и истории; поиск и права по нему запрещены.
13. **Права — только через участие в проекте.** Никаких списков объектов в массивах и узнавания по имени.
14. **Старое — мостом с датой снятия.** Мост (`*_aliases`, `*_core_links`, триггер «текст → id») — с пунктом в `TECH_DEBT.md` и блоком, который его снимает.
15. **Оси обязательны.** Новая учётная таблица несёт нужные оси п. 1 как ссылки; проверяется тестом-линтером схемы вместе с правилами 1–3.
16. **Модуль работает один** (MODULES §1а): связь с другим модулем — только через ядро и только при включённых у компании обоих; проверяется тремя проверками изоляции карточки.
17. **Наследование вместо копий.** Настройка или параметр задаётся на самом высоком уровне (платформа → компания → проект) и наследуется; переопределение ниже — только если нет замка; изменение наверху доходит вниз явным обновлением по версии, а не тихой перезаписью.

## 7. План первого блока — «Подразделение → Проект → Объекты → места» (черновик до карточки)

**Что увидит владелец:** «Компания → Проекты» → проекты сгруппированы по подразделениям (если заведены) → карточка проекта (код, адрес, даты, РП, стадия, подразделение) → вкладка «Объекты и места»: объекты (корпус, паркинг, сети, благоустройство), под ними секции, этажи, квартиры со строительным номером и номером БТИ. Во всей Платформе и План/Факте — слово «Проект». Всё это работает у компании, у которой не включён ни один модуль.

| № | Этап (вертикальный срез) | Проверка → ожидаемо | Показ |
|---|---|---|---|
| 1 | **Сервер (самый рискованный):** миграция — `core.divisions` (RLS по компании), у проекта поля карточки + `division_id` + стадия; у места тип `object` + вид объекта, номера помещения; правило «корень дерева = объект»; синхронизация мест Качества (P2-0045) переводит корневые корпуса RBI в объекты. Проба на копии: сколько корней RBI станет объектами, сколько «не корпус» | PGlite: миграция + откат побайтно; проба на сервере только чтением — число объектов = числу корпусов, ошибок 0; `test:server` = база | нет |
| 2 | **Карточка проекта и подразделения:** справочник подразделений в «Компании», список проектов с группировкой и фильтром, карточка проекта | unit + экран в оболочке; ПК и 375 px, светлая/тёмная | да |
| 3 | **«Объекты и места»** внутри проекта: объекты → дерево мест, номера квартир; у проектов, чьи места ведёт Качество, — только просмотр с пометкой | unit + экран; место без объекта создать нельзя | да |
| 4 | **Слово «Проект»** вместо «Объект» в Платформе и План/Факте (~19 файлов `src/platform`, `src/modules/planfact`); старое Качество не трогаем | поиск по коду: «Объект» в значении ЖК — 0; сборки company/planfact/platform | нет |

**Проверки изоляции (MODULES §1а):** (1) **чужая компания** — сотрудник компании Б не видит подразделения, проекты, объекты и места компании А (REST, RPC) → пусто/отказ; (2) **без модулей** — тестовая компания с выключенными План/Факт, Качеством, Стройконтролем: «Компания → Проекты», карточка и «Объекты и места» работают, ссылок на модули нет; (3) **с модулями** — у RBI План/Факт показывает в выборе места объекты верхним уровнем, Качество и Стройконтроль работают как раньше, видимость замечаний не меняется.

**Не входит:** права по подразделению/объекту/секции (блок 2), договоры (блок 3), набор видов работ и настройки с замком (блок 4), правка мест RBI из Платформы (блок 6), импорт структуры из Excel и типовые этажи.
**CRITICAL-зона одна:** миграции (этапы 1, 5). Откат — `down`-миграция, приложение — `git reset` на прежний коммит.
