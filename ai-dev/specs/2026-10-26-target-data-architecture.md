## 1. Главная идея

Любая рабочая запись любого модуля (позиция работ, факт, проверка, замечание, приёмка, строка графика, статья бюджета, гарантийное обращение) отвечает на вопросы **ссылками на записи ядра, не текстом** — это «оси» MODULES §6:

| Ось | Запись ядра |
|---|---|
| **Где** | (подразделение →) проект → объект → место |
| **Что** | вид работ (→ позиция работ) |
| **Кто делает** | договор → контрагент → бригада |
| **Кто отвечает** | человек (участие в проекте) |
| **Когда** | дата / период |

Тогда «качество + срок + деньги» по объекту, этажу, виду работ, договору или бригаде — простое сложение, без сопоставления названий, и пять сквозных цепочек MODULES §6 проходят по одним записям.

## 2а. Модули по компаниям (MODULES §1а)

- **У каждой компании свой набор модулей; ядро есть у всех.** Все записи ядра (проект, объекты и места, люди и участие, контрагенты, договоры, бригады, виды работ, шаблоны чек-листов) ведутся в разделе «Компания» и работают **без единого включённого модуля**. Экран записи ядра не живёт внутри модуля.
- **Модуль работает один.** Модуль ссылается только на ядро и свои таблицы (правило 4 от 23.10); никакой внешний ключ, запрос, функция или экран модуля не требует другого модуля.
- **Связь — только если у компании включены оба.** Связи между модулями идут через ядро: позиция работ, `core.links`, `core.events`. Потребитель показывает чужие данные (например, «принято» СК в План/Факте, «выполнено» прораба в шахматке СК) только при `company_modules` = включён у обоих; иначе связь скрыта, данные не теряются. Проверка — на сервере, не только в интерфейсе.
- **Три проверки изоляции в каждой карточке** (`templates/TASK_CARD.md`, раздел 3в): чужая компания · без модуля-партнёра · с модулем-партнёром.

## 2б. Стороны модулей и роль компании в проекте (MODULES §1б)

- **Сторону задаёт проект, а не компания.** У проекта поле «наша роль» (`core.projects.own_role`): заказчик · генподрядчик · подрядчик · технадзор · проектировщик. Из неё следует сторона модулей на этом проекте:

  | Наша роль | Сторона | Пример |
  |---|---|---|
  | заказчик, технадзор | заказчика | ИД — проверка; Стройконтроль — замечания и приёмка |
  | подрядчик | подрядчика | ИД — подготовка; План/Факт — факт и КС-2 |
  | генподрядчик | **обе**: подрядчика — вверх (к заказчику по договору), заказчика — вниз (к своим субподрядчикам) | приём ИД субподрядчиков и отправка своей ИД заказчику |
  | проектировщик | своя (ПТО и документы / Проектирование) | выпуск РД, ответы на запросы |

- **Что видит человек** = лицензия компании (модуль × сторона) ∩ сторона по роли проекта ∩ его права по участию в проекте. Нет лицензии на сторону — экраны этой стороны скрыты, данные не теряются (1а п. 5).
- **Код и данные у сторон общие**, различаются экраны и права. Отдельных таблиц «для подрядчика» и «для заказчика» нет; запись знает свою сторону через договор (кто кому сдаёт).
- **Существующие поля** `core.projects.customer_id`, `general_contractor_id` (017) остаются как «кто заказчик / кто генподрядчик» — это контрагенты; «наша роль» — отдельный признак. Договоры (блок 3) связывают остальных участников проекта с нами.
- **Компании вместе** (§1б): (1) обе на платформе — **связь проектов** через договор + пакет-копия; (2) только заказчик — гостевой доступ подрядчика (как кабинет P2-0044); (3) только подрядчик — выгрузка PDF / ZIP / Excel.

**В ядре не хранятся** (MODULES §2): заполненные чек-листы, дефекты, замечания, факт, сметы, графики — это рабочие данные модулей со ссылками на ядро. Шаблон чек-листа — запись ядра (MODULES v1.1 §2): один механизм для Качества, приёмки СК, ОТ и чек-листа заказчика; в ядре нет только **результатов** проверок и приёмок.

## 5. Правила «без костылей» (дополняют правила 1–10 от 23.10)

11. **Записи ядра — только в ядре.** Модуль не держит копий проектов, объектов, мест, фирм, договоров, бригад, видов работ, шаблонов чек-листов. Модульная настройка — своя таблица со ссылкой на id ядра.
12. **Ссылка — всегда id.** Название в записи модуля — только снимок для печати и истории; поиск и права по нему запрещены.
13. **Права — только через участие в проекте.** Никаких списков объектов в массивах и узнавания по имени.
14. **Старое — мостом с датой снятия.** Мост (`*_aliases`, `*_core_links`, триггер «текст → id») — с пунктом в `TECH_DEBT.md` и блоком, который его снимает.
15. **Оси обязательны.** Новая учётная таблица несёт нужные оси п. 1 как ссылки; проверяется тестом-линтером схемы вместе с правилами 1–3 — сторож таблиц P2-0069 (`standards/DATA_TABLES.md`, `npm run test:unit` / `test:schema`).
16. **Модуль работает один** (MODULES §1а): связь с другим модулем — только через ядро и только при включённых у компании обоих; проверяется тремя проверками изоляции карточки.
17. **Наследование вместо копий.** Настройка или параметр задаётся на самом высоком уровне (платформа → компания → проект) и наследуется; переопределение ниже — только если нет замка; изменение наверху доходит вниз явным обновлением по версии, а не тихой перезаписью.
