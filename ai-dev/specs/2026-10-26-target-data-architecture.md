# Целевая архитектура данных платформы — ядро на весь жизненный цикл проекта

**Дата:** 26.10.2026 · **Роль:** Архитектор · **Статус:** ПРОЕКТ, ждёт согласия владельца · без кода.
**Основа (главнее этого файла):** `reference/MODULES.md` (v1.1; раздел 1а — по v1.2, см. п. 2а) — разделы 2 (ядро), 5.x (модули), 6 (сквозные цепочки), **7 (решения владельца 26.10.2026 — обязательны)**; `specs/2026-10-23-platform-data-architecture.md` (правила 1–10 остаются в силе); ТЗ v1.1 §2.1, §3, §10; опись `specs/2026-10-26-master-data-inventory.md`; миграции 001–044 (P2-0045 влита).
**Задача владельца:** «выстроить архитектуру данных правильно сейчас, доработать то, что есть, без костылей; карта — ориентир».

---

## 1. Главная идея

Любая рабочая запись любого модуля (позиция работ, факт, проверка, замечание, приёмка, строка графика, статья бюджета, гарантийное обращение) отвечает на вопросы **ссылками на записи ядра, не текстом** — это «оси» MODULES §6:

| Ось | Запись ядра |
|---|---|
| **Где** | проект → объект → место |
| **Что** | вид работ (→ позиция работ) |
| **Кто делает** | договор → контрагент → бригада |
| **Кто отвечает** | человек (участие в проекте) |
| **Когда** | дата / период |

Тогда «качество + срок + деньги» по объекту, этажу, виду работ, договору или бригаде — простое сложение, без сопоставления названий, и пять сквозных цепочек MODULES §6 проходят по одним записям.

## 2. Целевая модель

```
КОМПАНИЯ (тенант, граница данных, лицензии модулей)
│
├─ ЛЮДИ И ПРАВА: сотрудник · роль · УЧАСТИЕ В ПРОЕКТЕ (человек + роль + проект [+ объект, договор, срок])
│
├─ ПРОЕКТ (ЖК, очередь): карточка, заказчик, сроки, РП, стадия жизненного цикла          ← 7.1
│   └─ ОБЪЕКТ (здание/сооружение): корпус · паркинг · сети · благоустройство              ← 7.1
│       └─ МЕСТА (одно дерево любой глубины): секция → этаж → помещение · МОП · кровля · захватка
│
├─ УЧАСТНИКИ: контрагент (ИНН; своя компания — тоже контрагент)
│   └─ ДОГОВОР = проект × контрагент: предмет, виды работ, фронт (объекты/места), сроки     ← 7.3
│       └─ БРИГАДА — всегда у контрагента («свои силы» = своя компания), состав с историей  ← 7.4
│
├─ КЛАССИФИКАТОРЫ: вид работ (раздел → вид, ЕИ, нормы) · единицы (+ синонимы)
│   └─ ШАБЛОН ЧЕК-ЛИСТА — привязан к виду работ, с версиями; назначение: проверка качества,  ← 7.6, 5.3
│      приёмка этапа, чек-лист заказчика
│
├─ ПОЗИЦИЯ РАБОТ = место × вид работ × объём (+ договор) — ячейка учёта для всех модулей
│
└─ СЕРВИСЫ ЯДРА: документы/фото · задачи · журнал изменений · связи (links) · события (events)

МОДУЛИ (своё, ссылаются только на ядро):
  План/Факт: ВОР-исходник и сопоставление, цены, смета, КП, факт, КС-2, ФОТ;
             ГРАФИК (ГПР/ГДРС) — отдельный блок внутри План/Факта на позициях ядра        ← 7.2
  Качество: проверки по шаблону, дефекты, эталоны, FMEA, совещания
  Стройконтроль: замечания на планах, ПРИЁМКА ЭТАПОВ по шаблону вида работ, ШАХМАТКА, передача ← 5.3
  ПТО и документы (вкл. проектирование на старте): РД, ИД, версии, маршруты                ← 7.5
  Далее по карте: Бюджет, Подрядчики, Тендеры, Безопасность, Гарантия … — те же записи ядра
```

## 2а. Модули по компаниям (MODULES §1а)

- **У каждой компании свой набор модулей; ядро есть у всех.** Все записи ядра (проект, объекты и места, люди и участие, контрагенты, договоры, бригады, виды работ, шаблоны чек-листов) ведутся в разделе «Компания» и работают **без единого включённого модуля**. Экран записи ядра не живёт внутри модуля.
- **Модуль работает один.** Модуль ссылается только на ядро и свои таблицы (правило 4 от 23.10); никакой внешний ключ, запрос, функция или экран модуля не требует другого модуля.
- **Связь — только если у компании включены оба.** Связи между модулями идут через ядро: позиция работ, `core.links`, `core.events`. Потребитель показывает чужие данные (например, «принято» СК в План/Факте, «выполнено» прораба в шахматке СК) только при `company_modules` = включён у обоих; иначе связь скрыта, данные не теряются. Проверка — на сервере, не только в интерфейсе.
- **Три проверки изоляции в каждой карточке** (`templates/TASK_CARD.md`, раздел 3в): чужая компания · без модуля-партнёра · с модулем-партнёром.

## 3. Записи ядра — сейчас → цель → работа

| Запись | Сейчас (сервер) | Цель | Что сделать |
|---|---|---|---|
| Компания, сотрудник, роль, модули | `core.companies`, `company_members`, `user_profiles`, `company_roles`, `module_catalog`, `company_modules` | без изменений | — |
| **Участие в проекте** | `core.role_assignments`: человек + роль + `project_id` (null = все), `counterparty_id`, `valid_from/to` **+ костыли `quality_objects text[]`, `quality_object_keys text[]`** | одно назначение = человек + роль + проект [+ объект, договор]; срок — `valid_to`. Права всех модулей — только по нему | `object_id`, `contract_id`; права Качества — по проекту/объекту; убрать `quality_objects*` |
| **Проект** | `core.projects`: имя, заказчик, генподрядчик **+ `quality_container`**; в интерфейсе — «Объект» | карточка: код, имя, адрес, даты план (старт/финиш), РП, **стадия** (проектирование → тендер → строительство → ввод → гарантия → эксплуатация), архив. В интерфейсе — «Проект» | поля; переименование в интерфейсе; убрать контейнер «Объекты RBI» и узнавание по названию |
| **Объект (здание)** | уровня нет; корпуса — узлы `building` в дереве мест | **верхний уровень дерева мест проекта** (тип `object`, вид: корпус / паркинг / сети / благоустройство / прочее). Отдельной таблицы нет — одно дерево, но корень всегда объект | тип `object` + `object_kind`; правило «корень = объект»; перенос корней RBI |
| **Места** | `core.locations` — главное дерево; у RBI ведёт Качество (P2-0045, шаг 1), План/Факт только видит; Стройконтроль v1 — своё дерево `construction_*` | одно дерево `core.locations`, **ведёт ядро** (экран «Объекты и места»), Качество и Стройконтроль ссылаются по id | шаг 2 P2-0045 (правка в ядре, Качество следует); Стройконтроль v1 → места ядра |
| Контрагент | `core.counterparties` (ИНН) + 4 таблицы Качества и текст | один справочник; вид «своя компания» (одна на компанию), «проектировщик» | виды; таблицы Качества — мост до блока уборки |
| **Договор** | нет; «подрядчики объекта» — `quality.contractor_directory`, `quality.contracts` | `core.contracts`: проект × контрагент, роль (генподряд / подряд / поставка / проектирование), номер, дата, виды работ, фронт (объекты/места), сроки | новая запись; заменяет справочник подрядчиков объекта Качества |
| **Бригада** | `planfact.brigades`: название, бригадир, телефон; без фирмы | `core.brigades`: контрагент (обязательно; «свои силы» = своя компания) + договор (необязательно), бригадир, **состав с историей**, архив | перенос в ядро, привязка к фирме; `fact_entries.brigade_id` сохраняется |
| **Вид работ** | `core.work_types` (ВОР); у Качества вид работ = шаблон (текст), категории замечаний — константы | один справочник компании: раздел → вид, ЕИ, нормы | поле «раздел»; соответствие категорий замечаний |
| Единица | `core.units` + текст `unit_text` | + синонимы | таблица синонимов (ТД №68) |
| **Шаблон чек-листа** | `quality.shared_checklists`, `data/system_templates.js`, выбор официальных — `rbi_company_settings`; к виду работ не привязан | `core.checklist_templates` (+ версии): вид работ, назначение (проверка качества / приёмка этапа / чек-лист заказчика), пункты с весом и нормой (ссылка на Базу знаний). **Заполненный** чек-лист — в модуле | перенос шаблонов Качества в ядро с привязкой к виду работ; Качество, СК и План/Факт берут шаблон оттуда |
| **Позиция работ** | `planfact.vor_positions` (место × вид работ × ЕИ × объём) | запись ядра `core.work_items`: проект, место, вид работ, ЕИ, объём план, договор; ВОР-исходник, редакции и сопоставление остаются в План/Факте | вынести вместе с первым вторым потребителем (приёмка или график) |
| Документ/фото, задача, журнал | по модулям; задачи — только в Качестве | сервисы ядра (MODULES §3) | по нужде первого второго модуля (MODULES §1, правило 5) |

**В ядре не хранятся** (MODULES §2): заполненные чек-листы, дефекты, замечания, факт, сметы, графики — это рабочие данные модулей со ссылками на ядро. Шаблон чек-листа — запись ядра (MODULES v1.1 §2): один механизм для Качества, приёмки СК, ОТ и чек-листа заказчика; в ядре нет только **результатов** проверок и приёмок.

## 4. Решения раздела 7 и 5.3 — как они легли в модель

| № | Решение | В модели |
|---|---|---|
| 7.1 | Проект → Объект (здание) → места | Проект — `core.projects`; объект — корень дерева мест (тип `object`); интерфейс говорит «Проект», «Объекты и места» |
| 7.2 | График сейчас в План/Факте, отдельным блоком на позициях ядра | таблицы графика — в `planfact`, но ссылаются только на `core.work_items`, места, договоры, бригады, не на строки ВОР. Вынос в модуль «Сроки» = смена владельца таблиц без переделки ссылок |
| 7.3 | Договор — запись ядра сейчас | `core.contracts`; к нему — бригады, участие гостей подрядчика, КС-2, позже Бюджет |
| 7.4 | Бригада принадлежит подрядчику или «своим силам» | `core.brigades.counterparty_id` обязателен; своя компания — контрагент |
| 7.5 | Проектирование — часть «ПТО и документы» на старте | новых записей ядра не требует: проект, объекты, договор с проектировщиком, документы |
| 7.6 | Чек-листы привязаны к виду работ ядра | `core.checklist_templates.work_type_id` обязателен |
| 5.3 | Приёмка этапов по чек-листу вида работ; шахматки | **Приёмка** (Стройконтроль): подрядчик записывается на место × вид работ (этап) **в пределах своего договора и фронта** и бронирует окно инженера → инженер принимает по шаблону «приёмка этапа» этого вида работ (телефон, без связи) → принято (акт) / принято с замечаниями (замечания из пунктов) / не принято (повторный вызов учитывается) → статус «место × вид работ = принято», следующий этап — «фронт готов» → событие «принято» в ядро (План/Факт и Сроки берут его, если включены). Хранит СК: календарь, заявки, результаты по пунктам, акты, статусы. **Шахматки** (готовность, замечания, передача) — представления «место × вид работ» по осям ядра; «выполнено (прораб)» — только если включён План/Факт |

## 5. Правила «без костылей» (дополняют правила 1–10 от 23.10)

11. **Записи ядра — только в ядре.** Модуль не держит копий проектов, объектов, мест, фирм, договоров, бригад, видов работ, шаблонов чек-листов. Модульная настройка — своя таблица со ссылкой на id ядра.
12. **Ссылка — всегда id.** Название в записи модуля — только снимок для печати и истории; поиск и права по нему запрещены.
13. **Права — только через участие в проекте.** Никаких списков объектов в массивах и узнавания по имени.
14. **Старое — мостом с датой снятия.** Мост (`*_aliases`, `*_core_links`, триггер «текст → id») — с пунктом в `TECH_DEBT.md` и блоком, который его снимает.
15. **Оси обязательны.** Новая учётная таблица несёт нужные оси п. 1 как ссылки; проверяется тестом-линтером схемы вместе с правилами 1–3.
16. **Модуль работает один** (MODULES §1а): связь с другим модулем — только через ядро и только при включённых у компании обоих; проверяется тремя проверками изоляции карточки.
