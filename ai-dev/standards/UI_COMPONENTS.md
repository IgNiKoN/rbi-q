# Platform 2.0 — единый каталог компонентов и UX-паттернов

**Версия:** 1.0 · 20.10.2026  
**Статус:** правила для будущей общей библиотеки. **Не считать приведённый каталог реализованным или обязательным для первого MVP.**

## 1. Принцип компонента

**Один тип действия — один общедоступный компонент/паттерн** с едиными вариантами, поведением, состояниями и токенами. Отдельные модули не разрабатывают собственные несовместимые `Button`/`Modal`/`Table` при наличии подходящей общей реализации.

Выделять в общую библиотеку только устойчивое повторное поведение. Общие классы CSS и типизированные React-обёртки допускается выпускать независимо; публичный UI-контракт и совместимость документируются.

## 2. Приоритетный набор — по реальным задачам Plan/Fact

### Используемые в первом MVP

| Компонент / паттерн | Основные варианты/состояния | Ориентир из RBI Platform |
| --- | --- | --- |
| `Button` | primary / secondary / ghost / danger при реальной потребности; disabled, loading, focus | `.rbi-btn`, `.rbi-btn--primary`, `.rbi-btn--ghost` |
| `Card` / `Panel` | surface, header/content/footer, compact | `.rbi-card`, `.rbi-card--lg` |
| `Badge` / `Status` | в срок, риск, отставание, выполнено; текст + семантический цвет | `.rbi-chip` как исходный примитив |
| `Input` / `NumberField` | label, unit, required, error, readonly | адаптация существующих форм |
| `Select` / `Combobox` | проект, локация, вид работ; empty/loading/error | адаптация существующих форм |
| `DataTable` | ВОР, план/факт, сортировка, фильтры, пусто/ошибка | аудит существующих таблиц до создания нового |
| `Dialog` / `ConfirmDialog` | ввод/изменение факта, подтверждение опасных действий | аудит текущих modals и keyboard behavior |
| `Toast` / `InlineAlert` | успех, валидация, ошибки сети, конфликт | reuse-review существующих уведомлений |
| `Tabs` / `Navigation` | доступные разделы модуля | общий Shell, имеющиеся desktop strips |
| `EmptyState` / `Skeleton` | нет ВОР, нет данных, загрузка | общие паттерны вместо копирования разметки |

**Это целевой функциональный контракт, а не указание немедленно писать десять новых компонентов.** Если текущий `.rbi-btn` подходит, использовать его и тонкую обёртку, а не создавать с нуля новую кнопку.

| --- | --- | --- | --- |

## 3. Обязательные требования к публичному компоненту

1. Название и ответственность; единый источник истины.
2. API props/событий/ошибок и доступных вариантов; для TypeScript — публичные типы.
3. Использование общих semantic tokens (не свои hardcoded brand colors).
4. Состояния: loading/error/disabled/empty/focus по применимости.
5. Адаптивность и клавиатурная доступность; сообщения и labels читабельны.
6. Короткий пример использования и хотя бы один подтверждённый тест поведения.
7. Версия/правила совместимости, миграции, владелец компонента.
8. Отсутствие прямой зависимости от приватной бизнес-логики конкретного приложения.

## 4. Различия, которые нельзя терять

- **UI-компонент** отображает результат, **бизнес-сервис** определяет результат. `StatusBadge` не вычисляет отставание, он показывает переданный семантический статус.
- **Компонент таблицы** не знает о стоимости контрактов и правах пользователя; API решает, какие данные и операции разрешены.
- **Тема** меняет оформление, но не скрывает проверки прав и не изменяет объёмы.
- **Layout-configuration** может менять плотность, расположение панелей и вид карточки через утверждённые варианты; произвольная смена бизнес-процесса не является настройкой темы.

## 5. Жизненный цикл библиотечного компонента

**Найти существующий → использовать → проверить второе применение → при необходимости выделить/расширить публичный примитив → покрыть тестами → задокументировать → версионировать.**

Если библиотека ещё не выделена в самостоятельный пакет, временный публичный контракт и путь владельца фиксируются в `docs/UI_COMPONENTS.md` новой Platform 2.0. Нельзя делать дочерние модули зависимыми от нестабильного расположения файлов `js/modules/quality/...` или других внутренних каталогов.

## 6. Пример проверки одного сценария Plan/Fact

**Сценарий:** прораб выбирает работу, вводит 150 м² факта и сохраняет.

- Общий `Select` показывает доступные ему работы и состояние отсутствия данных.
- Общий `NumberField` показывает единицу измерения и валидирует форму; окончательная проверка объёма выполняется сервером.
- Общий `Button` показывает `loading`, защищает от случайного повторного нажатия (сервер дополнительно обеспечивает идемпотентность там, где требуется).
- Общий `Toast/InlineAlert` сообщает об успехе или ошибке сохранения.
- Общий `Status` отображает пересчитанное отклонение и текстовый смысл.
- Все элементы меняют оформление после выбора другой общей темы без изменения доменной логики.

**Критерий:** один и тот же общий компонент используется в следующем модуле без копирования его реализации и без правки ядра ради новой кнопки.
