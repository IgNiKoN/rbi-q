# Platform 2.0 — единая аутентификация, роли и серверные права

**Версия:** 1.0 · 20.10.2026  
**Статус:** обязательная логическая архитектура; точная физическая модель таблиц и API **предлагается** к подтверждению P2-0001/P2-0004.  
**Основание:** v1.3, разделы 4 и 10; v1.2, разделы 3, 19–22; ADR-020–031, 052–056.

## 1. Разделить четыре понятия

1. **Authentication — кто пользователь?** Одна личность и сессия через Supabase Auth в пределах SaaS-инсталляции. Company ID или имя должности не логин. On-prem использует собственный Auth.
2. **Membership / assignment — где ему разрешено работать?** Компания-владелец данных, проекты, действующие назначения и срок/фронт работ.
3. **Authorization — что он вправе сделать?** Сервер принимает решение по зарегистрированному `action`, ресурсу, текущим назначениям, состоянию данных и обязательным ограничениям.
4. **Entitlement — приобретена ли возможность?** Лицензия компании на модуль/подмодуль; роль не заменяет проверку лицензии.

Ни один модуль не реализует собственную параллельную систему входа или произвольную интерпретацию слов «прораб», «ПТО», «администратор».

## 2. Один каталог действий, но модули владеют своей бизнес-семантикой

- Платформа хранит единый реестр `permission_catalog` с **техническими ключами действий**, которые модуль публикует по версионированному контракту. Модуль вправе объявить новые поддерживаемые действия, но не выдать право на них самовольно.
- Примеры **условных** ключей: `planfact.wor.view`, `planfact.wor.edit`, `planfact.fact.create`, `planfact.fact.correct`, `planfact.plan.publish`, `security.members.assign`, `locations.create`.
- Регистрация ключа не означает предоставления права. Отсутствующий/неизвестный ключ, отозванный грант или отключённая лицензия означают **запрет**.
- Права выражаются действиями, а не названиями должностей. Бизнес-состояние ресурса (например, опубликованный план или собственный факт) проверяет серверный доменный обработчик модуля под общей политикой доступа.

## 3. Корпоративные роли управляются централизованно

**Цель:** изменить разрешения роли **один раз в пространстве компании**, и все модули используют обновлённые права для новых операций без переписывания проверок в их исходниках.

- Набор доступных действий определяется зарегистрированными сервером ключами.
- `company_roles` (условное имя) — роли **конкретной компании**; `company_role_permissions` — их действия; `role_assignments` — кому, в каком проекте/локации/сроке назначена роль. Физические таблицы согласовываются после аудита текущего Git/БД; уже существующие сущности не дублировать.
- Один пользователь может иметь несколько ролей с непересекающимися областями. Сложение разрешений допустимо лишь в границах каждого назначения и не объединяет доступ разных tenants.
- Роль можно переименовать без изменения разрешений или серверных ключей. Должность/ярлык в UI **не управляет доступом**.
- Позже полноценный конструктор роли позволит редактировать наборы действий через **черновик → анализ влияния → публикацию** с версиями и аудитом (как утверждено в v1.2). До MVP такой интерфейс **не нужен**.

**MVP:** достаточно ролей «Администратор», «РП», «ПТО», «Прораб», однако их ограничения и назначения должны храниться централизованно в серверной модели и проверяться по `action`, а не в десятках `if role === ...`. Начальные определения допустимо загрузить через проверяемые seed/миграции. Изменение полномочий не должно требовать правки каждого экрана. Любое изменение seed не заменяет управляемые опубликованные роли на рабочих данных автоматически.

## 4. Обязательная серверная цепочка проверки

```text
Аутентифицированный user_id (Supabase Auth)
      ↓
Активный контекст компании-владельца ресурса
      ↓
Членство пользователя / действующее гостевое назначение
      ↓
Проект + назначенная область действия (договор/локации/фронт)
      ↓
Зарегистрированное действие + эффективные роли/гранты
      ↓
Лицензия модуля/подмодуля + состояние ресурса/бизнес-ограничения
      ↓
РАЗРЕШИТЬ или ЗАПРЕТИТЬ (по умолчанию — ЗАПРЕТИТЬ)
```

- Контракт условного `AccessService.authorize({ actor, action, resource })` задаёт **семантику**, но не утверждённую сигнатуру TypeScript; конкретные API и хранение данных определяются P2-0004.
- Все чувствительные операции, запросы к таблицам, RPC, защищённые файлы Storage, экспорт и фоновые действия должны соблюдать **эквивалентную** политику. Скрытие кнопки — только UX, не контроль доступа.
- Postgres RLS, constraints и серверные функции обеспечивают невозможность обхода границ tenant. Общий сервис прав не заменяет RLS и наоборот: они используют согласованные централизованные данные и должны проверяться на одинаковых кейсах.
- Клиентский `ctx.permissions` — подсказка для UI. Роли, project_id и company_id из браузера нельзя доверять без серверной проверки.
- Переименование роли и замена темы не влияют на серверную авторизацию. Пользователь не может редактированием роли повысить себе права или выдать собственное администрирование.

## 5. Изменения и отзыв прав

- Источник истины прав — опубликованные серверные назначения и политики, а не выданная ранее клиенту копия объекта пользователя.
- После отзыва права **новые серверные операции** блокируются без требования повторного входа пользователя. UI обновляет представление прав при смене контекста или по согласованной схеме обновления; stale-кэш не даёт дополнительных полномочий.
- Любое изменение назначения/роли содержит автора, время и версию. Полный механизм публикации ролей откладывается, но протокол обновления должен допускать такую версионность без ломки контрактов.
- Офлайн-очередь в будущих релизах повторно авторизуется при синхронизации. Нельзя считать старый офлайн-токен вечным разрешением.
- Гостевой доступ, делегирование приглашений подрядчикам и временные scoped-grants сохраняются как **целевые требования** v1.2; не делать полноценный портал гостей до MVP.

## 6. Демонстрационный пример

Прорабу выдано разрешение `planfact.fact.create` на проект А. Он вводит объём — сервер принимает операцию. Администратор компании позже отзывает это разрешение в опубликованной роли. **Следующая** попытка создать факт через UI **и** прямой API должна завершиться отказом. Для этого не меняют исходники Plan/Fact, Quality или каждого экрана. Если пользователь остаётся вправе смотреть ВОР, его право просмотра не должно исчезнуть случайно.

## 7. Тесты, обязательные при создании/изменении этого механизма

1. Незнакомый `action` / отсутствующая роль / истёкшее назначение → запрет.
2. Подмена `company_id`, `project_id`, `location_id` в прямом запросе → отказ на сервере/RLS.
3. Пользователь двух компаний не переносит роли первой в контекст второй.
4. Изменение одного назначения действительно влияет на новые запросы соответствующих модулей/эндпоинтов без правок их кода.
5. Пользователь с правом редактировать роль не может выдать себе более высокую или чужую привилегию.
6. Отозванный гость (когда соответствующий функционал будет реализован) перестаёт выполнять новые операции; старые audit records сохраняются.
7. Лицензия отключена → даже ранее разрешённое действие недоступно; прочие модули сохраняют работу.
8. Клиентская кнопка скрыта, но прямой API/RPC/Storage запрос всё равно проверяется сервером.
9. Чувствительные статусы документа/плана изменяются только пользователем с отдельным действием и с соблюдением доменного бизнес-правила.

Тесты выполняются **по мере появления соответствующей функциональности**: отсутствие гостевого механизма в первом MVP не требует его предварительной полной реализации.

## 8. Чего **не** разрабатывать ради первого показа

Полный role builder, черновики и публикацию произвольных корпоративных ролей, иерархические гостевые делегирования, динамические лицензии с платежами, сложный policy-language/ABAC-движок. **Нужно:** одна реальная база правил/назначений, одна серверная семантика, работающие проверки и негативные тесты.

Светофор (цвет и пояснение), сроки и объёмы видят все с `fact.view` (прораб, заказчик) — **решение владельца 21.10.2026** (исключение к правилу «прогноз только при money.view»: цвет косвенно говорит о прогнозе, дата прогноза и ₽ не приходят). «Сделано ↔ КС-2» (`pf_summary_ks2_gap`) и итог выставленного в КС-2 видны с `fact.view` без `ks2.view`/`ks2.edit` — объёмы всем, ₽ только с `money.view` (по карточке P2-0008). Плановые даты проекта — `pf_project_set_dates` с `planfact.projects.manage`, проект не в архиве, журнал компании. Чужая компания, роль без `fact.view`, anon — отказ (тесты `011_summary.sql`).

Чтение: проекты и локации — всем, кто видит проект; единицы — общие всем вошедшим, свои — членам компании. Запись — только через `public.pf_*` (security definer, право проверяется внутри); прямые INSERT/UPDATE/DELETE у клиента закрыты. Изменения пишутся в журнал компании (`pf_list_company_audit`, виден при `security.roles.assign`).
