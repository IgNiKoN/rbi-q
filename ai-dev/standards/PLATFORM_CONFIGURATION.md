# Platform 2.0 — централизованные настройки, лицензии и feature flags

**Версия:** 1.0 · 20.10.2026  
**Статус:** обязательные принципы; физические схемы и UI настроек — техническое предложение по мере появления сценариев.

## 1. Одна модель настроек, разные области

Настройки нельзя разбрасывать по модулям в независимых файлах, таблицах или `localStorage`, если параметр влияет на всю платформу. У каждой настройки один владелец, валидируемая схема, область действия, версия и правила изменения.

| Область | Пример | Кто управляет |
| --- | --- | --- |
| **Инсталляция** | Endpoint безопасного тестового Supabase, базовая политика хранения | Уполномоченный оператор; секреты вне Git/UI |
| **Компания** | Разрешённая тема, язык по умолчанию, некоторые корпоративные предпочтения | Назначенный администратор компании |
| **Проект** | Параметры показа/представления работ, относящиеся к проекту | Пользователь с отдельным полномочием |
| **Пользователь** | Язык, фильтры, компактный режим, предпочтение светлой/тёмной темы | Сам пользователь в разрешённых пределах |
| **Модуль** | Опубликованные типизированные параметры конкретного Plan/Fact | Модуль объявляет схему; значение хранится с нужной областью и проверяется владельцем |

**Предлагаемое разрешение значений:** безопасный default → разрешённое значение установки/компании → разрешённое переопределение проекта → личное предпочтение **только для подходящих UI-параметров**. Это не безусловное правило «последнее всегда побеждает»: некоторые системные ограничения запрещено переопределять вообще. Точный алгоритм фиксируется для каждой настройки в её схеме.

## 2. Контракты и безопасность

- Платформенный Configuration Service выдаёт только разрешённые/валидированные значения через публичный версионированный API. Клиент не читает напрямую произвольные строки БД и не изменяет настройки другой компании.
- Каждая настройка имеет стабильный ключ, тип, default, область, разрешённые значения, владельца, правила валидации и версию схемы.
- Значение должно изменяться через **одно контролируемое действие**, с авторизацией и аудитом; кэш/подписчики обновляются при необходимости.
- Secrets/API keys/passwords, серверные DSN и доступ `service_role` живут в серверной среде или secret management, **не в открытой конфигурации компании, браузере и Git**.
- Дизайн-токены задаёт Design System/Theme Service; Settings хранит выбранный theme ID и разрешённые пользовательские предпочтения, не альтернативный CSS каждого модуля.
- Установка, владелец и пользователь не вправе ослабить RLS, правило владения компанией, проверку подписи или обязательную лицензии через обычную настройку.

## 3. Feature flags и лицензии — разные механизмы

**Feature flag** управляет готовностью/раскаткой функции (например, включает экспериментально уже реализованную возможность). **Entitlement** проверяет право компании использовать оплаченный модуль. **Authorization** проверяет, вправе ли именно пользователь совершить действие. Это разные условия; они должны выполняться одновременно.

- Каталог возможностей и флагов централизован, но модуль регистрирует **свои** поддерживаемые ключи и совместимые версии.
- Любая функция, закрытая лицензией или относящаяся к чувствительным данным, защищена **сервером**, а не только отображением кнопки или клиентским флагом.
- Выключенный модуль не должен ломать Shell, другие модули или уничтожать накопленные данные.
- До первого MVP не делать конструктор тарифов, биллинг, огромную консоль toggles или сложный экспериментальный движок. Достаточно проверки реально нужного права использования.

## 4. Локализация, единицы измерения и форматы

- Строки интерфейсов — через общий контракт локализации и ресурсные словари приложения; код не содержит локальные копии одинаковых подписей общего UI.
- Даты, часовые пояса, числовые форматы, проценты и единицы — через согласованные общие форматтеры (по мере использования), а **исходные числовые значения** хранятся независимо от оформления.
- Справочник единиц измерения принадлежит Master Data; выбор отображаемого формата не меняет смысл утверждённой ВОР.
- Не требуется сразу вводить мультиязычный продукт; нужно избежать архитектуры, в которой перевод одной общей кнопки потребует правок во всех приложениях.

## 5. Тест «меняем в одном месте»

1. Меняем разрешённую тему компании → общая оболочка и установленный модуль используют новую тему.
2. Меняем пользовательскую локаль → общие компоненты, дата/число в подключённом модуле отображаются согласованно там, где такой контракт реализован.
3. Выключаем разрешённую функцию централизованно → её нельзя вызвать напрямую в обход серверной проверки, если функция чувствительная; остальные сценарии работают.
4. Компания Б не видит и не изменяет настройки компании А.
5. Неизвестный или некорректный параметр получает безопасную ошибку/default; не выполняется произвольный код из значения настройки.
