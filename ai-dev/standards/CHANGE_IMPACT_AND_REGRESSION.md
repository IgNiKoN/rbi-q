# Радиус изменения, проверка регрессий и локальный технический долг

**Статус:** адаптация принятых в прежнем `_ai` принципов повторного использования и проверки зависимостей к отдельному Platform 2.0. **Не новый функционал MVP.**

## До правки: проверить последствия

Архитектор должен ответить на пять вопросов:

1. Это приватная функция одного модуля, публичный контракт модуля или общий сервис Shell/Core?
2. Кто реальный потребитель? Проверить код, а не считать исторический список связей актуальным.
3. Где единый владелец: код + данные + модель разрешений + конфигурация?
4. Что будет при изменении или отключении модуля/смене компании/отзыве права?
5. Какие тесты подтвердят работу затронутого пути и отсутствие регрессии соседей?

**Оценка риска:**

- `LOCAL` — приватный рендер/расчёт одного модуля, без изменения контракта: unit + пользовательский сценарий данного модуля.
- `SHARED` — публичный API, дизайн-токены, общий компонент, событие, master data: контрактные тесты + все реально зависящие модули + shell smoke.
- `CRITICAL` — Auth, company/project scope, permissions, Storage/RLS, миграции, Sync, service worker, module loader, session/cache, релиз: интеграционные и негативные тесты, проверка восстановления/совместимости, изолированная БД, независимый Тестер. **Никакого теста на production.**

## Повторное использование и внешние библиотеки

Сначала проверить `js/shared/`, `js/services/`, публичные UI-примитивы и общие библиотеки. Выбирать `REUSE → EXTEND → EXTRACT → NEW`, учитывая не только похожее название, но и семантику, tenant-scoping, лицензию и риски. Новая общая абстракция оправданна при реальном втором потребителе или подтверждённом обязательном контракте; гипотеза «потом понадобится» недостаточна.

Для заменяемой интеграции: **модуль → публичный сервис/адаптер → конкретная библиотека**. Не размножать прямые подключения к PDF/XLSX/AI/файловому хранилищу, если уже есть согласованный интерфейс. При этом не создавать PrintExportService/AI Gateway только ради архитектурной красоты до первого потребителя.

## Технический долг «по касанию» — ограниченное исключение

В исходном архиве `_ai/PLATFORM_TARGET_ARCHITECTURE.md` §40.9 разрешено устранять **очевидный локальный** долг в уже затронутой функции: убрать неиспользуемый код, воспользоваться готовым helper, исправить явную ошибку. В новом регламенте соблюдаются дополнительные ворота:

1. Исправление остаётся **в границах утверждённой задачи и разрешённых файлов**, не затрагивает API/SQL/Auth/Sync/SW и не меняет смысл бизнес-функции.
2. Если потребовался новый файл или изменение scope — согласовать дополнительное разрешение Архитектора/владельца задачи **до** правки.
3. Если исправление опаснее/крупнее самой задачи — зафиксировать техдолг с адресом и не исправлять «заодно».
4. Тестер проверяет и эту правку. Скрывать такие изменения в diff запрещено.

От старого `_ai/PROJECT_RULES.md` **не переносится** правило минимальных 40–60 строк или желание делать «весь модуль одним блоком». Новый подход — **один законченный независимо проверяемый вертикальный сценарий**, достаточно крупный для демонстрации и достаточно малый для безопасного тестирования.

## Тест «одна точка изменения»

Для изменения общей роли/настройки/темы/сервиса убедиться, что операция через **один авторитетный источник** изменяет поведение всех применимых подключённых потребителей, без правки их приватных таблиц/файлов. Для permission проверять сервер: новые роли/назначения/отзывы учитываются API/RLS/Storage, не только UI. Для темы — Shell и React-модуль; для master data — канонический ID и сохранность ссылок.

## Минимальный отчёт о регрессии

```md
Задача / commit: ...
Уровень воздействия: LOCAL / SHARED / CRITICAL
Затронутый владелец/контракт: ...
Подтверждённые потребители: ...
Тесты (PASS/FAIL/NOT RUN): ...
Соседние экраны/Shell: ...
Безопасность, иная компания, отзыв права (если применимо): ...
Известные ограничения/rollback: ...
```
