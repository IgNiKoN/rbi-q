# Platform 2.0 — единый источник истины для общих правил и сервисов

**Версия:** 1.0 · 20.10.2026  
**Статус:** утверждённый архитектурный принцип; точные имена API/таблиц определяются аудитом и отдельными задачами.  
**Цель:** изменение общего правила, выполняемое **в одном контролируемом месте**, должно отражаться во всех модулях через общий интерфейс без правки бизнес-кода в каждом приложении.

## 1. Что означает «менять в одном месте»

У каждой сквозной возможности есть **один ответственный владелец (source of truth)**, одна опубликованная модель и один разрешённый способ обращения к ней. Источником может быть сервис ядра, централизованная серверная таблица, системный реестр или версионированный публичный пакет. **Не обязательно один физический файл и не один гигантский класс.**

- **Правило/настройка** хранится и изменяется у своего владельца; бизнес-модули его не копируют.
- **Применение** выполняется через один публичный контракт; каждый интерфейс и серверная операция обращаются к нему вместо локальной альтернативы.
- **Изменение** проверяется тестами на всех реально подключённых потребителях, с учётом версий контрактов, RLS и кэша.
- **Область действия** явная: вся установка, компания, проект, конкретный ресурс либо пользователь. Настройка одной компании никогда не меняет другую.
- **Новые правила** нельзя добавлять в произвольных местах: сначала определить владельца и проверить уже имеющийся сервис.

**Не путать:** четыре AI-роли разработки (`ARCHITECT`, `EXECUTOR`, `TESTER`, `DOCUMENTER`) — инструкции для организации разработки; корпоративные роли сотрудников (ПТО, прораб, РП) — данные платформенной авторизации. Это разные модели.

## 2. Карта единственных владельцев

| Область | Единственный логический владелец | Как используют приложения | Границы текущего MVP |
| --- | --- | --- | --- |
| Учётная запись и вход | Supabase Auth + платформенный адаптер Identity/Auth | Текущая аутентифицированная личность и сессия | Переиспользовать Auth, не создавать собственные PIN/логин-механизмы для нового SaaS |
| Членство в компании и проекте | Платформенный Company/Project Membership | Разрешённый активный контекст, назначения | Только реальные необходимые членства и проекты |
| Роли, назначения и решение о праве | Платформенный Access/Permission Service + серверные политики | `can(action, resource)` для UX; серверный `authorize` для операций | Небольшой каталог действий и четыре стартовые роли, без конструктора |
| Каталог действий | Единый платформенный реестр, наполненный публичными объявлениями модулей | Устойчивые ключи действия, например `planfact.fact.create` | Только реально реализованные действия |
| Права использования модулей | Entitlement/License Service | Проверка разрешённости модуля/функции **на сервере** | Минимальные записи/проверки, не биллинг |
| Компании, проекты (объекты), локации, ЕИ, виды работ, контрагенты | **Ядро платформы** — схема `core` (P2-0015, ADR-066) + клиентский сервис `src/platform/core/` | Модули получают данные только через `src/platform/core/` (функции `pf_*` ядра); ссылки — по `id` ядра | План/Факт — потребитель; Качество — позже (P2-0016) |
| Тема, токены и UI-компоненты | Design System / Theme Service | Одинаковые семантические токены и общие компоненты | Нужные Plan/Fact примитивы, светлая/тёмная тема |
| Настройки и feature flags | Platform Configuration Service с типизированной схемой | Разрешённая вычисленная конфигурация | Только реально изменяемые параметры; без UI-конструктора |
| Регистрация модулей и навигация | Module Registry + Shell Navigation | Манифесты, версии, маршруты, доступность | Проверяемый минимальный контракт независимого модуля |
| Файлы и вложения | Защищённый File/Storage Service | Метаданные, приватные файлы, права чтения/записи | Только когда вложения реально нужны |
| Локаль, даты, форматирование | Общий Locale/Formatting контракт | Язык, часовой пояс, числовые форматы, единицы | Минимальный общий интерфейс по потребности |
| Аудит и системные ошибки | Общие Audit / Error контракты | Одинаковые метаданные действия, идентификаторы ошибок | Минимальный аудит доступа и изменений факта |
| Уведомления и интеграции | Будущие разрешённые платформенные интерфейсы | Вызываются при подтверждённом потребителе | Не разрабатывать заранее |
| Правила расчёта ВОР, плана и факта | **Модуль Plan/Fact**, не Platform Core | Версионированный публичный API и одна проверенная реализация расчёта | Формулы, единицы, сохранение, сводка |
| Правила дефектов/приёмки Quality | **Модуль Quality**, не Plan/Fact | Публичные результаты и канонические ID | Не переносить в MVP |

Таблица определяет **ответственность**, но **не утверждает**, что все перечисленные сервисы уже существуют или подлежат реализации сейчас. Названия интерфейсов условные. Существующий код анализируется до изменений.

## 3. Универсальный порядок реализации сквозной функции

1. **Найти готовое:** исходный код, существующие `*Service`, таблицы, CSS/UI, контракты.
2. **Определить владельца:** кто владеет данными и бизнес-правилом, где разрешено менять его значение.
3. **Проверить границы:** кто может управлять настройкой и где сервер должен независимо проверять её действие.
4. **Опубликовать минимальный API:** вход, выход, ошибки, область, версия и поведение при отключённом сервисе.
5. **Подключить потребителей:** модули получают значение через API, а не через продублированные constants/локальные таблицы.
6. **Проверить единое изменение:** изменить настройку/роль/тему в источнике и подтвердить одинаковое действие в применимых модулях без правки их кода.
7. **Документировать:** источник истины, контракт, миграцию, совместимость и тесты.

**Стандартизировать по необходимости:** при первой реальной функции — минимальный владелец и API; при втором потребителе — проверить переиспользуемость и обоснованно выделить общий контракт. Не создавать универсальную платформу всех сервисов до MVP.

## 4. Запреты и исключения

**Запрещено без отдельного ADR:**

- писать `if (role === 'foreman')`, `if (user.title === 'Прораб')` как проверку реального серверного права;
- дублировать одинаковые таблицы ролей/прав внутри Plan/Fact и Quality;
- хранить независимые списки доступных модулей, меню или фирменных цветов в каждом приложении;
- создавать второй каталог `project/location/work_type`, параллельную логику Auth или отдельный файловый сервис с обходом Storage/RLS;
- разрешать клиентскому флагу/настройке отменять серверную политику, договорное ограничение или RLS;
- делать `Core` зависимым от приватной реализации конкретного модуля, превращать ядро в монолит;
- объединять несвязанные доменные вычисления в один «универсальный калькулятор» без общей бизнес-семантики.

**Ядро (P2-0015):** модуль не хранит копий объектов, локаций, ЕИ и контрагентов и не вызывает функции сервера ядра в обход `src/platform/core/`. Проверка — `src/platform/core/__tests__/single-entry.test.ts` (список функций ядра — там же). Исключения на сейчас: виды работ ведёт ВОР (`pf_vor_*work_type*`), даты и пороги объекта — настройки сводки План/Факта (`pf_project_set_dates` / `_thresholds`).

Временное дублирование при миграции возможно **только** через явно описанный адаптер совместимости, тесты и срок/условие устранения. Если источник недоступен, новая клиентская копия не становится источником права.

## 5. Примеры эффекта

- Администратор меняет разрешения корпоративной роли в опубликованной настройке компании. Новые **серверные запросы** Plan/Fact и других модулей получают актуальное решение доступа по ключу действия. UI при обновлении контекста/прав отображает изменения; отзыв права нельзя обойти старым UI или API.
- Компания меняет тему на брендированную. Shell и подключённые React-модули читают новые семантические токены, а бизнес-код остаётся прежним.
- Организация переименовала корпус. Канонический `location_id` сохраняется; модули получают новое разрешённое имя через Master Data без отдельных копий дерева.

## 6. Проверяемый критерий

Общий механизм считается правильно централизованным, если изменение в одном источнике через разрешённую операцию отражается во всех **подключённых и совместимых** потребителях, не требует правки их внутренних реализаций, проходит тесты областей доступа и не нарушает чужие компании.
