# Platform 2.0 — технологический стек и границы архитектуры

**Версия:** 1.0 · 20.10.2026  
**Статус:** общий технологический ориентир. Отдельные утверждённые принципы — в [DECISIONS_2026-10-20.md](DECISIONS_2026-10-20.md). Конкретные версии и не подтверждённые механизмами кода решения — после P2-0001–P2-0003.

## 1. Архитектурная схема

```text
                    Platform 2.0 App Shell
         (legacy JS/ES Modules, общая навигация и UI)
                             |
           Версионированный Platform Module API
       (manifest, lifecycle, ctx, routes, permissions)
               /                |               \
        Plan/Fact СМР         Quality         Future ID...
          React/TS          JS/TS*           React/TS
       separate build       adapter*       separate build
               \                |               /
          Публичные сервисы и общие Master Data
                (company/project/location IDs)
                             |
                 Supabase / PostgreSQL
               Auth + RLS + private Storage
                + проверяемые server APIs
```

`*` — перенос существующего Quality и его точный адаптер являются **будущими задачами**, не частью первого MVP. Production RBI Platform остаётся нетронутой.

## 2. Базовый стек

| Слой | Стандарт и текущая основа | Правило |
| --- | --- | --- |
| Shell и навигация | JavaScript, ES Modules, существующая RBI Platform | Переиспользовать в отдельной копии; не переписывать целиком на React |
| Новые приложения | React + TypeScript | Plan/Fact — обязательно; новые приложения — целевой единый стандарт |
| Сборка | Vite (имеется в наследуемом проекте) | Независимые артефакты модулей; формат и runtime-loading проверить экспериментом |
| Модульные границы | Типизированный, версионированный Platform Module API | Только публичный `ctx`, manifest, `init/mount/unmount`, маршруты, совместимость |
| Данные | PostgreSQL / Supabase | В одном SaaS-контуре многие компании с изоляцией RLS; self-hosted для on-prem |
| Авторизация | Supabase Auth + серверные назначения и права | `company_id` в запросе не даёт права; одна схема правил для RLS/RPC/Storage |
| Файлы | Supabase Storage, приватные бакеты | С учётом компании, проекта, роли; подписанные ссылки по необходимости |
| Offline/PWA | Существующие PWA, Service Worker, IndexedDB | В MVP допускается online-only; офлайн позже с изоляцией пользователь/компания/проект |
| Общие компоненты | Существующие CSS-токены/классы, совместимые адаптеры | Версионированная дизайн-система, общая для Shell и React |
| Развёртывание | Linux + HTTPS; self-hosted Supabase | Отдельные конфигурации SaaS/on-prem; точный инструмент контейнеризации после аудита |
| Git/CI | Независимые приватные репозитории и проверяемые сборки | CI/gates, миграции, тесты, журнал версий, безопасная публикация |
| AI и интеграции | Публичные API, будущий AI Gateway | Не требуются для первого MVP; не связывать бизнес-логику с внешним AI |

## 3. Что не фиксируем без аудита

- Конкретные версии Node.js, React, Vite, TypeScript, PostgreSQL, Supabase и их поддерживаемую матрицу.
- Будет ли у модуля собственная собранная копия React или разделяемый runtime; выбрать по реальной независимости и тестам загрузчика.
- Точный формат динамической загрузки и публикации (`import()`, manifest URL, hosting, cache-busting) и стратегию отката.
- Физическую PostgreSQL-схему модулей (таблицы `pf_*` или отдельная schema), API Edge Functions/RPC и точные SQL-права.
- Инструмент CI (GitHub Actions, GitLab CI и др.), инструмент e2e и систему контейнерной поставки — выбираются под фактическую инфраструктуру.
- Будущий механизм дистрибуции UI-компонентов (общий versioned package или согласованная адаптация runtime CSS); **никаких импортов private paths**.

## 4. Правила эволюции стека

1. Новые модули пишем на TypeScript (типизация публичных контрактов обязательна); React — стандарт интерактивных бизнес-экранов.
2. Не вводим другие фронтенд-фреймворки и собственные глобальные хранилища состояний без конкретного обоснования; не делаем Next.js/NestJS/Kubernetes/Kafka обязательной частью продукта по умолчанию.
3. Всё, что может меняться у клиента, отделяем от бизнес-логики: branding/theme/configuration, разрешения, справочники и настройки UI. Эти области имеют **единых логических владельцев** и публичные контракты, а не дублируются настройками модулей.
4. Модуль работает, даже если другой необязательный модуль отключён; отдельные релизы и независимая установка обязательны как целевой контракт.
5. Приложения не хранят собственные копии общих `company_id/project_id/location_id`; запросы получают контекст через публичный API с серверной перепроверкой.
6. SaaS и on-prem используют общие версии исходников, миграций и модулей. On-prem не зависит от постоянной связи с серверами поставщика.
7. Адаптер к наследуемому JS-коду допускается, но он документирован и тестируем. Не создавать постоянную неявную зависимость от `window.*` в новом модуле.
8. Не мигрировать существующее приложение на иной стек только ради технологической унификации. Единые **контракты** важнее единого языка наследуемых файлов.

## 5. Минимальная приёмка стека до MVP

- В независимом окружении существует рабочий App Shell со своей конфигурацией, origin, базой и кэшами.
- React/TS Plan/Fact собирается отдельно, загружается и выгружается корректно, не требует правки исходников Quality.
- Версия модуля известна; несовместимая версия получает контролируемую ошибку, а не разрушает Shell.
- Базовые company/project-права проверяются сервером; отказано в попытке обратиться к чужим данным.
- Токены оформления/общие UI-примитивы доступны модулю и реально меняются при переключении темы.
- Установка, сборка, тесты и известные ограничения воспроизводимы и описаны в Markdown.

## 7. Сквозные правила стека

Auth — через Supabase Auth/общий Identity adapter; авторизация — единая платформа разрешений плюс RLS и серверные доменные проверки. Управление конфигурацией, темами и лицензиями имеет отдельные владельцы. **Формат конкретного сервиса/пакета определяется первым рабочим интеграционным тестом**, а не созданием заранее всех сервисов.
