# Platform 2.0 — общие платформенные сервисы, контракты и границы модулей

**Версия:** 1.0 · 20.10.2026  
**Статус:** единые инженерные правила; названия будущих интерфейсов/пакетов — предложения, не подтверждённый as-built.

## 1. Правило проектирования

**Общее правило — общий владелец, бизнес-специфика — у своего модуля.** Не создавать ни дубликаты между приложениями, ни единый огромный сервис с обязанностями всего продукта.

Для каждого сервиса определить:

- **Владельца** (платформа / конкретный модуль).
- **Данные**, единственный источник их изменения и границы компании/проекта.
- **Публичный API**, типы данных, ошибки, версию и тесты совместимости.
- **Безопасность**, авторизацию, аудит и конфигурацию.
- **План внедрения**: существующая реализация → безопасное повторное использование/адаптер → самостоятельный публичный контракт.

## 2. Карта общих контрактов (по потребности)

**Нужны как архитектурные основы первого MVP:**

- `Auth/Identity` — текущий пользователь и сессия без собственного входа каждого модуля.
- `Access/Permission` — серверное решение действия над ресурсом по ролям/назначениям/лицензии; UI получает разрешённые возможности, но не решает доступ.
- `Company/Project Context` — текущая компания-владелец проекта и стабильные ID.
- `Master Data / Location` — единое проектное дерево и корпоративные справочники, без второй модели объектов.
- `Module Registry/Loader` — версии и загрузка независимых приложений, route lifecycle.
- `Design System / Theme` — единые токены, базовые UI-примитивы и настройка темы.

**Добавлять только когда появляется потребитель:**

- `File/Storage` — общий защищённый доступ к вложениям, метаданным и версиям; Storage RLS всегда проверяется.
- `Audit/Activity` — единый формат событий и изменений, проверенный серверный журнал чувствительных операций.
- `Notifications` — события, каналы и настройки доставки, без отдельного пуш-сервиса на каждый модуль.
- `Localization/Formatting` — общий язык/даты/числа/единицы и словари компонентов.
- `Configuration/Feature Flags` — централизованная типизированная настройка/доступность функций.
- `Exports/Imports` — общие безопасные технические примитивы; **бизнес-правила сопоставления ВОР остаются в Plan/Fact**.
- `AI Gateway/Integrations` — будущие версионированные интерфейсы без обязательной зависимости первого MVP.

Существующие `ObjectService`, `LocationService`, `FileService`, `StorageService` и другие сервисы RBI Platform — кандидаты на повторное использование **только после аудита и проверки безопасности**. Это не обещание, что они уже удовлетворяют новой мультитенантной архитектуре.

## 3. Запрет на дублирующую системную логику

- В Plan/Fact нельзя создать `PlanFactAuthService` с собственной базой паролей или собственный `PlanFactRoles`, который независимо решает, кто прораб.
- В Quality нельзя хранить второй канонический `location_id` для того же помещения одной компании.
- В каждом React-модуле не должно быть собственных копий `Button`, `Modal`, общих тем, глобального меню и постоянной логики авторизации.
- Разрешён **адаптер** к публичному контракту для особого UI, но он не владеет дублирующей бизнес-моделью и не подменяет серверные проверки.
- Общий вызов модуля не может напрямую изменять приватные таблицы другого модуля. Отношения идут по каноническим ID и разрешённым API/событиям.

## 4. Нельзя ошибочно централизовать всё

- `pf_*`: ВОР, планы, факты, распределения, графики и их формулы — единственный владелец **Plan/Fact**.
- Проверки качества, дефекты, эталоны и их жизненный цикл — **Quality**.
- Гарантийные обращения и их статусы — **Warranty**.
- Все эти модули **пользуются общей авторизацией**, но их бизнес-операции отдельно проверяют собственные состояния, данные и условия.
- Будущий общий отчёт получает разрешённые данные через контракты; не создаёт вторую «главную» копию всех таблиц.

## 5. Как избежать преждевременной универсализации

**MVP:** один реальный безопасный путь аутентификации/доступа, минимальные роли и назначения, канонический проект/локации, контракт модуля и используемые UI-токены. Не создавать заранее `NotificationsService`, полный `LocaleService`, AI Gateway, каталог всех возможных настроек и универсальный документный движок, пока нет конкретного потребителя.

**После MVP:** когда появляется второе приложение или новый сценарий, сначала проверять готовый публичный API. Если его недостаточно — расширять по совместимому контракту; физическая форма общих пакетов, схема таблиц и способы runtime-обновления определяются по фактическому коду и тестам.

## 6. Проверка в карточке разработки

Для сквозного изменения Архитектор должен ответить:

1. Где **единственный источник** данных/правила?
2. Кто владелец сервиса и кто вправе его менять?
3. Какие модули используют его через публичный контракт?
4. Потребуется ли правка каждого модуля при смене значения? Если да — почему не применён общий API?
5. Как подтверждён серверный контроль доступа и запрет другим tenants?
6. Как проверены независимые версии и регрессия?
7. Можно ли получить нужный результат простым расширением существующего сервиса без создания нового?
