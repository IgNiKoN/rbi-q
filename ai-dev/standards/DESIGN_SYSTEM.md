# Platform 2.0 — единая дизайн-система, токены, темы и white-label

> **20.10.2026: дизайн-система опубликована в Claude (тип Design System) — «Platform 2.0»: https://claude.ai/artifact/Bs4civLNjGjHhixGy2HRWW.** Модель: база Platform 2.0 (семантические токены `bg-*`, `text-*`, `border-*`, `action-*`, `status-*`, `pf-*`) + бренд-пак компании (`brand-*`, RBI — первый). Значения взяты из тем `rbi-light-v3`/`rbi-dark-v3`. При расхождении с этим файлом по токенам — главнее опубликованная система; правила и процесс — этот файл.

**Версия:** 1.0 · 20.10.2026  
**Статус:** принятые продуктовые требования + ограниченный проект технического контракта. **Это не утверждение, что все описанные компоненты уже существуют.**  
**Цель:** единое оформление всех приложений, переиспользование UI, быстрое создание тем и изменение внешнего вида **без переписывания бизнес-модулей**.

## 1. Принятые инварианты

1. **Одна дизайн-система — все модули.** Shell, Plan/Fact и будущие Quality, ИД, Warranty используют общий набор токенов, компонентов и UX-паттернов.
2. **Reuse-first.** Новый компонент сначала ищет существующий UI-примитив. Не создавать новую кнопку/таблицу/модальное окно ради отдельного экрана.
3. **Тема отделена от логики.** Цвет, типографика, радиусы, отступы, плотность, иконография, логотип и оформление оболочки задаются семантическими токенами/конфигурацией.
4. **Темы применяются ко всем модулям.** React-модуль должен наследовать токены оболочки. Не использовать внутри модуля жёсткий собственный бренд.
5. **Единый владелец темы.** Theme Service / общий Design System управляет токенами; Configuration Service хранит разрешённый выбор темы. Модуль не ведёт отдельную тему по собственной таблице. Подробности — [PLATFORM_CONFIGURATION.md](PLATFORM_CONFIGURATION.md) и [SINGLE_SOURCE_OF_TRUTH.md](SINGLE_SOURCE_OF_TRUTH.md).
6. **Единые состояния.** `hover`, `focus`, `active`, `disabled`, `loading`, `error`, `success`, `selected`, `read-only`, `empty` имеют согласованное поведение и визуальные признаки.
7. **Доступность и адаптивность.** Цвет не является единственным индикатором статуса; все основные операции доступны с клавиатуры и поддерживают видимый фокус.
8. **Безопасная настройка.** Изменение корпоративного оформления не может запускать произвольный JS/CSS, отключать контролируемые ограничения или влиять на бизнес-данные.
9. **Постепенная миграция.** Не переписывать UI старой RBI Platform целиком до MVP; переносить проверенные решения по мере работы с конкретным экраном.

## 3. Слои токенов — целевой контракт (предлагаемые имена)

Токены должны иметь **смысл**, а не название конкретного цвета или клиента. Для нового публичного интерфейса предлагается нейтральное пространство имён `--p2-*` (название является техническим, не коммерческим брендом).

### A. Foundation / базовые значения

Не являются публичным API модулей: палитра, шкала пространства, размеры шрифта, базовые радиусы, durations, elevation. Например `neutral-100`, `space-2`, `radius-md`. **Новым модулям не следует выбирать фирменные значения напрямую из палитры.**

### B. Semantic / публичные токены

Примеры **предлагаемого**, ещё не реализованного словаря:

```css
/* Пример структуры контракта; не готовый файл для production */
--p2-color-bg-canvas
--p2-color-bg-surface
--p2-color-bg-elevated
--p2-color-text-primary
--p2-color-text-secondary
--p2-color-text-inverse
--p2-color-border-default
--p2-color-border-focus
--p2-color-action-primary-bg
--p2-color-action-primary-text
--p2-color-action-primary-hover
--p2-color-status-success
--p2-color-status-warning
--p2-color-status-danger
--p2-color-focus-ring
--p2-font-family-body
--p2-font-size-body
--p2-font-size-caption
--p2-space-2
--p2-space-3
--p2-space-4
--p2-radius-sm
--p2-radius-md
--p2-radius-lg
--p2-shadow-card
--p2-motion-fast
--p2-control-height
```

Контракт должен включать и производственные состояния Plan/Fact (выполнено, в срок, риск отставания, отставание), **но семантика статуса задаётся бизнес-логикой, а цвет — темой**. Не кодировать правило «отставание = #...», а использовать статус + предназначенный токен, текстовый label и, при необходимости, иконку.

### C. Component / токены компонента

Специфичные параметры `Button`, `Input`, `Modal`, `Table`, `Badge`, `Tabs`, `Navigation`, `Card`, `Chart`, `Toast` ссылаются на semantic tokens, а не на брендовые RGB-значения. Если новая тема меняет плотность и радиусы, компоненты наследуют их автоматически.

### D. Product / модульные визуализации

Модуль может добавлять **только семантические** токены своего домена: например, серии на графике или фон конкретного состояния производственной сводки. Сначала проверяем, нет ли такого значения в общем каталоге. Значение должно иметь светлую и тёмную реализацию, достаточную различимость, документацию и fallback.

## 4. Переход от существующих `--rbi-*` и `--primary` к нейтральной системе

**Фаза 1 — до первого MVP:** сохранить проверенные старые токены и общие классы. Добавить **односторонний мост для нового UI**: новые `--p2-*` читают существующие значения там, где это корректно. Пример:

```css
/* Переходный пример, применяемый только после проверки каскада и тем */
:root {
  --p2-color-bg-canvas: var(--bg-main);
  --p2-color-bg-surface: var(--card-bg);
  --p2-color-text-primary: var(--text-main);
  --p2-color-text-secondary: var(--text-muted);
  --p2-color-border-default: var(--card-border);
  --p2-color-action-primary-bg: var(--primary);
  --p2-font-family-body: var(--rbi-font-sans);
  --p2-radius-md: var(--rbi-radius-md);
}
```

**Фаза 2 — после подтверждения схемы:** новые нейтральные токены становятся источником истины, а старые имена при необходимости становятся адаптерами к ним. **Нельзя оставлять обратные алиасы в обе стороны** (`--p2-x: var(--legacy-x)` и `--legacy-x: var(--p2-x)` одновременно): это создаёт циклические переменные CSS. Мигрировать малыми проверяемыми пакетами.

**Фаза 3 — по спросу:** убрать зависимость новых модулей от исторических `rbi-*` и локальных фиксаций дизайна. Старый production не менять.

## 5. Темизация: что можно быстро менять

### Требуемые возможности

- Светлая/тёмная тема + системный автоматический режим.
- Новая **фирменная тема инсталляции/компании**: палитра, контраст, логотип, шрифт из разрешённого набора, радиусы, тени, параметры оболочки.
- Плотность интерфейса (например, комфортная/компактная) — целевая возможность через единые токены, полезна для таблиц ВОР; в MVP не обязательна вся панель настроек.
- Общий выбор темы для shell и всех подключённых модулей, предсказуемое применение без перезагрузки там, где это технически подтверждено.
- Версионные темы с fallback: неполная/ошибочная настройка не должна делать приложение нечитаемым.

### Порядок разрешения настроек (предлагаемый)

1. Безопасные системные default tokens.
2. Опубликованная тема установки/компании (разрешённые брендовые поля).
3. Выбранный светлый/тёмный режим (личное предпочтение в разрешённых компанией пределах).
4. Пользовательские параметры доступности (например, reduced motion, масштабирование браузера), которые не должны блокироваться брендом.

Каждая компания видит только свою тему в **своём контексте**; при переключении контекста тема пересчитывается, без утечки корпоративных настроек и без доступа к чужому branding API. Правила выбора темы должны быть одним общим сервисом; клиентские значения являются настройками отображения, а не механизмом авторизации.

### Границы настройки

Настраиваемые темы ≠ генератор произвольных экранов. Изменение цвета, шрифта, формы кнопки и визуальной плотности должно происходить через тему. Новая навигационная структура, процесс согласования или бизнес-экран — отдельная задача с тестированием. Не строить до MVP универсальный визуальный UI-конструктор, CSS/JS-редактор для клиента или отдельный marketplace тем.

## 6. Контракт компонентов и React/JS-совместимость

- UI-контракт состоит из **общих CSS-токенов и публичного API примитивов**; React-обёртки — тонкие и независимые от внутреннего глобального состояния shell.
- Общие примитивы обязаны одинаково понимать `disabled`, `loading`, `readOnly`, ошибки, варианты размера и статусы, если они предусмотрены компонентом.
- UI-компоненты не должны вызывать бизнес-API напрямую, принимать финансовые решения или менять `company_id`.
- Все новые классы/селекторы модулей — в локальной области `planfact`/корня модуля; темы и общие токены остаются управляемыми shell. Избегать неограниченных глобальных CSS-правил.
- Для модальных окон, выпадающих меню и порталов нужно проверить наследование темы от их реального DOM-контейнера. Портал вне тематического контейнера может потерять токены — учесть в адаптере.
- Пакет общих React-компонентов — разумное направление **после реального повторного использования**. В MVP допустимы простые wrapper-компоненты над утверждёнными CSS-классами; нельзя копировать одну и ту же компонентную реализацию между репозиториями.
- Версии UI-контракта и правила миграции должны позволять обновлять Plan/Fact без обязательного обновления другого бизнес-модуля.

## 7. Доступность, UX и проверка тем

**Минимальные принципы:** видимый фокус, логичная клавиатурная навигация, семантика кнопок/полей/таблиц, label ошибок, не только цветовая маркировка, корректная обработка loading/empty/error, достаточная контрастность. Целевой ориентир — WCAG 2.2 AA для нового UI (проверяем применимые критерии; не заявляем сертификацию всего legacy интерфейса).

При изменениях компонентов Тестер проверяет:

1. Светлую и тёмную темы и переключение без пропажи текста/иконок/контрастов.
2. Клавиатурный фокус, disabled/loading/error, сообщение о результатах и недоступном API.
3. Ширины для мобильного и настольного экрана, прежде всего формы и таблицы ВОР.
4. Корректное наследование темы у модальных окон, popover, chart и встроенного React-модуля.
5. Отсутствие видимого влияния нового CSS на существующие экраны shell/других модулей.
6. Статусы Plan/Fact в разных темах: одинаковый смысл, понятный текст и индикатор, отсутствие зависимости от одного цвета.

Снимки экранов и визуальная регрессия полезны по мере расширения компонентной библиотеки, но не превращаются в отдельный большой проект до MVP.

## 8. Ограниченный состав работ для первого MVP

**Сделать при первом фактическом UI-сценарии:**

- Проинвентаризировать существующие темы/переменные и кнопки/карточки, проверить загрузку CSS.
- Подтвердить небольшой нейтральный набор публичных семантических токенов или совместимых алиасов.
- Использовать/адаптировать кнопки, поля, таблицу ВОР, статусы и диалоги, реально нужные Plan/Fact.
- Проверить светлый/тёмный режим на этих экранах; оставить резерв для брендирования без переработки данных/логики.
- Задокументировать карту токенов и компонентный API, изменённые файлы и тесты.

**Не делать ради первого показа:** весь каталог UI, брендовый редактор, конструктор дизайн-токенов, полную стандартизацию существующего Quality, десятки тем, перестраиваемое без кода рабочее место или мощную систему visual regression.

## 9. Контрольная приёмка одного нового компонента

- У компонента один владелец и публичный контракт; reuse-review выполнен.
- Цвета, размеры, радиусы и типографика берутся из общих токенов.
- Поддержаны относящиеся к нему состояния и доступность; проверены темы.
- Реальный React/JS пользователь получает одинаковую семантику действия.
- Не добавлен приватный импорт из соседнего модуля или глобальный стиль, ломающий shell.
- Проверки проведены и описаны, а ограничение/компромисс зафиксировано.
