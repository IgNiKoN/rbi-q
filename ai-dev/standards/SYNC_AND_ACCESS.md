# Стандарт синхронизации и прав на устройстве

**Статус:** действующий с P2-0061 (29.10.2026; решение владельца: «сделать нормальный механизм синхронизации и прав, чтобы потом по всему коду не искать, а сделать стандарты; добавлять модули к механизму; использовать id»). Разделы «Описание вида записи», «Как подключить модуль» и «Где в коде» — по факту кода P2-0061. **P2-0070 (30.10.2026, «Общий механизм + СК первым»):** раздел «Права на сервере» — один механизм прав платформы (ядро `core.*`, миграция 052) и как модуль к нему подключается; режим `area` правила устройства.
**Опирается на:** `reference/MODULES.md` (сервис «Офлайн и синхронизация», решение 7.9; фундамент, правило 1 «Устойчивые ID»), `standards/AUTH_AND_ACCESS.md` («права проверяет сервер, не по названию роли»; «Качество узнаёт человека по номеру учётки»), `reference/GLOSSARY.md`.

## Правила

1. **Сервер — окончательный судья.** Устройство решает заранее только для того, чтобы не слать заведомо отклоняемое и **показать причину**. Права на сервере (RLS, `quality.row_visible*`) этим стандартом не ослабляются.
2. **Правило устройства = правило сервера.** Решение «моё / можно отправить / видно» на устройстве повторяет серверное для той же таблицы. Совпадение проверяется **зеркальным тестом**: одни и те же случаи — серверной функции (PGlite) и правилу устройства → одинаковые ответы.
3. **Кто — по id.** Автор записи — id учётной записи (`authorId` на устройстве ↔ на сервере `created_by` в новых таблицах, `core_created_by` — мост в таблицах Качества; сервер ставит его сам; `standards/DATA_TABLES.md` правило 4). Объект — id объекта ядра, место — id места, фирма — id контрагента. ФИО и названия — **только подпись** на экране и в документах.
4. **Права — по действиям и области, не по названию роли.** Устройство берёт с сервера список действий (`quality.edit`, `construction.edit`, `quality.scope.contractor` …) и область (объекты, фирма, вся компания) — `my_access`, участие в проекте. Название роли («Инженер СК», «Руководитель») в решениях синхронизации не участвует; переименование роли или своя роль компании работают без правки кода.
5. **Модуль подключается описанием, а не своим кодом.** Модуль перечисляет свои виды записей в манифесте (поле `sync`, рядом с `offline` из P2-0060). Общий движок и общее правило делают остальное: отбор «моё», проверку перед отправкой, причину, порядок «своё первым», отбор при скачивании, счётчик «не отправлено», список в «Данные на устройстве → Отправка».
6. **Ничего не молчит.** Каждая неотправленная запись имеет понятную причину и подсказку «что делать». Запись, отсеянная на устройстве, получает статус «Не отправлено» (`blocked`) с причиной — видно в Истории модуля и в «Данные на устройстве → Отправка». Отклонённая сервером — «Сервер отклонил: …».
7. **Переходное правило для старых записей.** Запись без `authorId` считается моей, если её ФИО совпадает с моим **текущим или прежним** ФИО (устройство запоминает прежнее ФИО при смене, по «компания + пользователь»). При первой проверке такой записи устройство дописывает ей мой `authorId`. Не совпало — «Не отправлено: запись другого сотрудника (ФИО)»; отправит руководитель (право на чужие записи по серверу) или сам автор, войдя на этом телефоне.
8. **Повтор, а не тупик.** Записи «Не отправлено» и «Сервер отклонил» перепроверяются при каждой синхронизации, если с прошлой попытки изменился мой доступ (действия, объекты, фирма), и по кнопке «Отправить снова». Повтор не создаёт дубль (id записи создаётся на устройстве).
9. **Одно место для каждого решения.** Списки хранилищ, правило «моё», причины — по одному в коде. Новый вид записи — одна строка описания, без правки движка, экрана «Отправка» и счётчика.
10. **Загрузка — только изменения (P2-0078).** Таблица, которую проход синхронизации читает, грузит «изменено после своей метки − 15 мин» (`sync-pull.policy` `tablePullSince` / `tablePullDone`: метка ставится после записи строк на устройство, сбой таблицы её не сдвигает; полный проход — вход, смена прав, объектов, роли — целиком). Новую таблицу целиком каждый проход не читать.

| `objectType` / `memory` | вид для общей отправки «объектов» (`pushCloudObject`) и массив в памяти — тогда движок отправляет его по описанию | совещание — `meeting` / `rbi_meetingsData` |

### Вид, который уходит функцией сервера (P2-0064)

Модуль, у которого ввод на сервере — функция (не строка таблицы), описывает вид полем `rpc` (план/факт: `{ kind: 'pf_fact', store: 'device_records', rpc: 'pf_fact_submit', title: 'Факт' }`). Такая запись живёт в **базе записей устройства** сервиса платформы (`src/platform/services/offline/device-records.ts`, своя база IndexedDB `platform2_device_records`, под «компания + пользователь») — она есть в любой компании, и без Качества (база Качества и его движок есть только у компаний с Качеством / Стройконтролем). Отправка — общая отправка сервиса (`send.ts`, браузер — `device-send.ts`): функция вызывается с `p_client_id` (id записи с телефона) и `p_entry` (что внёс человек); повтор с тем же id — прежний ответ, дубля нет (сервер хранит принятые номера). Правила те же: один проход на все вкладки (замок `p2-device-records`), по порядку создания, ограничение времени, обрыв — повтор с паузой 30 с → 5 мин, отказ — «Сервер отклонил: причина» (сама не уходит до «Отправить снова»), модуль выключен у компании — «Не отправлено: …» (перепроверяется каждый проход), журнал синхронизации, счётчик и «Отправка». Права и область проверяет функция сервера; правило устройства для такого вида — только «вошёл» и «модуль включён» (зеркала нет: решение — на сервере). Со связью запись тоже сначала кладётся на телефон и сразу уходит; отказ сразу — запись удаляется с телефона, экран показывает причину.

## Правило устройства — что решает и как

- `meFrom` / `deviceMe` — «кто я»: id учётной записи, ФИО (текущее, прежние — мост запоминает при смене), почта, действия и закреплённые объекты из `quality.my_access`, фирма по id, модули компании. Нет входа почтой — `null`: ничего не уходит, причина «нужно войти».
- `isMine` — я автор (по `authorId`; без id — переходное правило по подписи: текущее / прежнее ФИО, почта; id главнее подписи) или исполнитель. Исполнитель автором не становится (`stampAuthor` — только по авторству).
- Пока права с сервера не пришли (пустые действия), записи не помечаются и скачанное не отбирается — решение на следующем проходе.
- `stampAuthor` — моей записи без id и новой записи без подписи дописывает мой id (при сохранении и перед отправкой).
- `canSend` (отправка) и `visible` (видно) — порядок проверок как `quality.record_visible` / `assignment_sees_id` (039a) и `row_visible_id` (043): модуль включён → действие есть → объект (если права модуля по объектам) → вся компания / управление → своя фирма (подрядчик) → только автор (режим `author`). Ответ — `{ ok, code, reason, hint }`; причины — «Не отправлено: …» с подсказкой «что делать».
- `canChange` — «изменить / удалить» на экране: можно отправить **и** запись моя (или я управляю модулем / вся компания). Строже сервера для режимов `contractor` и `shared`: чужое меняет руководитель (как было на экранах).
- `keepPulled` — отбор после скачивания: видно по правилу; «Только мои» сужает того, кто правит только своё (инженер), по id.
- `accessStamp` — отпечаток доступа: «Не отправлено» и «Сервер отклонил» перепроверяются, когда он изменился, или по «Отправить снова».
- **Режим `area` (P2-0070)** — участие модуля `me.areas[модуль]` с сервера (`core.my_grants`: Стройконтроль — `quality.my_access → construction.grants`, План/Факт — `pf_my_area → grants`): по каждому участию — проект, место и всё под ним, действия роли (на часть проекта — только `area_scoped`), фирма. `canAct(запись, вид, я, действие)` — одна кнопка («Закрыть», «В работу», «Записаться»); `canSend` — любое действие правки. Порядок как `core.assignment_allows`: «вся компания» → проект → место (запись без места участник части проекта только видит, и только свою) → управление модулем → своя фирма. Сервер без 052 (участия нет) — одно участие на компанию из прежних ключей (`fineFromLegacy`), решает сервер.

## Как подключить модуль

1. В манифесте модуля — поле `sync` с видами записей (таблица выше). Этого достаточно, чтобы вид появился в счётчике «не отправлено», в «Данные на устройстве → Отправка», в правиле отправки и отбора и (с `objectType`) в общей отправке «объектов». Движок, `RECORD_STORES` и экран не правятся (стенд `s-new-kind`).
2. При создании записи — `authorId` ставит `stampAuthor` (осмотры — `inspection.service.save`), ФИО — подписью. При скачивании `core_created_by` сохраняется как `authorId`.
3. Кнопки «изменить / удалить» — `permissions.canEdit(запись, вид)` / `permissions.canDelete(запись, вид)`; старая подпись `canDelete(ФИО, id)` совместима.
4. На сервере у таблицы — политика по разделу «Права на сервере» (`core.row_allowed`; Качество до своего блока — `quality.record_visible` / `row_visible_id` / `quality.can`) и строка в зеркальном тесте `tests/server/sync-access.mirror.mjs` (`TABLES`). Своей функции прав в модуле нет.
5. Проверка: `node --test js/shared/__tests__/sync-access.policy.test.js`; зеркало `P2_PGLITE=<папка> node tests/server/sync-access.mirror.mjs` (FAIL 0); стенд `tests/offline` — «моя запись уходит 1 раз», «чужая — видна причина», «смена ФИО — уходит 1 раз» (`s-rename`, `s-foreign`, `s-kinds`).

## Права на сервере (P2-0070) — один механизм для всех модулей

Одна проверка «может ли человек действие на этом месте» — в ядре (миграция 052); модуль подключается **данными и описанием**, своей функции или таблицы прав у модуля нет. Подключены Стройконтроль 2.0, План/Факт (052) и **Качество (P2-0071, 053)** — образец модуля, у которого запись живёт на уровне объекта, есть «своя» запись и общая библиотека.

**Что есть в ядре**

| Что | Где | Зачем |
|---|---|---|
| Действия | `core.permission_catalog`: `action`, `description`, `module` (код модуля; `null` — ядро «Компания»), `group_name`, `sort`, `label` (короткая подпись — галочка и текст отказа), `area_scoped` (действует при участии на часть проекта) | экран «Роли и права» строит группы из каталога (`action-groups.ts`) — новое действие появляется без кода; роли — `core.company_role_permissions` |
| Участие | `core.role_assignments`: компания / проект / место (`location_id` — узел дерева и всё под ним) / фирма (`counterparty_id`) / срок / отзыв | «где» человек может |
| Область | `core.my_area(проект)`, `core.my_area_nodes`, `core.in_area(место, область)` | списки и фильтры «моя область» (План/Факт, перенесено из `planfact.my_area`) |
| Проверка | `core.has_grant(компания, проект, место, действие)` — назначения дают действие; `core.can_at(…)` — то же и модуль действия включён у компании. Проект `null` — только назначения на всю компанию; место `null` — где-то в проекте | функции модуля («можно ли» в RPC) |
| Правило строк | `core.row_allowed(компания, проект, место, действия[], автор, фирма)` — одно из действий над записью: «вся компания» (`quality.scope.company`) → проект → место (без места — только своё, только просмотр у участника части) → `<модуль>.manage` → своя фирма (`quality.scope.contractor`) | RLS таблиц модуля (клиенту доступна только она и `in_area`, ТД №104) |
| Отказ | `core.require_action(…, действие, …)` — 42501 «Нет права «<label>» на объекте «<проект>»» | сторож действий модуля |
| Для телефона | `core.my_grants(компания, проект, модуль)` — участие × действия модуля | «кто я» модуля → режим `area` правила устройства |
| Экран | `pf_who_can(компания, проект, место)` — люди × действия включённых модулей; `pf_permission_catalog` — каталог с группами | «Компания → Сотрудники и доступ» |
| Запись без места (053) | `core.permission_catalog.unplaced`: что участник **части** проекта может с записью без места — `all` (видит все), `own` (только своя); пусто — только видит свою (052) | Качество: записи на уровне объекта — участник секции видит весь объект, правит своё (решение владельца) |
| «Без объектов» (053) | назначение на проект-контейнер Качества (`core.projects.quality_container`): записей объектов нет, общие разделы (база знаний, ИИ, справочники) — по действиям роли | мастер назначения: «Все объекты / Выбранные объекты / Без объектов»; `pf_quality_container` |

**Как подключить модуль (новый или Качество)**

1. **Действия** — строки `core.permission_catalog` в миграции модуля: `module`, `group_name`, `sort` (свой диапазон: План/Факт 1000, Качество 2000, Стройконтроль 3000, ядро 9000), `label`, `area_scoped`. Роли получают новые действия **по прежним** (перенос в той же миграции; прежние ключи не удаляются) — таблица «до = после» по каждому пользователю тестовой базы (образец — `tests/server/052_rights_mechanism.seed.pglite.sql` + `_compare.check.sql`).
2. **Место записи — по id ядра:** `core_project_id`, `core_location_id uuid references core.locations` (новая таблица — `project_id`, `location_id` по `DATA_TABLES.md`); ставит сервер (триггер), неоднозначно — пусто, не угадывать.
3. **Правило строк:** `select` — `core.row_allowed(…, '{<модуль>.<запись>.view}', …)` (в Качестве с P2-0078 — права один раз на запрос: `(select quality.area_scope(…))` + `quality.area_ok(…)`, без security definer на строке — сторож `test:schema`; для ядра и План/Факта — ТД 426); `insert / update / delete` — любое действие правки записи (какое именно — решает сторож). В таблицах Качества — дополнительно `core_company_id = quality.request_company()`.
4. **Сторож действий** (BEFORE-триггер, последним): по разнице полей → нужное действие (создать, статус → своё действие перехода, исполнитель и срок, пометка удаления) → `core.require_action`. Только запросы клиента (роль `authenticated` / `anon`); сервер, миграции и администратор платформы — без сторожа. Образец — `quality.construction_action_guard` (052).
5. **Телефон:** в манифесте `sync` — `mode: 'area'`, `place`, `view` / `edit` (действия каталога); участие — `core.my_grants` в «кто я» модуля; кнопки — `canAct` (Стройконтроль — `src/modules/construction-v2/rights.ts`). Строка в зеркальном тесте (`sync-access.mirror.mjs`).
**Модуль с «своей» записью (Качество, 053):** правило строк модуля — обёртка над ядром (`quality.rec_ok`): одно из действий «видеть все / любое действие правки» в области **или** своя запись (автор / исполнитель) — по действиям «своих» (`own`); запись без объекта — только назначенные на всю компанию и автор (проект-заглушка `quality.no_object`); сторож (`quality.quality_rights_guard`, с правами вызывающего — функции сервера проходят без него): своё — «Создание» / «Выполнение», чужое — «Редактирование чужих», удаление — «Удаление» (+ «Редактирование чужих» у чужой). Подписи галочек — единые: Просмотр / Просмотр всех / Создание / Выполнение / Редактирование / Редактирование чужих / Удаление / Загрузка; отказ — «Нет права «<группа>: <действие>» на объекте «…»». Библиотека компании (эталоны, практики, документы …) — общая: право есть — видно независимо от объекта записи. Описание `sync` такого вида: `mode: 'area'`, `noObject: true`, `view` / `edit`, `own: { view, edit, change, remove, acts }`, `editAny`.

6. **Проверки:** PGlite — сценарии модуля (видит / не видит по участию, отказ с текстом, подрядчик, изоляция: чужая компания, модуль выключен), «до = после» с отрицательным контролем, откат — отпечаток схемы; зеркало FAIL 0; `test:schema`.

**Доступ к модулю (053):** в «Роли и права» у модуля — переключатель: выключен — у роли нет действий модуля, модуля нет в меню (`pf_my_platform` отдаёт модуль, только если роль даёт его действие). Индивидуальных галочек у человека нет: роль — «что», назначение — «где».

**Переходное (ТД):** План/Факт складывает область всех своих ролей (`has_permission` ∧ `my_area`), ядро и телефон — по каждому участию отдельно; расхождение — только у человека с ролью без действия на весь объект и ролью с действием на часть (сервер разрешает шире, телефон лишнего не шлёт). `planfact.my_area / in_area / has_permission` — обёртки над ядром на переходный срок.
