# Platform 2.0 — единые инженерные стандарты и повторное использование

**Версия:** 1.0 · 20.10.2026  
**Статус:** обязательные принципы разработки, развитие по мере появления реального кода. **Не основание для массового рефакторинга наследуемой RBI Platform до MVP.**

## 1. Правило reuse-first (до написания новой функции)

Архитектор и Исполнитель обязаны провести короткий `reuse review`:

1. **Найти:** есть ли аналогичный сервис, хелпер, алгоритм, UI-примитив или API в новой копии исходного кода, общем слое либо утверждённом модуле.
2. **Проверить:** контракт, владельца, побочные эффекты, безопасность, область компании/проекта, зависимости, тесты, совместимость и технический долг.
3. **Выбрать:** `REUSE` (готовый интерфейс) → `EXTEND` (совместимое расширение) → `EXTRACT` (выделить общий интерфейс при повторном использовании) → `NEW` (новая реализация с причиной).
4. **Записать в задаче:** выбранный путь, путь найденного компонента/контракта, основание отказа от готового решения (если отказ есть).

**Не означает:** любой legacy-сервис безопасен. Повторное использование не оправдывает переноса слабой авторизации, жёсткого `companyId: 'rbi'`, неконтролируемой записи в чужие таблицы или широкой политики RLS.

## 2. Единая ответственность за общие функции

Обязателен принцип **одного источника истины**: для каждой общей настройки/роли/правила/справочника указать логического владельца, место изменения и опубликованный API. Изменение не должно требовать правок во всех приложениях. [Правила централизованного владения](SINGLE_SOURCE_OF_TRUTH.md), [Auth и права](AUTH_AND_ACCESS.md), [Конфигурация](PLATFORM_CONFIGURATION.md).

- **Shell/Core:** навигация, регистрация и загрузка модулей, контекст активной компании/проекта, публичные сервисы пользователя/прав/настроек.
- **Master Data:** канонические проекты, локации, общие справочники видов работ/единиц и необходимые публичные методы. Один `location_id` на один узел внутри tenant.
- **Общий UI:** токены, тема, доступные публичные визуальные примитивы и стандарты взаимодействия.
- **Модуль Plan/Fact:** позиции ВОР, распределение объёмов, версии планов, факты, вычисления и сводки.
- **Другие бизнес-модули:** собственные доменные сущности; общие данные только по каноническим ID и публичным контрактам.

**Запрещено:** копировать алгоритм расчёта процента готовности в разные части продукта с разными правилами; дублировать permissions, деревья проектов, компании или компоненты UI под новым названием без причины.

## 3. Публичные контракты и версии

- Новая общая функция получает **владельца**, входы/выходы, описание ошибок, область авторизации и минимальный тест.
- Межмодульные API типизированы (где используются TypeScript) и версионируются; нельзя импортировать приватные файлы соседнего репозитория через относительные пути.
- Общие пакеты/компоненты публикуются как стабильные артефакты или разрешённые публичные интерфейсы, а не копируются вручную в каждый репозиторий.
- Ломающая модификация контракта требует плана перехода и совместимости; запрет тихих изменений поведения существующего клиента.
- Бизнес-события и frontend EventBus не заменяют серверную авторизацию или гарантированную доставку. Сложную event-инфраструктуру делать по необходимости.

## 4. Стандарты для TypeScript/React и JS-оболочки

- Новый TypeScript: строгая типизация (`strict`, если подтверждена конфигурация проекта), отсутствие бесконтрольного `any`, явные публичные типы; ошибки сети и валидации обрабатываются явно.
- React-модули не должны изменять глобальное состояние shell, объявлять глобальные имена или строить свой экземпляр навигации/авторизации.
- Один источник истины для расчёта: чистые тестируемые доменные функции; бизнес-проверки дублем защищаются сервером там, где это требуется.
- Общий Shell может оставаться на JavaScript. Новый слой адаптации имеет узкую типизированную поверхность для TypeScript-модулей.
- В новых компонентах запрещены прямое копирование чужого HTML/CSS без оформления общего паттерна, произвольные inline-фирменные цвета и `!important` как стандартный способ решения конфликтов.
- Не вводить зависимость (UI toolkit, state manager, charts, dates, forms) автоматически. Сначала сверить имеющиеся инструменты и потребность; зафиксировать версию, лицензию и причину новой зависимости.

## 5. Единые договорённости по данным и безопасности

- `company_id`/`project_id`/`location_id` — стабильные идентификаторы; интерфейс их передаёт, но **не является источником права**.
- На сервере: единые аутентификация, корпоративные назначения/роли/лицензии, реестр действий и смысл проверки доступа; RLS, приватный Storage, контролируемые RPC/views и аудит. **Не дублировать `if role === ...` как правило безопасности во множестве модулей.**
- Миграции — версионированные файлы в Git, тест чистого развёртывания и безопасный порядок изменения схемы.
- Ошибки, аудит и история исправлений содержат авторов/время и не разглашают секреты/данные другого tenant.
- Сохранение и отображение количественных данных: единицы измерения не смешиваются, baseline и история коррекций воспроизводимы.
- Опасные действия не выполняются «по нажатию на скрытую кнопку» без серверной проверки; интерфейсные запреты — лишь дополнительный слой.

## 6. Общие соглашения UX и локализации

- Одинаковое действие называется одинаково: `Создать`, `Сохранить`, `Отменить`, `Удалить`, `Архивировать`, `Подтвердить`; опасные действия требуют явного подтверждения.
- Одинаковые состояния имеют одинаковый вид и терминологию: `loading`, `empty`, `error`, `success`, `disabled`, `readonly`, `pending`, `conflict`.
- Кнопки, формы, таблицы, модальные окна и сообщения должны использовать [общие UI-паттерны](UI_COMPONENTS.md), без отдельных реализаций для каждого модуля.
- Форматирование дат/чисел/единиц и локализация — через согласованные интерфейсы и настройки контекста, а не вручную по экранам.
- Responsive и клавиатурное управление проверяются вместе с UX, не считаются необязательным украшением.

## 7. Definition of Done — дополнения к существующему регламенту

Архитектор в задаче фиксирует `reuse review` и затронутые публичные контракты. Исполнитель реализует минимальный diff без дубликатов. Тестер проверяет повторное использование/совместимость, а для UI — темы, состояния и доступность. Документатор обновляет описание компонента и его публичного API только если он действительно создан/изменён.

**Отложить:** большой автоматический рефакторинг всех модулей; общую сверхуниверсальную UI/форм-библиотеку; генератор всего приложения; кастомную движковую систему схем и форм; массовую замену JS на React.

## 8. Обязательное поле карточки новой функции

```md
**Reuse review:**
- Единственный владелец данных/правила: <сервис/модуль + источник>.
- Где параметр/разрешение меняется один раз и как подписчики его получают: <контракт>.
- Найденные похожие сервисы/компоненты: <путь/публичный API>.
- Решение: REUSE / EXTEND / EXTRACT / NEW.
- Почему выбран именно этот вариант: <факт, не предположение>.
- Затронутый публичный контракт/версия: <если есть>.
- Что проверяется на регрессию: <конкретные сценарии>.
```

Если код ещё недоступен, поставить `NOT VERIFIED` и не придумывать пути.

## 9. Исторические принципы, подтверждённые в `_ai.zip` (дополнение v1.3)

- **Публичный адаптер поверх заменяемой библиотеки:** модуль использует стабильный service/API; точка замены PDF/XLSX/AI/Storage/темы не должна размножаться по файлам продукта. См. `CHANGE_IMPACT_AND_REGRESSION.md`.
- **Один владелец общего правила:** до дублирования вспомнить `SERVICES_API.md` и `MODULE_CROSS_REFERENCE_MAP.md` из старого архива, но фактический сервис и consumers проверить по текущему Git. Актуальная навигация — `FILE_MAP.md`.
- **Локальный техдолг при касании:** разрешено исправить только очевидное, в уже утверждённых файлах и без изменения публичных контрактов/критичных областей. Более широкую работу планировать отдельно.
- **Радиус изменения:** приватный модуль → локальные тесты; общий API/UI/данные → тесты реальных потребителей; Auth/RLS/Sync/Storage/SW → критичный режим проверки. Подробности в `CHANGE_IMPACT_AND_REGRESSION.md`.
- **Не использовать нормы строк кода как KPI задачи.** Масштаб определяется завершённым функциональным сценарием, риском и доказуемостью тестирования.
