# Platform 2.0 — критерии завершения (Definition of Done)

## 1. Готовность отдельной задачи

Перевод в `DONE` возможен **только после всех применимых пунктов**:

- [ ] Текущая карточка утверждена, её ID, требования и границы подтверждены.
- [ ] Функция выполняет критерии приёмки на фактическом коде, не только в отчёте/макете.
- [ ] Не затронута production RBI Platform/Quality; нет подключения к её рабочей базе/секретам.
- [ ] Изменены только согласованные компоненты либо отклонения отдельно утверждены.
- [ ] Нет прямых приватных импортов между модулями; публичные API версии/совместимости соблюдены, если применимо.
- [ ] Для сквозного правила/настройки назначен единственный владелец и публичный контракт; изменение возможно через него без правок каждого бизнес-модуля. Нет несогласованных дублирующих таблиц ролей, правил доступа, настроек, тем или авторизации.
- [ ] До нового общего кода выполнен `reuse review`: выбран REUSE/EXTEND/EXTRACT/NEW, причина указана в задаче; нет необоснованного дублирования алгоритмов, сервисов и UI.
- [ ] Если менялся UI: используется единая дизайн-система/семантические токены; проверены состояния, применимые светлая/тёмная темы, базовая доступность и отсутствие стилистической регрессии оболочки.
- [ ] Запущены доступные сборка, проверки TypeScript, unit/integration и пользовательские сценарии; указаны **команды, фактический результат, commit и окружение**.
- [ ] Для данных/авторизации используются единый каталог действий и серверная проверка по контексту/ресурсу/лицензии; нет `role name`-based разрешения в UI как единственной защиты; проведены негативные тесты компании/проекта/роли, API/RLS/Storage в затронутых частях; отсутствие теста не замаскировано.
- [ ] Значимые версии планов, фактов и миграций сохраняют историю; нет скрытой потери данных.
- [ ] Миграции воспроизводимы, проверены на чистой/тестовой БД и имеют безопасный путь восстановления при ошибке, если применимо.
- [ ] Исполнитель выполнил самопроверку (команда → фактический результат) и просмотрел свой окончательный diff; для CRITICAL-изменений Архитектор сделал read-only ревью (ADR-062).
- [ ] Исполнитель обновил ровно необходимые Markdown и CHANGELOG/техдолг, если применимо.
- [ ] Владелец продукта явно принял работу и разрешил `DONE`.

**NOT RUN ≠ PASS.** При невозможности обязательной проверки ставится `BLOCKED`, до устранения блокера полноценной приёмки нет. Ранее известные несвязанные ошибки baseline допустимо фиксировать отдельно: новая задача не должна ухудшать исходное состояние, но не обязана устранять весь наследуемый долг.

## 2. Принципы оценки бизнес-функционала Plan/Fact

- Плановые значения и сохранённый baseline воспроизводимы.
- Факт имеет объём, дату, автора и корректно учитываемое исправление/историю.
- Остатки и отклонения вычисляются по сохранённым данным, а не по демонстрационным константам.
- Расчёт процента проекта не должен некорректно агрегировать м², м³, шт. без определённой методики.
- При смене компании/проекта запрещён доступ к чужим данным на **сервере**, а не только в UI.
- После перезагрузки интерфейса сохраняются реальные записи; ошибки ввода отображаются явно.

## 3. Отдельная готовность к первому показу заказчику

Требования раздела 12 архитектуры v1.3 остаются основными. На демо обязателен путь: **компания/проект → локации → ВОР → план → факт → расчёт → сводка**, работающий на сохраняемых данных. Независимая сборка React и контроль доступов доказаны. Ограничения MVP явно названы.

Первый показ на вымышленных данных допустим только с обозначением **demo**. Использование реальных корпоративных данных или доступ внешних пользователей — отдельное ворото безопасности: серверная авторизация, tenant isolation, Storage, секреты, тесты угроз и одобрение на использование данных.

## 4. Что НЕ считать обязательным для первого показа

Не требовать заранее полноценные: конструктор корпоративных ролей, шаблоны мастер-данных, пакетный обмен между компаниями, универсальные интеграции, AI Gateway, offline, фото, шахматку, финансовые и договорные реестры, on-prem установщик. Эти требования не отменены, а отнесены к последующим релизам.

- [ ] Если изменён общий публичный контракт, описаны его реальные потребители и влияние по `LOCAL / SHARED / CRITICAL`; выполнены соответствующие проверки без обращения к production.
- [ ] Если поменялись места поиска кода, Исполнитель обновил `FILE_MAP.md` и тематическую карту и проверил ссылки.
- [ ] Скрипты и методы тестирования взяты из текущей безопасной среды, а не из старых учётных данных / runtime-конфигурации `_ai.zip`.
- [ ] При разработке Plan/Fact проверено, не существует ли подтверждённая реализация/доменные тесты ПФ-1…ПФ-6 в актуальном Git, чтобы не повторять готовую работу.
