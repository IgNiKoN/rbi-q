# P2-0072 — план выкладки «Номера Качества по стандарту»

**Статус:** готов к приёмке, **не выложено**. Выкладка — только по разрешению владельца. Миграция 054 — **до** приложения: приложение 054 не требует (номер и связи ставит сервер), но новые проверки с телефона приходят с номером-uuid, и сервер сразу ставит им `core_id = id`. Старое приложение с 054 работает без изменений (`core_id` ему не нужен, сервер ставит сам); новое приложение без 054 тоже работает (лишних полей не отправляет). Порядок «054 → сайт» — чтобы проверить сервер раньше телефонов.

Ничего нового на экранах: номер записи нигде не показывается. Проверки, задачи, совещания, отчёты, Стройконтроль открываются и правятся как раньше. Повторная отправка проверки (плохая связь, обрыв) не создаёт дублей пунктов и фото.

## 3. Шаги

1. **Проба на боевой (только чтение):** SQL Editor → `scripts/p2-0072/01_dryrun.sql` → одна таблица: по 41 таблице — строк, сколько уже с uuid-номером, сколько uuid-номеров повторяется в двух компаниях (такие получат новый `core_id`); по 16 связям — ссылок, совпадёт, не совпадёт (висячие — связь останется пустой, строки на месте), пусто. Таблицу — в отчёт. **Стоп и вопрос владельцу**, если «не совпадёт» у пунктов или фото проверки больше 1 % (это значит, что у проверок потерялись строки).
2. Свежий `main` в ветку (если ушёл вперёд); `npm run build:version`, `npx tsc --noEmit`, `npm run test:unit`, `npm run test:schema`, PGlite 054 (`tests/server/run-pglite.mjs`).
3. **Сервер:** снимок базы (панель Beget) → SQL Editor: `054_quality_ids_up.sql`. Время на копии: 30 тыс. проверок, 300 тыс. пунктов, 90 тыс. фото — 17,6 с в PGlite (настоящий сервер быстрее); на это время запись в таблицы Качества ждёт (телефоны досылают сами). Проверка:
   `select (select count(*) from information_schema.columns where table_schema = 'quality' and column_name = 'core_id'), (select count(*) from quality.rbi_inspections where core_id is null), (select count(*) from quality.rbi_inspection_items where core_inspection_id is null and inspection_id <> '')` → `41, 0, N` (N — «не совпадёт» из пробы).
4. Слияние в `main` (fast-forward), push в `IgNiKoN/rbi-q` — по разрешению владельца.
5. Сайт: `cd /var/www/rbi-quality && git rev-parse HEAD` (запомнить) → `git pull --ff-only` → `node scripts/check-release.mjs`. Новая версия включится при следующем запуске или кнопкой «Перезапустить сейчас» («Настройки → Помощь и о программе»).

**Откат (обратный порядок):** сайт — `git reset --hard <запомненный HEAD>`; затем SQL Editor — `054_quality_ids_down.sql`: сторожа, связи и `core_id` снимаются, данные записей не меняются. Проверки, созданные новой версией, остаются с номером-uuid в старой колонке `id` — прежнее приложение их принимает (номер — просто текст). Проверено на PGlite: отпечаток схемы после отката = до миграции, повторное применение — без ошибок.

## 4. Проверка владельцем (10 минут, телефон)

1. Телефон, «Качество → Проверка»: провести проверку с 2–3 фото **в авиарежиме** → включить сеть → в «Истории» проверка одна, отправлена.
2. Нажать «Синхронизировать» ещё раз → в «Истории» по-прежнему одна проверка, фото на месте.
3. Открыть старую проверку (до обновления) → изменить комментарий → сохранить → отправилась, открывается как раньше.
4. Поставить задачу без сети → включить сеть → задача у исполнителя одна.
5. (По желанию, SQL Editor, только чтение): `select id, core_id from quality.rbi_inspections order by created_at desc limit 3` — у новой проверки `id` = `core_id`.

**Не проверялось на живом сервере и настоящих телефонах** (локальная копия сервера PGlite и стенд Chromium с подставным сервером).
