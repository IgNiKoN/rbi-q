## Что сделано

1. **Правила чтения без функции на строке (059).** Права человека считаются один раз на запрос (подзапрос `(select …)` — initplan), строка — дешёвое сравнение без запросов к базе:
   - `quality.can` → `quality.readable_projects(действия)`: проекты, где есть действие (+ метки «любой проект», «без проекта», контейнеры компании); правило — `array[…] && (select …)`; 39 таблиц (в т. ч. `file_registry`, `location_nodes`, `construction_*_v2` планы и помещения, библиотека компании);
   - `quality.rec_ok` → `quality.read_scope(видеть все, своя)` + `quality.read_ok(…)` (plpgsql, не security definer): 9 таблиц (`sk_records`, проверки, задачи, совещания, FMEA, отчёты);
   - `quality.row_visible` → `visible_scope` + `visible_ok` (Стройконтроль 1, черновики, очередь); `core.row_allowed` с местом → `area_scope` + `area_ok` (замечания и приёмки СК 2.0: поддерево места, в т. ч. удалённые места — как `core.place_up`);
   - пункты и фото проверки — «проверка видна» одним хеш-подзапросом по `rbi_inspections` (её правило) + своё без проверки;
   - файлы `quality-*` (`storage.objects`, обычное правило и сторож) → `quality.storage_companies(модули)`.
   Смысл прав — прежний, включая найденную особенность 053: запись **без автора** проходит «только своя» (ТД 420, сохранено ради «до = после»). Правила записи не менялись.
2. **Сторож `test:schema`:** у таблиц `quality.*` правило чтения не зовёт security definer на строке (кроме скалярного подзапроса без FROM; исключения с причиной: `member_by_email` у записи без автора — ТД 422, `row_exists` у своего пункта без видимой проверки).
3. **`storage.search` 10 с — причина:** при каждой отправке фото `rbiUploadAsset` 2–6 раз просил список **всей папки** бакета (`storage.list` → `storage.search`), а правило `storage.objects` проверяло права на каждом файле, дважды. Теперь — `storage.exists` (один файл, HEAD); список — запасной путь (сервер без HEAD или файл после загрузки ещё не виден).
4. **Синхронизация Качества — только изменения:** 11 таблиц, читавшихся целиком каждый проход, `sk_records` (был один запрос `limit 25000` — теперь по 1 000) и `file_registry` — «изменено после своей метки − 15 мин»; у каждой таблицы своя метка (ставится после записи строк на устройство; сбой не сдвигает; полный проход — целиком). Подрядчики платформы дописывают реквизиты в карточки: пришли новые карточки — целиком.
5. **План/Факт:** `public.pf_my_permissions_all(объекты)` (059) — права всех объектов одним вызовом (прежняя функция остаётся); клиент — `permissions-batch.ts` в `vor.service` (30 с, сброс при смене прав/компании; без сети и на сервере без 059 — прежний вызов и копия). «Заранее» — после первой синхронизации Качества и не раньше 45 с после запуска, объекты порциями по 3, между порциями ждёт синхронизацию.

## Пользовательский сценарий

1. Новый телефон: вход → Качество загружается быстрее, на графике Beget при входе нет пика 300 % (после выкладки).
2. «План/Факт» у обычного сотрудника с 20 объектами — открывается ≈ за 1 с.
3. Осмотр с фото уходит; фото открывается на другом устройстве.
4. Подрядчик, инженер на секции, руководитель видят те же записи, что вчера.

## Изменения API / БД / безопасности

- Только правила **чтения** и новые функции; данные и правила записи не меняются. Функции `quality.*_scope`, `readable_projects`, `storage_companies`, `pf_my_permissions_all` — security definer, отдают только права **вызывающего** (`auth.uid()`, компания запроса); `*_ok` — чистые функции без запросов к базе. Служебные функции Качества закрытыми и остались (`018e` — FAIL 0): «своя фирма» Стройконтроля 1 сверяет название фирмы в записи со списком названий, собранным один раз на запрос.
- Контейнеры — только своей компании (внешний ключ проекта записи `(core_project_id, core_company_id)` не даёт сослаться на чужой — проверено по схеме). Место записи — внешний ключ на `core.locations`, поэтому «без места» = пустое поле.
- Публичные RPC не менялись; новая — `pf_my_permissions_all(uuid[])` (до 500 объектов).
