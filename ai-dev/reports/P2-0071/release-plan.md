# P2-0071 — план выкладки «Качество на единые права»

**Статус:** готов к приёмке, **не выложено**. Выкладка — только по разрешению владельца. Миграция 053 — **до** приложения: новое приложение читает участие Качества (`quality.my_access → quality`) и `pf_quality_container`. Старое приложение с 053 работает (лишние поля ответа игнорирует; что видно и можно — решает сервер; мастер старого приложения со «Объектами Качества» получит отказ «Объекты Качества больше не выбираются…» — выкладывать приложение сразу за миграцией).

## 2. Что увидят люди

- **Администратор компании:** «Роли и права» — у каждого модуля переключатель «Доступ к модулю»; у Качества группы «Проверки», «Задачи», «Совещания и мероприятия», «FMEA и этапы», «Отчёты», «Внешний СК», «База знаний и справочники», «Настройки» с едиными подписями. «Сотрудники → Назначить» → «Где»: «Все объекты / Выбранные объекты / Без объектов».
- **Инженер с выбранными объектами** (было в назначении «объекты Качества») — участие на эти объекты: в Качестве **и в Стройконтроле** видит только их, целиком; свои записи правит, чужие — нет.
- **Инженер без выбранных объектов** («только свои») — «Без объектов»: база знаний и ИИ остаются, записей объектов нет. По словам владельца, таких нет — покажет проба (шаг 1).
- **Руководство, «вся компания»** — как раньше. **Подрядчик** — как раньше (своя фирма).
- **Исполнитель задачи** выполняет её, но переназначить может только автор или тот, у кого «Задачи: редактирование чужих».
- **Совещания, мероприятия, FMEA, этапы:** изменить / удалить чужое — у кого «Редактирование» группы (сервер разрешал и раньше; экран раньше пускал только руководителя, ТД 374).

## 3. Шаги

1. **Проба на боевой (только чтение):** SQL Editor → `scripts/p2-0071/01_dryrun.sql` → три таблицы: (1) кого как перенесёт (объекты → участие, «без объектов», «нет контейнера»); (2) записи Качества без объекта (их увидят только автор и назначенные на всю компанию); (3) какие роли какой набор действий получат. Таблицы — в отчёт; если в (1) есть «без объектов» или «нет контейнера» — **стоп, вопрос владельцу** (список людей).
2. Свежий `main` в ветку (если ушёл вперёд); `npm run build:platform && npm run build:company`, `npx tsc --noEmit`, `npm run test:unit`, PGlite 053.
3. **Сервер:** снимок базы (панель Beget) → SQL Editor: `053_quality_rights_up.sql` → проверка: `select (select count(*) from core.permission_catalog where unplaced is not null), to_regprocedure('quality.rec_ok(uuid,uuid,uuid,text[],text[],uuid,uuid,uuid)') is not null, (select count(*) from p2_backup.m053_assignments)` → `15, true, N` (N — как в пробе).
4. Слияние в `main` (fast-forward), push в `IgNiKoN/rbi-q` — по разрешению владельца.
5. Сайт: `cd /var/www/rbi-quality && git rev-parse HEAD` (запомнить) → `git pull --ff-only` → `node scripts/check-release.mjs`. Новая версия включится при следующем запуске или кнопкой «Перезапустить сейчас».

**Откат (обратный порядок):** сайт — `git reset --hard <запомненный HEAD>`; затем SQL Editor — `053_quality_rights_down.sql`: назначения — как до 053 (перенесённые удаляются, прежние снова действуют, по журналу), правила Качества — прежние (мост `quality_objects`), каталог и роли — без новых действий, ядро — как 052. Назначения, сделанные после 053 вручную, остаются. Проверено на PGlite: отпечаток схемы после отката = до миграции, повторное применение — без ошибок, «до = после» снова 0 неожиданных.

1. «Роли и права» → «Инженер строительного контроля»: у Качества «Проверки: просмотр всех, создание, удаление», «Редактирование чужих» — нет.

3. «Сотрудники → Назначить» инженеру «Выбранные объекты: ЖК-1» → войти им: в Качестве и Стройконтроле только ЖК-1; чужую проверку изменить нельзя.
4. «Кто что может» → ЖК-1 → «Качество»: у инженера «Редактирование чужих» — «—».
5. «Назначить» → «Без объектов» → войти: база знаний и ИИ есть, проверок объектов нет.
