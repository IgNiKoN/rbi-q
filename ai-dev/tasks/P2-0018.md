## 1. Цель

Сотрудник компании в Качестве / Стройконтроле 2.0 видит ровно то, что видел бы с той же ролью в старом Качестве, и сервер не отдаёт ему больше даже в обход экрана. Заодно закрыты дыры из ревью P2-0016: опасный порядок откатов, лишние разделы в API, черновики подрядчиков, ключи записей без компании, кэш файлов на общем устройстве.

## 2. Подтверждённое исходное состояние (`main` `4aac301`)

- **Старое Качество (как задумано, только на клиенте):**

  | роль | видит |
  |---|---|
  | Гость | ничего |
  | Подрядчик | только записи своего подрядчика (на своих объектах) |
  | Инженер СК | только свои записи на своих объектах |
  | РП | всё по своим объектам, только чтение |
  | Зам. / Директор / Админ | всё; директор — только чтение |

- **2.0 сейчас:**
  - сервер (`quality.can`, 018) проверяет компанию, модуль, право и объект назначения (`role_assignments.project_id` или вся компания);
  - «свои записи» и «свой подрядчик» сервер не проверяет;
  - шаблоны ролей (018 :29–40): РП и админ получают `*.manage`, прораб — `construction.edit`, ПТО / руководство / заказчик — `*.view`;
  - экранную роль строит мост (`src/platform/auth/quality-bridge.ts` `roleFor` :57–64): manage → «manager», edit → «engineer», `contractor_rep` → «contractor», view → «director»;
  - мост не передаёт старому экрану ни назначенные объекты, ни подрядчика. Итог: РП видит и правит всё, у подрядчика пусто, прораб/ПТО/заказчик видят всё по компании.
- **Связи человека с подрядчиком нет:** назначение роли (`core.role_assignments`) не знает фирму. Подрядчики Качества связаны с контрагентами ядра (018e: `quality.contractor_core_links`, `contractor_directory`).
- **Техдолг:** №117 (сторож порядка откатов 018/018c), №118 + №99 (`pgrst.db_schemas` и открытые служебные схемы), №119 (черновики контрагентов из Качества), №120 (ключи 43 таблиц без компании), №121 (кэш `sw.js` при 401/403, откаты файлов 018d/018e). Данные Качества 2.0 сейчас — только демо и тестовые компании.
- **Не подтверждено:** настройка `PGRST_DB_SCHEMAS` на сервере; есть ли у записей Качества колонка подрядчика-ссылки или только `contractor_name` (уточнить на этапе 4); как старый экран ведёт себя при роли «РП» и пустом списке объектов.

## 3. Объём реализации

1. **Откаты (№117, №121-откаты).**
   - `018_quality_down.sql`, `018c_quality_access_down.sql`: в начале — сторож (ошибка, если есть бакеты `quality-*` или триггер `counterparties_to_quality`).
   - `018d_down`: файлы не удалять SQL-ом — сторож «сначала очистите бакеты через Storage API» и инструкция в `docs/SERVERS.md`.
   - `018e_down`: не падать, если черновик где-то указан (понятная ошибка до изменений).
2. **API-разделы (№118, №99).**
   - Только чтение на сервере: фактические `pgrst.db_schemas` / `PGRST_DB_SCHEMAS`, RLS у `net.*`, `supabase_functions.*`, `realtime.subscription`.
   - Расхождение → миграция `019_api_schemas` (вернуть пропавший раздел); служебные схемы в API не открывать.
   - Если нужен доступ к настройкам контейнера — вопрос владельцу с инструкцией.
3. **Ключи по компании (№120).**
   - Миграция `021_quality_keys`: `core_company_id` в первичные и уникальные ключи 43 таблиц (по образцу `sk_records`), `allowed_projects`, ключи настроек.
   - Данные сохраняются; откат — `021_down`.
4. **Видимость по ролям — сервер.** Миграция `020_quality_scope`:
   - **Область видимости** — одна функция `quality.row_visible(...)`, вызывается в `select`-правилах таблиц с записями:
     - вся компания — `*.manage` или новое право `quality.scope.company` (Администратор компании, Руководство);
     - свои объекты — назначение с объектом или на всю компанию;
     - свои записи — новый столбец автора `created_by` (ставит сервер, менять нельзя); для экранной роли «инженер»;
     - свой подрядчик — новое право `quality.scope.contractor` и `counterparty_id` у назначения роли; запись видна, если её подрядчик связан с этим контрагентом (через `contractor_core_links`).
   - **Шаблоны ролей:**
     - РП, Прораб, ПТО, Заказчик — только `*.view`, свои объекты (снять `*.edit` / `*.manage` у РП и `construction.edit` у прораба);
     - Инженер СК — `*.edit`, свои записи;
     - Представитель подрядчика — `*.view` + `construction.edit` + `quality.scope.contractor`;
     - Администратор компании — всё;
     - Руководство — вся компания, только чтение.
   - **Запись** — те же правила плюс право edit (правка чужих записей — только при `*.manage`).
   - **Пользовательские роли конструктора** (P2-0004b) получают область по своим правам: manage / `scope.company` → компания; `scope.contractor` → подрядчик; edit → свои записи; view → свои объекты.
5. **Видимость — клиент.**
   - Мост (`quality-bridge.ts`) передаёт старому экрану роль по той же таблице: «Руководство» → директор, «РП / Прораб / ПТО / Заказчик» → РП (свои объекты), «Инженер» → инженер, «Подрядчик» → подрядчик + название фирмы. Также передаёт назначенные объекты.
   - Список объектов в «Синхронизации команды» — только свои.
   - «Компания → Роли / люди»: при назначении роли с `quality.scope.contractor` — выбор фирмы из «Контрагентов» (вид «подрядчик»), сохраняет сервер (`pf_assign_role` + `counterparty_id`).
   - Экран — подсказка: правило держит сервер.
6. **Черновики подрядчиков и кэш (№119, №121-кэш).**
   - 018e-поведение исправить новой миграцией `022_quality_contractors_fix`:
     - автор в журнале;
     - лимит черновиков на пользователя в сутки;
     - правка контрагента в ядре не воскрешает удалённую в Качестве строку;
     - архив контрагента или снятие вида «подрядчик» убирает его из справочника Качества.
   - `sw.js`: закрытый файл из кэша — только при сетевой ошибке (не при 401/403); при выходе и смене компании кэш закрытых файлов чистится.
7. **Самопроверка, документы, версия.** `test:server` (+ матрица ролей), снимок RBI до = после, APP_GUIDE («кто что видит в Качестве»), SERVERS.md, TECH_DEBT (закрыть №99, 117–121), CHANGELOG, «История обновлений», SW.

**Вне блока:** перенос РБИ и дыры старого РБИ (ТД №95–98, 116); приглашение людей письмом; разрез видимости План/Факта; новые экраны Качества.

## 3а. Единый источник истины

- Кто что видит — одна функция на сервере (`quality.row_visible`) + права ядра.
- Фирма подрядчика — контрагент ядра, привязанный к назначению.
- Автор записи — `auth.uid()`, ставит сервер.
- Экранная роль старого Качества выводится из тех же прав (одна таблица соответствия в мосте, покрыта тестом).

## 8. Риски и зависимости

- **Две CRITICAL-зоны в одном блоке** (решение владельца). Мера: самый рискованный этап первым и только на PGlite; сервер — одним этапом после всех PGlite-проверок; снимок RBI.
