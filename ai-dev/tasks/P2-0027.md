**Владелец продукта:** Igor (IgNiKoN)

**Ветка:** `task/P2-0027-rbi-transfer` (создаёт Исполнитель от `main`).

**Решения владельца (25.10.2026, чат и кнопки):**
- Единый вход = почта + пароль (решение ADR-068 не пересматривается); старых пользователей перевести на Платформу 2.0 без потери данных.
- Переход **разом** (12 человек), не «по людям»; потеря данных за пару дней между пробным и финальным переносом допустима.
- Старое приложение работает со своим облаком как есть, не трогаем; новое выкладывается вместо старого позже, **после теста на владельце** (выкладка — следующий блок P2-0028).
- Готовые отчёты (`shared_report_snapshots` ≈ 1,6 ГБ, бакет `reports` ≈ 1,8 ГБ) **не переносятся** — генерируются заново; их удаление со старого сервера — отдельно, после перехода, руками владельца (с архивом).
- Почта есть у всех 12 человек.
- **Название компании — «RBI» (латиницей)**, решение владельца 25.10.2026.
- **Без пробной компании:** перенос сразу в «RBI»; сначала владелец (его учётка и его данные проверяются), остальные 11 учёток — потом (P2-0028).
- Все старые данные → компания «RBI»; старые учётки переезжают со всеми доступами (роль, объекты) — вход по почте; владелец — роль «вся компания».
- Старое приложение работает во время перевода; в день переключения владелец заливает код Платформы 2.0 туда, откуда открывается старое приложение (откат — прежняя версия по метке); инструкция — P2-0028.
- Модули у компаний включает владелец в «Администрировании»: План/Факт, Качество, **Стройконтроль и Стройконтроль v2 — отдельными переключателями** (решение 25.10.2026, делается в P2-0028); **База знаний — отдельный модуль со своим переключателем** (решение владельца 25.10.2026, делается в P2-0028; её данные переносятся в этом блоке).

## 1. Цель

Откройте Платформу 2.0 (стенд/локально), войдите **своей почтой** → Качество → компания «RBI» → видите **свои старые проверки, фото, задачи, ПК СК, объекты, подрядчиков**; «История» и «Аналитика» показывают те же числа, что старое приложение (сверка в отчёте). Старое приложение и его данные не изменились.

## 2. Подтверждённое исходное состояние (25.10.2026)

- Размеры (SQL только чтение, владелец разрешил): база 1,7 ГБ, из них `public` 1,66 ГБ — почти всё `shared_report_snapshots` (1,57 ГБ, 317 строк); рабочие таблицы ~70 МБ (`sk_records` 10,5 тыс., `rbi_inspection_items` 22 тыс., `rbi_tasks` 2,7 тыс., `rbi_engineer_profiles` 23). Файлы 3,4 ГБ: `reports` 1,8 ГБ, `inspection-photos` 1,2 ГБ (4260), `library-etalons` 113 МБ, `custom-assets` 99 МБ, `library-docs` 65 МБ, `library-twi` 57 МБ, `construction-plans` 26 МБ, `construction-defects` 11 МБ.
- `quality.*` = `public.*` того же имени + `core_company_id`, `core_project_id` (`scripts/gen-quality-schema.mjs`, `TABLES`: 55 таблиц; `SKIPPED` — не переносятся). Видимость — `quality.row_visible` (`020`), автор — `core_created_by`. Ключи с компанией (`021`). Бакеты компаний приватные, путь `<company_id>/…` (`018d`).
- Старый вход: профиль `public.rbi_engineer_profiles` (`project_code` + `inspector_id` = «код_имя»), записи помечены **именем** (`inspector_name` / `engineer_name`), компания = код проекта (`allowed_projects`).
- Свободное место на диске сервера — **не известно** (через SQL не видно) → этап 1, вопрос владельцу.

## 3. Объём реализации

1. **Скрипт переноса** `scripts/rbi-transfer/` (в репозитории, повторяемый): читает `public.*` (только `SELECT`), пишет в `quality.*` компании-получателя. Связка «старая ↔ новая запись» — таблица `quality.rbi_transfer_map` (новый объект, миграция `NNN_rbi_transfer`) или сохранение старого id (если id уже текстовый/UUID и уникален в компании — решить на этапе 1). Повторный запуск — без дублей (по связке), «очистить перенос компании» — одной командой (откат).
2. **Компания и объекты:** сразу компания «RBI» (решение владельца 25.10.2026: без пробной компании; до дня переключения в ней работает только владелец; повторный запуск и «очистить перенос» — в ней же; финальный перенос P2-0028 — докопирование в неё); коды проектов `allowed_projects` → объекты ядра компании (`core_project_id`); подрядчики — по существующему правилу P2-0016 (черновик контрагента без ИНН).
3. **Люди:** таблица соответствия «старый профиль (код + имя) → почта» (заполняет владелец, файл вне git или строки в `quality.rbi_transfer_people`); `core_created_by` записей = учётка почты, если она уже есть, иначе — пусто с сохранением имени (дозаполнит P2-0028). Роль и объекты — из профиля → назначения ролей компании (`role_assignments`) по правилу P2-0018.
4. **Файлы:** фото проверок, эталоны, документы, ТИВИ, планы, дефекты, `custom-assets` — копия в бакеты компании (`<company_id>/…`) с переписыванием ссылок в записях; `reports` и `shared_report_snapshots` — не переносятся.
5. **Сверка** `scripts/rbi-transfer/verify` (только чтение): по каждой таблице — строк старое/новое; по каждому человеку и объекту — проверок, пунктов, фото; средний УрК по подрядчикам/объектам; файлов и их суммарный размер. Результат — таблица в отчёте.

## 3а. Reuse / единый источник истины

- Список таблиц и их класс (project/company, модуль) — **только** `TABLES`/`SKIPPED` из `scripts/gen-quality-schema.mjs` (импорт, не копия).
- Подрядчики, роли, видимость — существующие функции/правила P2-0016/0018 (`quality.*`, `role_assignments`), без новых правил доступа.
- Пути файлов компании — правило `018d` (`<company_id>/…`).

## 5. Запреты и границы

- **`public.*` и бакеты старого приложения — только чтение** (ни одной записи, ни одного удаления). `rbi-q-main` не трогать.
- Не менять настройки Auth/GoTrue/JWT (ADR-061a); учётки по почте — только через Auth API/админку, пароли не печатать и не хранить в git.
- Не переносить `reports`, `shared_report_snapshots`; не удалять их.
- Финальный перенос в «RBI», выкладка нового приложения, выключение PIN, рассылка паролей — **P2-0028**, не здесь.
- Ключи сервиса — только из переменных окружения, не печатать.

## 6. Критерии приёмки

1. Пробный перенос в «RBI»: все таблицы по `TABLES` (кроме исключённых) — старое = новое; фото/файлы открываются.
2. Владелец по почте видит свои данные; числа «Истории»/«Аналитики» = старому приложению.
3. Повторный запуск без дублей; «очистить перенос» работает; `public` не изменился (сверка до/после).
4. Инструкция дня переключения готова.
5. unit ×3, `check:ts` 0, `test:server` PASS.

## 7. План тестирования

SQL-сверка (только чтение) до/после, повторный запуск, откат на «RBI»; новое приложение локально/стенд с учёткой владельца; снимок чисел аналитики старого и нового приложения. NOT RUN — с причиной.

## 8. Риски

- Имя как идентичность: однофамильцы/переименования в одном коде проекта → таблица соответствия людей проверяется владельцем.
- Ссылки на файлы внутри JSON записей (фото в `details`/`photos`) — переписать все; пропуск = «битые» фото (сверка этапа 2).
- Копирование 1,5 ГБ файлов через Storage API — время и место; при нехватке места — `BLOCKED`.
- Общий сервер: нагрузка в рабочее время — большие прогоны вечером/в выходные.
