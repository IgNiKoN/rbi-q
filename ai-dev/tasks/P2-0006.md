## 1. Цель

ПТО загружает Excel-ВОР заказчика в его собственной форме и без перепечатки получает нормализованные позиции «место (узел дерева) + вид работ + ЕИ + объём». Система сама находит шапку и колонки, типы строк (группа / работа / материал / заголовок места), привязывает заголовки «Секция / Этаж / кв.» к дереву объекта, сопоставляет наименования со справочником видов работ по словарю (🟢 / 🟡 / 🔴) и сверяет суммы. Решения ПТО запоминаются: второй ВОР той же формы — почти без ручной работы.

## 3. Объём реализации

1. **Разбор в браузере** (`src/modules/planfact/vor/` — чистые функции, без DOM): чтение листа → поиск шапки (ключевые слова «Наименование», «Ед. изм.», «Кол-во/Объём/Количество», «Норма расхода», «Цена/Стоимость»; двухстрочная шапка; строка нумерации колонок пропускается) → карта колонок → тип каждой строки: `group` / `work` / `material` / `context` (место) / `skip` (итоги, пустые, реквизиты). Материал — дочерняя строка работы (по колонке типа «М», номеру `x.y.z`, или «нет ЕИ работы + идёт сразу после работы» — правило фиксирует Исполнитель по образцам). Числа: запятая/пробелы/строки → `numeric`. Контекст места: «Корпус N», «Секция N», «Этаж N», «Этажи N-M», «кв. 3, 16, 24…» — стек контекста наследуется строками ниже до следующего заголовка того же или старшего уровня. Сверка: Σ объёмов/стоимостей работ по группе = итог группы, если итог есть в файле. Лимит MVP — **≤ 10 000 строк** на лист; больше — понятный отказ (асинхронные пачки до 50 000 из PTO-01 — техдолг).
2. **Миграция 007** (только `planfact.*` и `public.pf_*`, есть `007_down.sql`, **применять файлом, не через буфер** — урок `006a`):
   - `vor_profiles` — профиль формы: `company_id`, `name` (заказчик/форма), `signature` (нормализованные заголовки шапки), `column_map`, `rules` (jsonb), `created_by/at`.
   - `vor_imports` — загрузка: `company_id`, `project_id`, `profile_id`, `file_name`, `file_sha256`, `sheet_name`, `status` (`draft` → `confirmed`), итоги, `created_by/at`, `confirmed_by/at`. После `confirmed` строки исходника и позиции неизменяемы (функции отказывают).
   - `vor_source_rows` — каждая строка исходника как есть: `import_id`, `row_no` (номер строки Excel), `kind`, `number`, `name`, `unit_text`, `qty`, `norm`, `prices` (jsonb), `context` (jsonb: корпус/секция/этаж/список квартир), `parent_row_id` (материал → работа), `raw` (jsonb ячеек).
   - `work_types` — справочник видов работ компании: `company_id`, `code` (необязательно), `name`, `unit_id`, `deleted_at`; «живой» — ПТО добавляет при разборе.
   - `vor_dictionary` — «наименование у заказчика → вид работ»: `company_id`, `canon_name` (через `planfact.canon_name`), `unit_text`, `work_type_id`, `confirmed_by/at`, `hits`; общий на все формы компании.
   - `vor_positions` — наша позиция: `import_id`, `project_id`, `location_id` (любой уровень), `work_type_id`, `unit_id`, `qty`, `apartments_note` (текст «кв. 3, 16, 24…» для групп), `status` (`green|yellow|red|confirmed`).
   - `vor_links` — связка «строка заказчика ↔ позиция + доля» (`source_row_id`, `position_id`, `share numeric`); в этом блоке 1:1 (`share = 1`), таблица готова к 1:N / N:1.
   - Новое действие `planfact.vor.manage` (загрузка ВОР, профили, словарь, виды работ) → шаблоны `company_admin`, `project_manager`, `pto` + **дозаполнение существующих ролей** (как 006 §2). Чтение ВОР и позиций — члены проекта; профили/словарь/виды работ — члены компании.
   - RLS на все таблицы: клиенту только SELECT (по проекту/компании); запись — только `public.pf_*` (security definer, фиксированный `search_path`, право внутри, `company_id` берётся из проекта, не от клиента). Пакетная запись строк — `pf_vor_add_rows(import, rows jsonb)` порциями ≤ 1 000.
   - Все изменения (импорт, подтверждение, словарь, виды работ) — в `audit_log`.
3. **Экран «План/Факт → ВОР»** (новая подвкладка в `manifest.nav`, видна при доступе к проекту; ПК + телефон 375 px): список загрузок проекта → «Загрузить Excel» → выбор листа (лист «не похож на ВОР» — предупреждение) → предпросмотр строк цветом по типу и с контекстом места → правка карты колонок вручную (выпадающие списки) → профиль формы запоминается и в следующий раз узнаётся по шапке автоматически.
4. **Места:** контекст строк → узлы дерева проекта по `canonical_key` и типу; найдено — привязка; нет — список «не хватает узлов: Секция 4 → Этажи 4–12…» и кнопка «Создать недостающие» (через `pf_add_location`, проверка права внутри). «Этажи 4–12» — диапазон: позиция на уровне секции с пометкой этажей **или** раскрывается в этажи — правило выбирает Исполнитель, фиксирует в отчёте и показывает владельцу на показе 2. Группа квартир — позиция на уровне ближайшего узла (секция/этаж) с `apartments_note`.
5. **Словарь и светофор:** для каждой строки-работы: 🟢 точное совпадение `canon_name` (+ ЕИ) в словаре компании → вид работ подставлен; 🟡 похожее (сходство слов ≥ порога, порог — константа в коде, подобрать на образцах) → предложение, ПТО подтверждает **пачкой** одной кнопкой; 🔴 нет вариантов → ПТО выбирает вид работ из справочника или создаёт новый (наименование и ЕИ заполнены из строки). Каждое подтверждение пополняет словарь. Счётчики 🟢/🟡/🔴 сверху экрана, фильтр по цвету.
6. **Подтверждение загрузки:** доступно, когда нет 🔴, все места привязаны и все ЕИ распознаны (ЕИ строки → `units` по коду/синониму: «м2» = «м²», «м.п» = «м.п.»; неизвестная ЕИ — 🔴 с предложением добавить в справочник). Создаются позиции и связки; проверка **Σ объёмов позиций = объём строки заказчика** по каждой строке; статус `confirmed`. Список позиций проекта «место (полный путь) · вид работ · ЕИ · объём», с фильтром по месту — только чтение для всех членов проекта.
7. Документы и отчёт: `docs/APP_GUIDE.md` (раздел «ВОР»), `standards/AUTH_AND_ACCESS.md` (новое действие), `docs/SERVERS.md` (миграция 007), `FILE_MAP.md`, `docs/TECH_DEBT.md`, `CHANGELOG`.

**Материалы** в этом блоке: хранятся как строки исходника с нормой и связью с работой; позиций для прораба не создают; в светофоре не участвуют (понадобятся для сметы P2-0006c и КС-2).
