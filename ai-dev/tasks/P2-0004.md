## 1. Цель

Владелец входит по почте и паролю и видит в «План/Факт» работы только своей компании и своих проектов. Пользователь другой компании их не видит — даже прямым запросом к серверу. Роли хранятся в базе как данные (шаблоны можно копировать и менять), права проверяются на сервере по действию, а не по названию роли. Это основа для конструктора ролей (P2-0004b).

## 3. Объём реализации

1. Схема `planfact`: компании, участники компаний, проекты, участники проектов, модули компании (лицензия `planfact`), работы (перенос демо-строк), журнал аудита. RLS — в той же миграции, deny-by-default.
2. Каталог действий (`planfact.works.view`, `planfact.works.edit`, `planfact.fact.create`, `planfact.wor.import`, `planfact.money.view`, `security.roles.assign` и т. п. — список фиксирует Исполнитель в отчёте), роли компании, их действия, назначения (пользователь → роль → проект). Одна серверная функция проверки права; RLS использует её же.
3. Девять ролей-шаблонов для каждой новой компании: Администратор компании, Руководитель проекта, Инженер ПТО, Прораб/мастер, Инженер строительного контроля, Экономист, Руководство, Заказчик (только чтение, без сумм), Представитель подрядчика (без механизма делегирования). Наборы действий — по матрице ТЗ §3.
4. Вход почта + пароль в оболочке для Platform 2.0, отдельно от старого облачного входа Quality; выход; показ «кто вошёл, компания, роль».
5. «План/Факт» читает работы из базы; переключатель проекта; кнопка «Добавить работу» видна по праву, сервер проверяет право сам. Изменения работ пишутся в журнал «кто — что — когда — было/стало».

## 3а. Reuse review

- **Найдено:** `permission.service.js` (клиентские роли Quality), `sync-auth.js` (вход projectCode+PIN), `config.service.js` (единственная настройка сервера), модуль `planfact`.
- **Решение:** серверная модель прав — **NEW** (в старом коде её нет); `permission.service.js` и `sync-auth.js` — **не трогать** (ADR-061 п. 7: новая схема входа не повторяет PIN); адрес сервера — **EXTEND** `config.service.js` отдельными ключами Platform 2.0 (например `P2_SUPABASE_URL`/`P2_SUPABASE_ANON_KEY`), старые `SUPABASE_URL/KEY` остаются пустыми, чтобы старая синхронизация не включилась; клиент — `@supabase/supabase-js` (точная версия) внутри модуля/сервиса Platform 2.0.
- **UI:** форма входа и шапка «пользователь/компания» — на CSS-переменных оболочки, светлая и тёмная темы.
- **Совместимость:** режим «Работать локально» и демо-данные продолжают работать без входа (демо-режим); остальные модули — регрессия.

## 3а. Единый источник истины

- **Права:** только серверные таблицы ролей/назначений + одна функция проверки. Клиентский список прав — подсказка для кнопок. В коде модуля нет `if role === …`.
- **Роли-шаблоны:** определены один раз в миграции (сид), копируются в компанию при её создании. P2-0004b будет менять эти же таблицы.
- **Адрес сервера:** одно место — `config.service.js`; секреты (service_role, строка подключения к БД, пароли тестовых пользователей) — только в `.env.local`, не в git и не в чате.
