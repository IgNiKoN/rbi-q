## 3. Объём реализации

1. **Опись** — скрипт `scripts/schema-inventory.mjs`. Он поднимает PGlite со всеми миграциями (`serverDb()`), читает `information_schema` / `pg_catalog` (таблицы, колонки, типы, ключи, внешние ключи, RLS вкл./выкл.) и пишет `ai-dev/reference/schema-inventory.json` (машинный) и `ai-dev/reports/P2-0069/inventory.html` (для владельца). У каждой таблицы указан модуль по `MODULES.md`.
2. **Стандарт** — `ai-dev/standards/DATA_TABLES.md`, не больше 2 экранов: обязательные поля и их имена — только из словаря (колонка «В коде»). Минимум:
   - ключ `id uuid` (создаётся на устройстве, §9 п. 1);
   - `company_id uuid` — граница данных;
   - ось проекта / объекта / места — ссылкой id, если запись к ним относится (п. 15 спеки);
   - автор — `created_by uuid` (пользователь); ФИО — только снимок `*_name` для печати;
   - `created_at` / `updated_at timestamptz`;
   - удаление — только пометка `deleted_at timestamptz` (+ `deleted_by`), без `is_deleted` и `archived` (§9 п. 2);
   - ссылки на записи ядра — `uuid` с внешним ключом, не текст;
   - имена — `snake_case`;
   - RLS включён;
   - деньги — `numeric` + валюта (§9 п. 5), если есть суммы.

   Исключения — классами (каталог платформы, связка с составным ключом, журнал, дочерняя строка), у каждого — причина. Правила с подписью «почему» — простым языком.
3. **Светофор** — каждую таблицу из описи проверить по каждому правилу стандарта: зелёный — соблюдено, жёлтый — исключение с причиной, красный — нарушение. Внизу — итог по модулям и по правилам.
4. **Сторож.** Проверка, которая падает, если:
   - (а) у **новой** таблицы любого раздела (включая `quality`) есть нарушение без исключения;
   - (б) у старых таблиц нарушений **стало больше**, чем записано в потолке `ai-dev/reference/schema-debt.json` (по таблице и правилу).

   Если нарушений стало меньше — проверка просит снизить потолок; счётчик только убывает. Заменяет или расширяет `migrations-lint.test.ts` (одна проверка, не две). Запуск — обычной командой самопроверки; если нужен PGlite — `npm run test:schema` и строка в `roles/TESTER.md`.
5. **Сверка с боевой.**
   - Запрос `supabase/checks/002_schema_inventory_readonly.sql`: только `select` из `information_schema`/`pg_catalog`, **без строк данных**, результат — одной таблицей для копирования.
   - Владелец запускает его в SQL Editor (как в памяти «Панель SQL Editor»).
   - Исполнитель сравнивает результат с описью, расхождения показывает в `inventory.html` отдельным разделом и записывает в ТД.
6. **План переезда** — `ai-dev/reports/P2-0069/migration-plan.md`.
   - Группы таблиц: ядро · План/Факт · Качество — автор · Качество — компания/проект · Стройконтроль · прочее.
   - Для каждой группы: что меняется, способ, CRITICAL или нет, порядок, оценка, какой блок очереди уже трогает эти таблицы (по §9 — чинить там, где всё равно трогаем).
   - **Способ для Качества (решение владельца 30.10):** добавить правильное поле рядом (`created_by uuid`, `company_id uuid` …), заполнить по сопоставлению, писать в оба, старое поле оставить и снять позже уборкой (мост с датой снятия, п. 14 спеки). Переименований в таблицах Качества нет.
   - Для `core`/`planfact` переименование допустимо, если код их читает только через RPC Платформы. Это проверяется по коду; не проверено — тоже «рядом».
