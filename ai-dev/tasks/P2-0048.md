## 1. Цель

РП назначает человека на проект целиком или на его часть (объект, секцию, этаж) с ролью и отметкой «ответственный за факт». Человек во всех экранах План/Факта видит только свою область. Факт по чужой секции сервер не принимает.

## 2. Подтверждённое исходное состояние

- `core.role_assignments`: человек + роль + `project_id` (null = вся компания) + `counterparty_id` + `valid_from/to` + `revoked_at`; костыли Качества `quality_objects text[]`, `quality_object_keys text[]` (033, 039*).
- `planfact.has_permission(project, action)` и `core.is_project_participant(project)` проверяют доступ только «проект или вся компания», места не учитывают.
- `planfact.fact_entries` → `position_id` (`vor_positions`) → место; автор `created_by`; поля «за кого» нет.
- С P2-0047 есть подразделения, дерево «Проект → Объекты → места» в `core.locations`; экран сотрудников — `src/platform/company/CompanyMembers.ts`, `CompanyScope.ts`.
- **NOT VERIFIED (уточнить Исполнителю на этапе 1):** точная связь `vor_positions` ↔ `core.locations`; как ВОР-шахматка и дашборд берут списки (RPC или прямые select под RLS).

## 3. Объём реализации

1. Область назначения в ядре: `division_id`, `location_id` (узел дерева: объект / секция / этаж; область = узел и всё под ним), `fact_owner boolean`. Старые назначения не меняют смысла: `project_id is null` — вся компания, `project_id` без `location_id` — весь проект.
2. Одна серверная функция «человек видит место» (по поддереву, с учётом подразделения, срока и отзыва) — её используют все проверки План/Факта.
3. Права План/Факта: списки ВОР, позиций, факта, шахматки, сводки — только в своей области; ввод и правка факта — только `fact_owner` по этому месту либо РП проекта с полем «за кого» (`on_behalf_of`).
4. «Компания → Сотрудники → Участие»: пакетный ввод — несколько людей × проект × несколько узлов дерева (галочками по дереву) × роль × «ответственный за факт» × срок; список назначений человека; отзыв. Три размера экрана.
4а. **Привязка и перепривязка инженера качества (замечание владельца 27.10):** у каждого назначения — видимое поле «Объекты / область» (дерево проекта, галочки) и действие «Изменить область» у действующего назначения: добавить/убрать объекты без отзыва (сервер — одна функция правки области с записью в журнал; повторное «Назначить» на ту же роль и проект сейчас даёт «Такое назначение уже действует»). Для ролей Качества изменение сразу доходит до Качества через переходник (п. 5). По коду сейчас: поле «Проекты Качества» есть только в форме «Назначить роль» и только если у роли есть права `quality.*` и `pf_list_quality_objects` вернул объекты; у действующего назначения правки объектов нет (`CompanyMembers.ts`, `pf_assign_role` в `033`). Исполнитель на этапе 2 воспроизводит на стенде и в отчёте пишет, почему поля не видно.
4б. **Новый внешний вид раздела «Компания» (решение владельца 27.10):** все подвкладки — Сотрудники, Роли, Проекты, Контрагенты, Справочники, Оформление, Модули компании, Журнал, Образцы (`src/platform/company/CompanyApp.ts`, `TABS`). Только внешний вид и раскладка по образцам P2-0046 (`Patterns.ts`, `ui/registry`, `ui/settings.ts`), подвкладки — как в Качестве. Три размера: телефон (iPhone 7, 375), планшет (768), ПК — без прокрутки вбок, светлая и тёмная темы. **Ничего не удалять:** до кода — опись «сейчас → где будет → что делает» по каждой кнопке, полю, фильтру и действию каждой подвкладки (`reports/P2-0048/settings-inventory.md`), после — та же опись сверена на стенде (всё на месте, всё работает). Серверную логику и права подвкладок не менять (кроме участия по п. 1–4а). Проекты и Образцы уже по образцам P2-0046/0047 — только проверить три размера и при необходимости подправить.
5. Переходник для Качества: из области назначения сервер выводит список объектов Качества (как сейчас в `quality_objects`). Экраны и правила Качества не трогаем. Пункт в `TECH_DEBT.md` с блоком снятия.

**Вне объёма:** договор в назначении (`contract_id`) — блок «Договоры и бригады»; гости подрядчика по договору; роль `customer`; права Качества по области — блок снятия переходника.
