## 1. Цель

Сотрудник открывает привычный `app.rbi-q.ru` (или иконку на телефоне) → вход по почте → временный пароль → свой пароль → все его данные в Платформе 2.0. Старое приложение и PIN-вход сотрудникам недоступны; старая локальная база и кэш на устройстве удаляются один раз.

## 2. Подтверждённое исходное состояние (26.10.2026)

- `app.rbi-q.ru` → nginx на VPS Beget (тот же сервер, что `api.rbi-q.ru`); по словам владельца — каталог, обновляемый `git pull` из `IgNiKoN/rbi-q`. **Не подтверждено:** путь каталога и ветка на сервере — Исполнитель с владельцем выясняет в этапе 1 (только чтение, файловый менеджер/терминал Beget), без доступа к `.env`.
- Платформа 2.0 — статический сайт (`index.html`, `js/`, `css/`, `js/dist/*`), публикуется GitHub Pages из `main` `platform-2-core`; работает из подпапки (`/platform-2-core/`).
- Данные RBI на сервере: перенос P2-0027/0036, роли P2-0033, id объектов и подрядчиков P2-0035 (`039`–`039d`).

## Решение владельца 25.10.2026 (упрощение — заменяет п. 2–3 и 6 ниже)

- **Порядок:** сначала P2-0035 (Качество по id), потом P2-0032.
- **Переход устройства — без сохранения неотправленного:** «потеря не синхронизированных данных не страшна». Перед днём — просьба всем синхронизироваться; новое приложение старые черновики/очередь **не читает и не отправляет**.
- Остаётся минимум: выкладка новой версии по прежнему адресу (там, откуда открывается старое приложение; откат — прежняя версия по метке) → новая база устройства загружается полностью; старая локальная база и кэш старого приложения удаляются один раз (чтобы не занимали место).
- Убрано: принудительная загрузка «уже загружавших RBI» (покрыто первой полной загрузкой), проверка старой очереди (`rbi_sync_queue`, `rbi_error_logs` — не переносить), проверки «через неделю»/«другой сотрудник на телефоне». Удаление старых отчётов со старого сервера — не в этом блоке, отдельно владельцем.
- Остаются: финальный перенос + сверка, закрытие PIN и открытой регистрации (разрешение по ADR-061a), временные пароли, короткая сверка действий тестовой учёткой, памятка.

## Решения и требования владельца (накопленные, 25.10.2026)

1. **Порядок дня:** все синхронизируют старое приложение → финальный перенос в «RBI» (очистка + полный, `docs/RBI_TRANSFER.md`) → сверка → выкладка кода Платформы 2.0 туда, откуда открывается старое приложение (откат — прежняя версия по метке) → вход по PIN выключен → **открытая регистрация на сервере закрыта** (разрешение владельца на изменение настройки Auth — отдельно, ADR-061a) → владелец выдаёт временные пароли кнопкой «Сбросить пароль».
2. **Загрузка на устройствах — без дублей, полная замена один раз** (владелец 25.10.2026: «данные не должны дублироваться, полностью заменить старые новыми единоразово»):
   - при первом запуске новой версии на устройстве со старыми данными РБИ — найти неотправленное в старой локальной базе (черновики, проверки «не отправлено», очередь); отправить или показать «у вас N неотправленных» и не терять;
   - затем новая база устройства (своя для компании/учётки) загружается **полностью одним разом**; записи с теми же id заменяются, а не добавляются;
   - после успешной загрузки старая локальная база и кэш старого приложения **удаляются один раз автоматически**;
   - устройства, уже загружавшие «RBI» до финального переноса, — принудительная полная загрузка один раз (ТД №176).
   - **Ровно один раз на устройстве:** после успешной загрузки и чистки — отметка «переход выполнен»; при следующих открытиях — без чистки и полной загрузки (обычная синхронизация). Не удалось (обрыв связи, закрыли) — отметки нет, при следующем открытии повтор загрузки и чистки (уже отправленное не отправляется повторно). Другой сотрудник на том же телефоне — своя новая база, повторной чистки нет.
   - Чистит только приложение по **тому же адресу**, что старое (браузер даёт доступ только к своим данным) — выкладка по прежнему адресу обязательна; телефон, где новое приложение не открывали, не меняется до первого входа.
   - Проверка на телефоне: до — старое приложение с данными и одним неотправленным черновиком; после — новые данные целиком, черновик не потерян, дублей нет (числа «Истории» = сверке), старая база удалена; три открытия подряд — чистка и полная загрузка только в первый; обрыв связи посередине — старое цело, при следующем открытии завершилось; вход через неделю — так же.
3. **Очередь отправки РБИ** (`rbi_sync_queue`, 1849) и журнал ошибок (`rbi_error_logs`, 2847) — проверить, что новое приложение не повторяет старую очередь; при сомнении — не переносить в финальном переносе (замечание приёмки P2-0027).
4. **Сверка действий «старое ↔ новое»** тестовой учёткой инженера до выдачи паролей: создать проверку с фото, СК, задачи, сформировать отчёт, База знаний.
5. **Памятка сотрудникам** (1 страница): как войти, первая смена пароля, что изменилось.
6. После перехода — удаление со старого сервера готовых отчётов (`shared_report_snapshots`, бакет `reports`) — владельцем, с архивом (ADR-069 п. 3).
