## 1. Цель

Администратор компании сам настраивает роли без программиста: копирует роль-шаблон, переименовывает, отмечает действия, назначает человеку на проект (или на всю компанию) со сроком, отзывает. Права действуют со следующего запроса, без правки кода модулей и без повторного входа.

## 2. Подтверждённое исходное состояние (main `bd2b841`)

- Сервер (схема `planfact`, миграции 001–004): `permission_catalog` (19 действий), `role_templates` + `role_template_permissions` (9 шаблонов), `company_roles` + `company_role_permissions` (копия шаблонов при создании компании), `role_assignments` (проект/вся компания, срок, отзыв), `company_modules`, `audit_log` (append-only, пока только по `works`).
- Проверка права — только `planfact.has_permission` / `has_company_permission`; точки входа `public.pf_my_permissions`, `pf_my_context`, `pf_assign_role` (запрет самоназначения), `pf_revoke_assignment`, `pf_list_works`, `pf_list_audit`.
- Клиент: вход почта+пароль — `src/platform/auth/auth.service.ts`; сейчас форма входа и шапка живут внутри модуля `src/modules/planfact/` (отклонение P2-0004). Меню платформы — `js/core/app-shell.js` (`getPlatformMenuItems`, пункты из manifest).
- Пользователей добавляет только SQL-скрипт (`docs/SERVERS.md`, техдолг №13). Экранов ролей нет.
- Техдолг из приёмки P2-0004: прямой SELECT `planfact.audit_log` содержит `plan_amount` (`docs/TECH_DEBT.md`).

## 3. Объём реализации

1. **Миграция 005** (только `planfact.*` и `public.pf_*`): функции `pf_list_company_roles`, `pf_list_company_members` (почта, роли, проекты, сроки), `pf_create_role` (копия шаблона или своей роли), `pf_rename_role`, `pf_set_role_actions`, `pf_delete_role`; доработка `pf_assign_role` / `pf_revoke_assignment` под правила защиты; аудит изменений ролей и назначений в `audit_log`.
2. **Правила защиты (на сервере):** всё — только с `security.roles.assign` на уровне компании; роли из шаблонов (`template_code is not null`) не меняются и не удаляются — только копируются; ~~нельзя выдать роли действие, которого нет у самого администратора (без повышения)~~ — **отменено владельцем 21.10.2026 (кнопка «Админ выдаёт любые права»)**: обладатель `security.roles.assign` может отметить любое действие каталога; самоназначение по-прежнему запрещено; нельзя назначить себе роль; нельзя отозвать/изменить так, чтобы в компании не осталось ни одного действующего назначения с `security.roles.assign`; роль с действующими назначениями не удаляется; действие вне каталога → отказ; всё — только в своей компании.
3. **Общий раздел «Компания»** в меню платформы, виден только при `security.roles.assign`: вкладки «Роли» и «Сотрудники». Вход — тот же `auth.service.ts`; если для этого нужно вынести форму входа из модуля в оболочку — вынести (это закрывает отклонение P2-0004), без изменения поведения «План/Факт».
4. **«Роли»:** список (шаблоны — с пометкой «шаблон, только копия»), «Копировать», переименование, галочки действий с русскими названиями по группам (Работы и план · Факт · Чек-листы · Деньги и выплаты · КС-2 · Настройки и журнал · Безопасность), удаление своей роли.
5. **«Сотрудники»:** участники компании (почта), их назначения (роль, проект или «все проекты», срок), «Назначить роль», «Отозвать». Добавления новых людей нет (решение владельца).
6. Техдолг журнала: закрыть прямой доступ к суммам в `audit_log` (прямой SELECT отозвать — чтение только через `pf_list_audit`) — в той же миграции 005.

## 3а. Единый источник истины

- **Владелец правил:** платформа, таблицы `planfact.company_roles` / `company_role_permissions` / `role_assignments`. Названия действий — `permission_catalog` (русские подписи групп — в одном файле клиента, ключи — только из каталога).
- **Где меняется:** только через `public.pf_*` функции миграции 005; прямых INSERT/UPDATE с клиента нет.
- **Проверка централизованности:** изменили галочку в «Ролях» → кнопка в «План/Факт» появилась/пропала без правки кода модуля.
