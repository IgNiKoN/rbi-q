# P2-0015 — ядро платформы: свой раздел базы `core`, Контрагенты компании, объект со ссылкой на заказчика

**Статус:** DONE (принято владельцем 23.10.2026, `reports/P2-0015/acceptance-record.md`)  
**Владелец продукта:** Igor (IgNiKoN)  
**Репозиторий:** `platform-2-core`, база — `main` после P2-0014.  
**Ветка:** `task/P2-0015-core`.  
**Источник:** ADR-066 (+ пп. 8–12 от 23.10.2026, `specs/2026-10-23-platform-data-architecture.md`) (утверждается этим блоком: открытые вопросы 1–2 закрыты владельцем 22.10.2026); решение владельца: «в План/Факте только тестовые объекты (Альфа, Бета…) — переносить сейчас, пока дёшево» → вариант A (отдельный раздел ядра), а не «ядро на месте».  
**Предшествующая задача:** P2-0014. Следующая: P2-0016 «Качество и Стройконтроль у покупателя на посмотреть (на устройстве, объекты из ядра)».

## 1. Цель

У платформы появляется ядро — один справочник компании, которым пользуются все модули: компании, люди и роли, модули, **Объекты** (объект → корпус → секция → этаж → помещение), **Контрагенты** (заказчики, генподрядчики, подрядчики, поставщики с ИНН), ЕИ и виды работ. План/Факт работает как раньше, но берёт всё это из ядра. Владелец заводит заказчика один раз и выбирает его в карточке объекта; реквизиты в КС-2 подставляются из карточки.

## 2. Подтверждённое исходное состояние (22.10.2026, только чтение)

- Все таблицы — в схеме `planfact` (миграции 001–014). На `planfact.projects`/`locations` ссылаются 11 миграций (~150 упоминаний); серверных функций ~170, почти все `security definer set search_path = pg_catalog, planfact` (имена таблиц без схемы) + часть с явным `planfact.<таблица>`.
- Клиент ходит **только через RPC** (`pf_*`, ~100 имён), схема в API не опубликована (ADR-061 п.2) → перенос таблиц не меняет клиентский код, если имена RPC сохраняются.
- Данных нет: только тестовые/демо компании (`is_test`, «Демо-компания»). Контрагентов как сущности нет; реквизиты заказчика КС-2 — текстом в `ks2_settings.requisites` (jsonb).
- Тесты: unit ≈ 304, `test:server` 241 PASS, PGlite-прогоны миграций.

## 3. Объём реализации

1. **Схема `core`** (миграция `016_core`): `create schema core`; `alter table … set schema core` для таблиц ядра (ADR-066 п.1): компании, участники, админы платформы, каталог и модули компаний, права/роли/назначения, `projects` (= Объекты, имя таблицы и колонки `project_id` **не переименовываем**), `project_members`, `locations`, `units`, `work_types`, `audit_log`. Модульные таблицы (ВОР, цены, сметы, КП, факт, бригады, КС-2) остаются в `planfact`. Функции: `search_path` → `pg_catalog, planfact, core`; тела с явным `planfact.<таблица ядра>` — пересоздать с `core.`. RLS, политики, внешние ключи, данные сохраняются. Имена RPC не меняются. Откат — `016_down` (обратный `set schema`).
2. **Контрагенты** (`017_counterparties`): `core.counterparties` (компания, название, ИНН, КПП, вид: заказчик / генподрядчик / подрядчик / поставщик — можно несколько, реквизиты jsonb, архив); RLS по компании deny-by-default; ИНН уникален в компании; право `core.counterparties.manage` в каталоге прав (шаблонам «Администратор компании», «ПТО» — да); RPC `pf_counterparties_*`. Экран **«Настройки → Компания → Контрагенты»**: список, поиск по названию/ИНН, добавить, править, в архив.
3. **Объект ↔ Контрагенты:** у `core.projects` ссылки «Заказчик», «Генподрядчик» (nullable, только контрагенты своей компании — проверка на сервере); выбор в «Справочники → Объекты». КС-2: если реквизиты заказчика в настройках КС-2 объекта пусты — подставляются из карточки заказчика; ручная правка как раньше сильнее.
4. **Один вход в ядро для модулей:** клиентский сервис `src/platform/core/` (объекты, локации, контрагенты, ЕИ) — План/Факт (`ProjectPicker`, «Справочники», КС-2) берёт данные только через него; правило в `standards/SINGLE_SOURCE_OF_TRUTH.md`: «модуль не хранит копий объектов/контрагентов и не вызывает RPC ядра в обход сервиса»; проверка — unit/grep-тест.

5. **Правила данных на будущее** (`specs/2026-10-23-platform-data-architecture.md`, решения владельца 23.10.2026): у таблиц ядра — `updated_at` (+ триггер) и `deleted_at` там, где их нет (для работы без сети); у `core.counterparties` — необязательная ссылка `platform_company_id` (контрагент = компания на платформе, для будущего обмена документами; в интерфейсе пока не показывается); тест-линтер миграций: новая таблица в `core`/`planfact` без `company_id` (кроме каталогов) или без UUID-ключа — FAIL. `core.links`, `core.events`, обмен и работа без сети — **не в этом блоке**.

## 3а. Reuse / единый источник истины

- **REUSE:** все RPC и экраны План/Факта, `CompanyScope`, `ProjectsTab`, конструктор ролей (P2-0004b), тестовая обвязка PGlite и `test:server`.
- **EXTEND:** каталог прав (новое право), «Справочники → Объекты» (поля заказчик/генподрядчик), КС-2 (подстановка реквизитов).
- **NEW:** схема `core`, `core.counterparties`, `src/platform/core/`, экран «Контрагенты».
- Владелец мастер-данных — **ядро**; План/Факт — потребитель. Качество в этом блоке не трогается (P2-0016, ADR-065).

## 4. Допустимые изменения

`supabase/migrations/016_*`, `017_*` (+ down), `tests/server/016_*`, `017_*`; `src/platform/core/*` (новое); `src/platform/company/*` (экран Контрагенты), `src/modules/planfact/{ProjectPicker,…}` и КС-2 — только переход на сервис ядра и подстановка реквизитов; каталог прав; `js/dist/*`, `sw.js`, changelog; документы этапа 6.

## 5. Запреты и границы

- Объекты RBI/Quality, Auth/JWT, Storage — не трогать (ADR-061/061a). Таблицы Качества в ядро **не** копировать (это блок переноса РБИ, ADR-065).
- Не переименовывать RPC, таблицы и колонки (`projects`, `project_id` остаются) — только перенос схемы.
- Договоры, документы, уведомления в ядро — не в этом блоке (ADR-066 п.6).

## 6. Критерии приёмки

- [ ] Таблицы ядра в схеме `core`, модульные — в `planfact`; все прежние тесты PASS без правки ожиданий.
- [ ] Контрагенты: заводятся в «Компании», компании друг друга не видят, дубль ИНН запрещён.
- [ ] У объекта выбирается заказчик/генподрядчик; КС-2 подставляет реквизиты.
- [ ] План/Факт берёт мастер-данные только через сервис ядра.
- [ ] Боевые объекты RBI не изменены (снимок до = после); откат 016/017 проверен на копии.

## 7. Риски

- Пропущенная ссылка `planfact.<таблица ядра>` в теле функции — ошибка только при вызове. Мера: этап 1 — поиск по телам всех функций после переноса + полный прогон серверных тестов.
- Одна CRITICAL-зона (миграции); вход/RLS RBI — в P2-0014, не здесь.
