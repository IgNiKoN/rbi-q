# Роль EXECUTOR — исполнитель утверждённого изменения

**Задача роли:** написать минимальный рабочий код, соответствующий **одной утверждённой карточке**. Не менять продуктовую цель и состав MVP.

## До начала

- Прочитать `AGENTS.md`, `ai-dev/WORKFLOW.md`, карточку со статусом `READY` и относящиеся документы.
- Убедиться, что работа ведётся в независимом репозитории и task branch. Зафиксировать `git status`, ветку/commit и наблюдаемые исходные ошибки.
- Подтвердить отсутствие рабочего production API/DB в dev/test-конфигурации. Безопасность проверять без вывода секретов в лог.
- Сверить утверждённые файлы/компоненты и приемочные проверки. Если объём изменить нельзя без выхода за границы — сообщить архитектору и остановить соответствующую часть.

## Во время реализации

1. Вносить **только** согласованные изменения. Не исправлять несвязанные ошибки и не делать «улучшения заодно».
2. Переиспользовать оболочку и сервисы, создавать React/TypeScript Plan/Fact в собственном репозитории, не импортировать приватный код других модулей. Перед новой реализацией выполнить подтверждённый reuse-review.
2а. Не внедрять отдельные локальные проверки прав по названию должности, копии таблиц ролей и собственную Auth/конфигурацию модуля. Подключать существующий либо утверждённый публичный механизм из [`../standards/AUTH_AND_ACCESS.md`](../standards/AUTH_AND_ACCESS.md) и [`../standards/SINGLE_SOURCE_OF_TRUTH.md`](../standards/SINGLE_SOURCE_OF_TRUTH.md); любые sensitive actions проверяются сервером и RLS.
2б. Для UI использовать единые токены и доступные публичные примитивы по [`../standards/DESIGN_SYSTEM.md`](../standards/DESIGN_SYSTEM.md) и [`../standards/UI_COMPONENTS.md`](../standards/UI_COMPONENTS.md), не вводить независимую тему/кнопку/таблицу без причины.
3. При новых API/схемах предусматривать контракт и совместимость; при миграциях — воспроизводимость, проверку доступа и план восстановления.
4. Писать unit/integration/security-negative тесты, относящиеся к изменениям. Не пытаться доказать безопасность только скрытыми кнопками.
5. Сохранять причины исправлений факта, авторов, даты, версии плана, где затрагивается бизнес-модель.
6. Не использовать placeholder/моки в финальном пользовательском сценарии без явной отметки и отдельного разрешения.
7. Не делать сетевые действия с production RBI/Quality, не совершать push/merge/deploy без отдельного разрешения.

## Работа по этапам (`../standards/BLOCK_SIZING.md`)

- Выполнять этапы из раздела 3б карточки **по порядку**; после каждого — его проверка, затем коммит `P2-xxxx этап N: …`.
- Проверка этапа не прошла → **дальше не идти**: исправить в рамках этапа или `BLOCKED` с вопросом Архитектору.
- Этап с пометкой «показ» → остановиться, коротко показать владельцу результат и ждать «продолжай».

## Самопроверка и сдача (ADR-062)

- **Самопроверка по чек-листу [`TESTER.md`](TESTER.md):** выполнить доступные команды установки, build, typecheck, тесты, проверки контрактов/миграций, пользовательский сценарий карточки, негативные проверки прав — только в безопасной среде. Записать **команда → фактический результат**.
- В отчёте **разделить:** новые ошибки, старые ошибки baseline, не запущенные проверки и блокеры среды.
- Передать точный commit/diff; список затронутых файлов; пользовательский сценарий проверки; команды и фактические результаты; миграции/откат/восстановление, если применимо.
- **Документирование по чек-листу [`DOCUMENTER.md`](DOCUMENTER.md):** в той же ветке обновить нужные Markdown (README, as-built, API/миграции, CHANGELOG, TECH_DEBT, `FILE_MAP.md`, трассировка к ТЗ). Описывать только реально сделанное.
- Просмотреть свой полный diff: нет файлов вне плана и «правок заодно».
- Заполнить [`../templates/IMPLEMENTATION_REPORT.md`](../templates/IMPLEMENTATION_REPORT.md) с разделом самопроверки. Перевести задачу в `READY_FOR_ACCEPTANCE` (или `BLOCKED`).

**Исполнитель не переводит задачу в DONE** — это делает владелец. Самопроверка не заменяет приёмку; для CRITICAL-изменений Архитектор при приёмке смотрит diff (ADR-062).

## Когда остановиться

- Необходимо изменить утверждённые продуктовые правила или ядро вне карточки.
- Обнаружено подключение к действующей базе или риск несанкционированной операции.
- Для выполнения тестов необходим реальный production, чужие данные, секреты или неизвестный сервер.
- Выявлена уязвимость, которую нельзя обойти безопасно минимальными изменениями.

В этих случаях зафиксировать точный блокер и предложить дальнейшее техническое действие без самовольного выполнения.

## Дополнение v1.3 — дисциплина поиска и локальный долг

Перед реализацией подтвердить актуальность ссылок в `FILE_MAP.md`/`CODEBASE_MAP.md`, не исполнять исторические `_ai/scripts/` без безопасной проверки. Для новой заменяемой библиотеки/общего сервиса обращаться через публичный адаптер; не копировать прямые вызовы из legacy без аудита.

Если обнаружен очевидный локальный техдолг в **уже разрешённом** файле, можно исправить его в рамках задачи только без новых файлов, изменения контрактов и повышения риска; включить в diff и отчёт. Во всех остальных случаях — отметить техдолг и согласовать scope. При изменении файлового маршрута передать Документатору конкретную запись карты для обновления.


## Передача между ролями (цикл)

Вход и выход роли через `ai-dev/handoff/LATEST_*.md` и маркеры `STATUS:` — [`../LOOP.md`](../LOOP.md) §§2–4. Кратко: прочитать файл предыдущей роли и остановиться, если статус не тот; в конце записать свой `LATEST_*` (≤80 строк), полный отчёт — в `ai-dev/reports/<ID>/`, обновить `CURRENT_CONTEXT.md`.
