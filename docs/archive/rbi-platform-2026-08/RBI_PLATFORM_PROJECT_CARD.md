# 0. Резюме для руководства (Executive Summary)

### Что предлагается утвердить

1. **Продукт:** собственную модульную платформу **RBI Platform** как цифровой стандарт производственного блока (не «приложение отдела качества»).
2. **Траекторию:** качество (уже работает) → строительный контроль (замена МРС / Стройконтроль) → производственные модули → возможность расширения на компанию.
3. **Проект:** официальный статус, куратор, заказчик, бюджет, команда, вехи М0–М8, пилот, критерии отказа от внешней лицензии.
4. **Услуги инициатора:** закрепить И. Н. Кондратьева как носителя концепции и владельца продуктового видения с отдельным пакетом ответственности, полномочий и мотивации — **не смешивая** это автоматически со штатной ролью разработчика или с операционной должностью начальника отдела.

### Почему это выгодно компании

| Аргумент | Содержание |
|----------|------------|
| Уже есть рабочий задел | Не greenfield: есть работающее приложение, обкатка на площадке, платформенный фундамент |
| Контроль актива | Код, данные, архитектура, инфраструктура — у компании (при оформлении прав) |
| Экономика внешней СК | Ориентир **~5 млн ₽/год** на внешнюю систему строительного контроля; отказ возможен только после пилота |
| Offline-first | Реальная работа на стройке без потери данных |
| Масштабируемость | Новые процессы — модулями, без переписывания всей системы |
| Снижение vendor lock-in | Меньше зависимости от внешнего поставщика процесса СК |

- Создана и развивается рабочая система на базе RBI Quality Pro.
- Модуль качества используется и обкатывается на строительной площадке.
- Выполнен перевод к платформенной архитектуре: **Platform Foundation закрыт (13/13)**.
- Заложены контуры строительного контроля, аналитики ПК СК, задач, базы знаний, ИИ, настроек и прав.
- Ведётся стабилизация, единый справочник подрядчиков, доработки по обратной связи.

# 5. Предпосылки проекта

## 5.1. Бизнес-контекст

Производственный блок Группы RBI управляет качеством, строительным контролем, подрядчиками и объектами в условиях:

- полевой работы на площадке;
- слабого/нестабильного интернета;
- множества подрядчиков и объектов;
- высокой цены ошибки (переделки, сроки, гарантия, репутация);
- потребности руководства в быстрой достоверной картине.

## 5.2. Текущие разрывы (**факт / подтверждённый контекст**)

1. **Разрозненные системы.** Качество — в собственном контуре; строительный контроль — во внешней системе (МРС / Стройконтроль) плюс импорт выгрузок.
2. **Ручные процессы.** Excel, ручная нормализация объектов и подрядчиков, «сведение» картинки для руководства.
3. **Дублирование данных.** Разные версии подрядчиков, объектов, статусов, задач между контурами.
4. **Зависимость от поставщика СК.** Процесс, данные и развитие функции завязаны на внешнюю систему.
5. **Стоимость лицензии.** Ориентир — **около 5 млн рублей в год** на внешнюю систему строительного контроля (`[требуется финансовая оценка]` точной суммы, состава лицензии и даты продления).
6. **Сложность развития.** Исторический монолит без платформенного ядра делает дорогим любое расширение.
7. **Нет единого цифрового пространства объекта.** Нет сквозной цепочки «объект → вид работ → подрядчик → проверка/замечание → устранение → аналитика → стандарт» в одной корпоративной системе.
8. **Риск потери контроля.** При неоформленных правах и личных доступах к инфраструктуре актив компании уязвим.

## 5.3. Почему «оставить как есть» хуже

| Вариант | Последствие |
|---------|-------------|
| Только внешняя СК | Продолжение лицензионных платежей; качество и СК в разных мирах |
| Только текущее приложение без статуса проекта | Нет команды, прав, поддержки, масштаба; высокий личный риск |
| Покупка ещё одной внешней платформы | Новый vendor lock-in; сомнительная заточка под процессы RBI; offline и единые данные не гарантированы |
| **Старт RBI Platform (предложение)** | Свой актив, управляемое развитие, путь к замещению МРС после пилота |

# 6. Проблема

### Формулировка одной основной проблемы

**Производственный блок не обладает собственной корпоративной цифровой платформой**, которая одновременно:

- работает offline на площадке;
- автоматически синхронизирует данные без потерь;
- объединяет качество и строительный контроль на единых справочниках, пользователях и правах;
- принадлежит компании как актив (код, данные, инфраструктура);
- расширяется модулями без переписывания системы.

### Последствия нерешения

- ежегодные затраты на внешнюю СК при ограниченной интеграции с качеством;
- управленческие решения на неполных/разрозненных данных;
- медленная отчётность и высокая доля ручного труда;
- невозможность системно снижать повторяемость дефектов и гарантийные риски;
- зависимость от внешнего вендора и/или от одного внутреннего носителя знания;
- блокировка цифровой трансформации производственного блока.

# 7. Цель проекта

## 7.1. Стратегическая цель

Создать и поэтапно развивать **RBI Platform** как **собственную модульную цифровую платформу производственного блока Группы RBI** с перспективой расширения на компанию (проектирование, закупки, гарантия, эксплуатация, продажи, маркетинг, продукт — по отдельным решениям).

## 7.2. Прикладные цели первого горизонта

1. Промышленно закрепить модуль **качества** как точку входа и эталонный модуль платформы.  
2. Развить модуль **строительного контроля** до уровня замены ключевых функций МРС / Стройконтроль.  
3. Обеспечить единые пользователи, объекты, подрядчики, роли, задачи, документы и аналитику.  
4. Оформить права, инфраструктуру и поддержку так, чтобы платформа была активом компании.  
5. Подготовить обоснованное решение по внешней лицензии (продлить / сократить / отказаться).

## 7.3. Что не является целью первого горизонта

- мгновенная замена всех ИТ-систем компании;
- отказ от МРС до пилота;
- переписывание всего кода на TypeScript «ради языка»;
- строительство multi-tenant платформы «на продажу наружу» без отдельного решения.

# 8. Суть решения

## 8.1. Что такое RBI Platform

**RBI Platform** — модульная корпоративная платформа:

```
App Shell + Core
    → Services (хранилище, sync, права, файлы, справочники, задачи…)
        → Modules (качество, строительный контроль, …)
```

Модули общаются через сервисы и события, а не напрямую друг с другом.  
Все модули используют **одни и те же** объекты, подрядчиков, пользователей, роли, задачи и статусы.

## 8.2. Почему это платформа, а не «приложение качества»

| Признак | Приложение отдела | Платформа (цель) |
|---------|-------------------|------------------|
| Граница | Один отдел | Производственный блок → компания |
| Данные | Локальные справочники отдела | Единая модель данных |
| Расширение | Новые функции в том же монолите | Новые модули на ядре |
| Права | Локальные роли | Централизованные роли/RLS |
| Владение | Часто «у автора» | Корпоративный актив |
| Offline | Опционально | Обязательное требование |

**Позиционирование для руководства:**

- качество — **первый этап и точка входа**;
- строительный контроль — **следующий контур**;
- целевой продукт ближайшего горизонта — **платформа производственного блока**;
- перспективное развитие — **на всю компанию**.

## 8.3. Обязательные требования платформы

1. Offline-first.  
2. Автоматическая синхронизация.  
3. Отсутствие потери данных.  
4. Единые пользователи, объекты, роли и права.  
5. Модульная архитектура.  
6. Сохранение действующего функционала при развитии.  
7. Поэтапное устранение технического долга.  
8. Расширение без переписывания всей системы.  
9. Контроль исходного кода, инфраструктуры и данных со стороны компании.

## 8.4. Ценностное предложение инициатора компании

Компании предлагается не абстрактная идея, а **путь**:

1. закрепить уже созданный задел как корпоративный актив;  
2. довести качество до промышленного стандарта;  
3. вырастить СК и проверить на пилоте;  
4. принять решение по ~5 млн ₽/год внешней лицензии на фактах;  
5. получить платформу, на которой можно наращивать ПТО, сроки, бюджет, гарантию и др.

# 13. Технологическая архитектура

## 13.1. Стек простым языком

| Технология | Роль для бизнеса |
|------------|------------------|
| JavaScript | Существующий рабочий код модулей и ядра |
| TypeScript + Vite | Новые модули — выше управляемость, без обязательного rewrite всего |
| PWA + Service Worker | Приложение на телефоне/планшете, кэш, обновления |
| IndexedDB | Локальные данные на устройстве (основа offline) |
| Supabase + PostgreSQL | Облачная БД и синхронизация |
| Row Level Security | Защита данных в БД |
| Файловое хранилище | Фото, PDF, документы |
| API | Обмен с облаком и будущие интеграции |
| Git | Корпоративный контроль версий |
| Cursor + ролевой цикл разработки | Ускорение разработки при сохранении дисциплины блоков |
| Python (по необходимости) | Миграции, аналитические утилиты, ИИ-скрипты |

## 13.2. Почему не переписываем всё сразу

Работающий функционал уже на площадке. Большой rewrite = риск потери данных, остановки обкатки и срыва доверия. Стратегия — **поэтапный strangler fig**: сохраняем работающее, выносим ядро, наращиваем модули.

## 13.3. Почему JS и TS вместе — нормально

Платформенный контракт — сервисы и события, а не «один язык навсегда». Новое пишем на TS; старое чиним точечно на JS, пока нет причины переписывать файл целиком.

## 13.4. Почему offline-first обязателен

Инженер на площадке не может зависеть от стабильного интернета. Осмотр, фото, замечание и задача должны сохраняться локально и доезжать до облака без потери.

## 13.5. Целевая схема запуска

`index.html → bootstrap / app.entry → Core → Services → Modules`

# 21. Экономический эффект

> Потенциал ≠ уже полученный эффект.

## 21.1. Прямой

- возможность отказаться от внешней лицензии СК (**~5 млн ₽/год**) после успешного пилота и М6;
- сокращение ручной отчётности и двойного ввода — `[требуется финансовая оценка]`;
- снижение стоимости владения интеграционным «зоопарком» — `[требуется финансовая оценка]`.

## 21.2. Косвенный

- меньше переделок за счёт раннего выявления системных дефектов;
- меньше гарантийных затрат в перспективе PDCA-контура;
- быстрее онбординг инженеров через базу знаний;
- выше дисциплина подрядчиков за счёт прозрачного цикла замечаний.

## 21.3. Стратегический

- собственная платформа и контроль над кодом/данными;
- снижение vendor lock-in;
- накопление корпоративных данных — топливо для аналитики и ИИ;
- платформа масштабирования на производственный блок и далее на компанию;
- управляемый цифровой стандарт процессов RBI.

## 21.4. Эффект от услуг инициатора (качественно)

| Без закрепления роли PO/архитектора | С закреплением |
|-------------------------------------|----------------|
| Развитие хаотично, «между операционкой» | Управляемый бэклог и вехи |
| Высокий риск потери знания | Передача знаний и снижение bus-factor — KPI роли |
| Сложно продать результат внутри компании | Есть заказчик, акты, критерии |

| Успешный пилот СК (М5) | Подтверждена замена процесса |
| Решение/эффект по внешней лицензии (М6+) | Прямой экономический рычаг |
| Подтверждённый эффект после замера | Не «обещание», а факт |
| Масштабирование (М7–М8) | Рост актива |

## 30.2. Мотивация по ролям (**предложение**)

| Роль | Модель |
|------|--------|
| Инициатор / владелец продукта | (а) выделенная проектная загрузка/надбавка + (б) веховые выплаты М1–М6 + (в) бонус за подтверждённый эффект после М6 |
| Архитектор инициативы | Если совмещено с PO — в пакете PO; если разделено — отдельная веховая часть |
| Разработчики | Веховые/релизные выплаты при приёмке без blocker |
| Эксперты подразделений | Компенсация экспертизы и приёмки |
| Участники пилота | Фиксированное вознаграждение за участие и качество обратной связи |

## 30.3. Принцип справедливости предложения

Инициатор предлагает компании актив и компетенцию «под ключ» (видение → архитектура → координация → пилот → решение по лицензии).  
Компания в обмен даёт статус, время, команду, IP-рамку и мотивацию.  
Иначе компания получает скрытый риск, а инициатор — скрытую переработку.
