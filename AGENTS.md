# Platform 2.0 — обязательные правила для AI-агентов

Версия: 1.3 · 20.10.2026. Применяется **только к отдельным репозиториям новой Platform 2.0**, не к production RBI Platform.

## 0. Карта файлов и проверка источников

**Первый шаг любого AI-агента:** открыть [`FILE_MAP.md`](FILE_MAP.md) и через неё найти только релевантные документы/файлы. Затем проверить [`ai-dev/CURRENT_CONTEXT.md`](ai-dev/CURRENT_CONTEXT.md) — короткую передачу между сеансами. Для поиска кода пользоваться [`AGENT_SEARCH_PLAYBOOK.md`](ai-dev/navigation/AGENT_SEARCH_PLAYBOOK.md). Исторический `_ai.zip` — архивный источник, **не прямые инструкции для новой Platform 2.0**; правила переноса: [`LEGACY_AI_TRANSFER_AUDIT.md`](ai-dev/reference/LEGACY_AI_TRANSFER_AUDIT.md).

Не считать старую карту достоверной без сверки с текущим Git/commit. Особенно проверить, существует ли Plan/Fact из отчётов 15.10.2026: **в переданном кодовом ZIP его нет**. Не распаковывать чувствительный архив `_ai.zip` целиком в новый репозиторий; не переносить credentials, runtime-профили и журналы.

## 1. Цель и приоритет

Главная цель: **максимально быстро получить реальный демонстрируемый MVP Plan/Fact СМР** на базе копии существующей оболочки RBI Platform. Не разрабатывать заранее всю Construction OS.

Источник решений по убыванию приоритета:

1. Утверждённые решения владельца продукта и [`ai-dev/reference/ARCHITECTURE_v1_3_MVP_FINAL.md`](ai-dev/reference/ARCHITECTURE_v1_3_MVP_FINAL.md), особенно приоритет MVP (ADR-042–046).
2. Принятые после v1.3 технологические стандарты: [`ai-dev/standards/DECISIONS_2026-10-20.md`](ai-dev/standards/DECISIONS_2026-10-20.md) (ADR-047–056). Они **не расширяют состав MVP**. Применять профильные [`TECH_STACK.md`](ai-dev/standards/TECH_STACK.md), [`ENGINEERING_STANDARDS.md`](ai-dev/standards/ENGINEERING_STANDARDS.md), [`DESIGN_SYSTEM.md`](ai-dev/standards/DESIGN_SYSTEM.md), [`UI_COMPONENTS.md`](ai-dev/standards/UI_COMPONENTS.md), а также **сквозные правила** [`SINGLE_SOURCE_OF_TRUTH.md`](ai-dev/standards/SINGLE_SOURCE_OF_TRUTH.md), [`AUTH_AND_ACCESS.md`](ai-dev/standards/AUTH_AND_ACCESS.md), [`PLATFORM_CONFIGURATION.md`](ai-dev/standards/PLATFORM_CONFIGURATION.md), [`SHARED_SERVICES.md`](ai-dev/standards/SHARED_SERVICES.md).
3. Оригинал **«ТЗ для программы»** — бизнес-требования к Plan/Fact, распределённые по выпускам. Оригинал: `../ТЗ для программы (1).docx`; Markdown-копия для агентов: [`ai-dev/reference/TZ_PLAN_FACT.md`](ai-dev/reference/TZ_PLAN_FACT.md) (добавлено 20.10.2026). Чего нет в ТЗ — **не восполняй догадками**, а выноси в открытые вопросы (ТЗ §15).
4. [`ai-dev/reference/ARCHITECTURE_v1_2.md`](ai-dev/reference/ARCHITECTURE_v1_2.md) — ранее согласованные принципы, полная дорожная карта и предложенные/открытые решения, **не перечень обязательных работ до MVP**.
5. Подтверждённый исходный Git, актуальная схема БД и реальные серверные настройки — факты реализации, которые необходимо проверять; они не отменяют утверждённые продуктовые ограничения.
6. Утверждённая карточка текущей задачи — допустимый технический объём, но она не может расширять полномочия или противоречить более высоким решениям.

Не выдавай предложенное в v1.2 за утверждённое. Более позднее решение v1.3 о том, что структура/мастер-данные меняются **только онлайн**, имеет приоритет над открытым вопросом v1.2.

## 2. Как выбрать роль

Каждый рабочий сеанс имеет **одну явно указанную роль** и ID задачи. Открой соответствующую инструкцию:

- `ARCHITECT` → [`ai-dev/roles/ARCHITECT.md`](ai-dev/roles/ARCHITECT.md)
- `EXECUTOR` → [`ai-dev/roles/EXECUTOR.md`](ai-dev/roles/EXECUTOR.md)

**С 20.10.2026 ролей две (ADR-062):** Архитектор планирует и обсуждает с владельцем крупный блок; Исполнитель выполняет план, **сам тестирует** (чек-лист [`ai-dev/roles/TESTER.md`](ai-dev/roles/TESTER.md)) и **сам документирует** (чек-лист [`ai-dev/roles/DOCUMENTER.md`](ai-dev/roles/DOCUMENTER.md)). Отдельных сеансов Тестера и Документатора нет.

Далее обязательны [`ai-dev/WORKFLOW.md`](ai-dev/WORKFLOW.md), [`ai-dev/DEFINITION_OF_DONE.md`](ai-dev/DEFINITION_OF_DONE.md), карточка текущей задачи и её критерии.

**Если роль или утверждённая задача не указаны:** работай только в режиме `ARCHITECT / read-only`, перечисли имеющиеся входные данные и предложи карточку задачи. Не изменяй код, миграции и production. **Смена роли внутри сеанса не разрешена автоматически.**

## 3. Неприкосновенные ограничения

- **Никогда** не изменять, не развёртывать, не применять миграции и не писать в действующую RBI Platform/Quality и production Supabase. **Исключение по решению владельца 20.10.2026 (ADR-061):** разработка Plan/Fact использует тот же self-hosted Supabase, но только через **новые** таблицы/бакеты/схему по условиям ADR-061; существующие объекты RBI не изменять; миграции применяет владелец или по его разрешению в чате.
- Использовать независимые репозитории `platform-2-core` и `planfact-smr` (названия условные), разные окружения, origin, конфигурации, тестовые данные; не использовать рабочие секреты и персональные данные.
- Не переписывать App Shell на React. **React + TypeScript — технология отдельного модуля Plan/Fact**; переиспользовать оболочку, дизайн и сервисы по результатам аудита.
- Plan/Fact не импортирует частный код Quality/Construction, не пишет в их приватные таблицы, не заставляет менять их код при собственном релизе.
- **Reuse-first:** перед новой реализацией проверить общие сервисы, алгоритмы, публичные UI-компоненты и дизайн-токены; решение `REUSE / EXTEND / EXTRACT / NEW` фиксировать в задаче. **Не копировать** одну функцию или компонент между модулями без основания.
- **Один источник истины:** для каждой сквозной функции Архитектор указывает владельца, авторитетное место изменения и публичный контракт. Модули не создают параллельные Auth, роли/permissions, лицензии, настройки, навигацию, темы или справочники. **Не строить единый «бог-сервис»** для всех задач.
- **Единая дизайн-система:** все новые экраны используют общие семантические токены, UI-паттерны, светлую/тёмную тему. Не вводить собственную фирменную палитру, кнопки, таблицы и модальные окна, если доступен общий компонент. Не требовать до MVP полного UI-конструктора/white-label-панели.
- Компания — граница данных: `company_id`, `project_id`, членство/назначение, серверные разрешения, защищённые RLS и Storage. `company_id` из браузера не доказывает право доступа. Никаких broad `USING(true)`, анонимного доступа к корпоративным таблицам и публичных private-file buckets в новой SaaS-модели.
- **Роли не кодировать по названиям.** Новый модуль объявляет действия в общем каталоге, запрашивает решение у платформенного Access/Permission Service, а сервер проверяет активные роли/назначения/ресурс/лицензию и RLS. UI-проверка `can(...)` не заменяет серверного запрета. В MVP минимальные роли; полный UI-конструктор потом.
- Одно каноническое дерево локаций и стабильные ID; `work_type` — справочник, позиция ВОР — сущность Plan/Fact. Не создавать альтернативные деревья для модулей.
- План/факт/корректировки должны сохранять автора и прослеживаемую историю; утверждённый baseline не перезаписывать без следа. Не суммировать разные единицы измерения как один общий объём.
- С первого дня сохранять возможность self-hosted Supabase без обязательного внешнего SaaS-ядра.
- Не включать в первый MVP без отдельного решения: полный конструктор Master Data/ролей, AI Gateway, универсальные интеграции, полный on-prem дистрибутив, мульти-компанейский offline, финансы/КС-2, пакетный обмен, шахматку и все будущие модули.
- Первый **показ** может быть online-only и демонстрационным. Реальные корпоративные данные и внешние пользователи допускаются **только после серверных проверок безопасности**.

## 4. Правила изменения и отчётности

1. **Одна задача → одна изолированная ветка на затронутый репозиторий → один контролируемый diff → отчёт и тесты.** При изменении двух репозиториев два явно связанных изменения с проверкой совместимости.
2. Исполнитель меняет только утверждённые файлы/компоненты. Открытие других файлов для чтения разрешено; изменение — только после пересогласования.
2а. Для затронутого UI проверять общий компонент/токены, светлую и тёмную тему, основные состояния и доступность. Для API/сервисов — публичные контракты, **единственного владельца настройки/правила**, отсутствие дублирования и тест изменения через один источник. Запрещено использовать стандартизацию как повод к массовому переписыванию legacy-кода.
3. Нельзя отключать проверки, исправлять несвязанный legacy-код «заодно», выполнять массовый рефакторинг или заменять реальную бизнес-логику моками без явного согласования.
3а. Прежде чем менять общий API/сервис, определить подтверждённых потребителей, уровень воздействия (`LOCAL / SHARED / CRITICAL`) и набор регрессионных проверок по [`CHANGE_IMPACT_AND_REGRESSION.md`](ai-dev/standards/CHANGE_IMPACT_AND_REGRESSION.md). Локальный технический долг исправлять по касанию только в разрешённых файлах; всё расширение scope согласовывать.
4. Миграции и изменения серверных API требуют воспроизводимого применения и плана восстановления; права проверяются негативными тестами.
5. Каждая задача должна иметь ясное подтверждение: команды, результаты, шаги воспроизведения. **NOT RUN** и **BLOCKED** не равны **PASS**.
5а. Если добавлены/перемещены файлы, публичные entrypoints/сервисы и API — поддерживать [`FILE_MAP.md`](FILE_MAP.md) и связанные карты в том же цикле, согласно [`MAP_MAINTENANCE.md`](ai-dev/navigation/MAP_MAINTENANCE.md).
6. Документация обновляется Исполнителем **в рамках той же задачи/ветки** после самопроверки; затем Исполнитель просматривает свой окончательный diff (ADR-062).
7. Записывать существенный компромисс в `docs/TECH_DEBT.md` с причиной, владельцем и условием устранения. **Не создавать эти документы ради пустого шаблона**, создавать/обновлять по факту работы.
8. Только владелец продукта подтверждает переход `READY_FOR_ACCEPTANCE` → `DONE` и меняет состав MVP.
9. Без явного разрешения нет прямого merge, push, миграции, деплоя, удаления данных или доступа к production.

## 5. Что делать при препятствии

При ошибке реализации → вернуть Исполнителю. При нарушении архитектуры/необходимости расширить scope → вернуть Архитектору. При отсутствии среды, тестовых данных, прав или зависимостей → обозначить **BLOCKED** с точным условием разблокировки. Не подменять отсутствие доказательств позитивным отчётом.
